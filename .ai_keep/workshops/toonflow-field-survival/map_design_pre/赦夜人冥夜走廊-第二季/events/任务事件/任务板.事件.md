# 任务板
走进任务板后 点击"任务" 可以接受任务 和完成任务 和放弃任务

ai 获取可接任务，程序获得已接任务。状态：进行中/已完成（点击获得奖励），可放弃任务，任务信息（点击查看信息，暂时任务详情，用户也可发送信息，ai回答）

### 1.2 插件侧（`entry.ts`，权威）

| 新增 | 作用 |
|------|------|
| `QuestDef` / `QuestObjective` / `QuestProgress` | 数据契约（见 `任务参考.list.md` §1） |
| `s.questBoard` / `s.quests` / `s.questView` | 任务定义 / 玩家进度 / 前端视图；随 `sys_state` 持久化 |
| `normalizeQuestDef` | 任意来源（AI/JSON/参数卡）收敛：标题截 12 字、type 与 kind 走枚举、非法项丢弃 |
| `noteQuestKill` / `noteQuestGather` / `noteQuestTalk` | 进度钩子，分别挂在 `damage()` 击杀分支、`addBagItemToCard` 入包、`sys_chat` |
| `syncQuestArriveAuto` | 每 tick：非 confirm 的到达目标走进半径即完成 + 护送货物跟随玩家 |
| `questArriveOk` | 点「到达」时校验地图 + 半径 |
| `spawnQuestCargo` / `removeQuestCargo` | 护送货物 `questcargo_<任务id>`；**被打掉 → 任务 failed** |
| `buildQuestView` | 产出 `available / active / done / turned` 四栏 + `canTurnIn / canArrive / atDest / progress` |
| `setPlayerFlag` / `removeBagItemFromCard` | 完成时写 `player_flags`（供事件系统 `flag_check`）；交付时扣背包 |
| `ensureQuestDefs` | 开局读 `pluginData["quest_defs"]`（CLI 上传的故事任务表） |

**状态机**：`active → done（目标达成，待交）→ turned（已领奖）`；护送另有 `active → failed`（货物被打掉，放弃后可重接）。

## 1.6 修复：任务板只显示一条同样的任务（2026-10-16 实测反馈）

**现象**：走进任务板只看到一条（重复的）委托——「清剿周边湮物」。

**根因（三层，逐层实证）**：

1. **`quest_defs` 从来没进过任何环境**。CLI 上传那步实际没执行（后端 `op=get quest_defs` 两个环境都返回 `null`）；
   dev-host 拟真宿主的 `pluginData` 是 localStorage，更读不到后端数据 → 任务板恒为空。
2. **「AI 生成委托」永远走兜底**。后端 `task-speaker-agent` 是**台词发言器**（`def.prompts.ts` 的系统提示词只让它生成 NPC 对白），
   对「只输出 JSON 数组」的请求实测回的是「嘿，冒险者！来看看今天的新委托吧——」→ `JSON.parse` 必失败 → 落兜底。
   旧兜底只有 **1 条**且 id 用 `Object.keys(s.quests).length + 1` 算（与板上条数无关）→ 连点几次堆出多条**同 id 同标题**的任务，
   Vue `:key="q.id"` 撞 key → 界面上看起来就"只有一条同样的任务"。
3. **任务数据的地图名与运行时对不上**。`quests.json` 写文件名 slug（`mulberryTown`），
   运行时 `s.levelName` 是显示名（`Mulberry Town`）→ `def.map === lv` 恒 false → 12 条全被标「别处发布」，
   arrive/explore 的 `atDest` 也永远不通过。

**修复**：

| 位置 | 改动 |
|------|------|
| `vite.config.ts`（dev-host PAGE） | 新增 `seedQuestDefs()`：story 加载后把故事目录的 `quests.json` 播种进插件会话数据（等价 CLI 上传）。**双 scope 写入**（`all` + `__STORY_SESSION_ID__`），因为并发 `tf_plugin_loaded` 会让 entry ctx 与 iframe SDK 落到不同 session；已有数据则跳过，不覆盖 |
| `entry.ts` `ensureQuestDefs` | 板子为空**或只剩兜底委托**（`from=ai-fallback`，或历史版本 `from=ai` 且 id 以 `QAI` 开头）→ 载入故事任务表；否则不动（保护宿主下发内容） |
| `entry.ts` `generateQuestsByAI` | 兜底改 **3 条不同类型**（清剿周边湮物 / 采集应急物资 / 探查附近区域），id 按板上已有 `QAI` 序号递增；入板前**按标题去重**，重复点击不再堆一模一样的任务；兜底委托标 `from=ai-fallback` 以便让位给故事任务表 |
| `entry.ts` `normalizeQuestDef` | 新增 `normQuestMap()`：任务数据里的地图名 slug → 运行时显示名（`mulberryTown` → `Mulberry Town`，含 dungeon/forest 等 17 个映射），`def.map` 与 `objective.map` 都过一遍 |
| `workshops/.../map_design/<故事>/events/任务事件/quests.json` | 从 `map_design_pre` 复制一份到运行时故事目录（dev-host 播种读这里） |
| 后端 `quest_defs` | 用 `POST /plugin/data {op:set, sessionId:"all"}` 把 12 条任务表写进 `localhost:60002` 与 `10.10.2.195:60002`（等效 CLI 上传，真实宿主路径生效） |

**实测（playwright + localhost:3000 dev-host，见 §5）**：任务板面板 12 条（8 条本图可接 + 4 条「别处发布」）、
接取后「进行中」页签出现 `采集 夜合花 0/3` 进度条、AI 生成委托新增 3 条 `QAI01-03`、再点一次 0 新增（去重生效）。

### 1.8.1 顺带修掉的 3 个真 bug（都是跑 E2E 才暴露的）

1. **`sys_quest_accept` 首次接取必被拒**（`entry.ts`）。原实现先 `ensureProg()` 生成 `{id,status:"active"}`，紧接着的 `p.status === "active"` 守卫把「首次接取」判成「已经在进行中」并提前 return →
   `acceptedTick` / `kill·gather·talked` 容器 / `cargoId` 全都没写：**限时任务永不超时、护送货物永不生成**。
   改为只读既有进度做守卫；同时补 `if (!s.quests || typeof s.quests !== "object") s.quests = {}`（原先靠 `ensureProg` 顺带建容器，去掉后 `s.quests` 为 undefined 会直接抛 `Cannot set properties of undefined`，被宿主记为「entry.js 执行失败」）。`restoreSys` 也补了同一句兜底。
2. **dev-host 的 pluginData 命名空间/会话分家**（`vite.config.ts`）。game iframe 的 SDK（`toonflowJsApi`）postMessage 时**不带 `pluginId`**、也**不带 `sessionId`**，而 dev-host 监听器直接拿 `undefined` 组 key、兜底 `sessionId||"all"`；entry.js 侧（`entryCtx`）却显式带 `ENTRY_PLUGIN_ID` + `__STORY_SESSION_ID__` → 同一份 `player_flags` 落在两个完全不同的 key 上，
   「后端写 flag / 前端读 flag」在 dev-host 下**永远对不上**（真实宿主是同一张 `t_plugin_session_data`，`/plugin/data` 的 `sessionId` 还是必填）。修：监听器里 `pid = pluginId || ENTRY_PLUGIN_ID`、`sid = sessionId || window.__STORY_SESSION_ID__ || "all"`。
3. **事件引擎 flag 缓存陈旧**（`eventEngine.ts`）。`loadFlags()` 有模块级 `flagCache`，只在首次读时填。后端（任务交付 → `setPlayerFlag`）或系统面板写的 flag 它看不到。
   修：导出 `invalidateFlagCache() / reloadFlags() / setEventFlag() / delEventFlag()`；`onMapEntered()` 开头清缓存（切图 = 「后端进度可能已变」的天然同步点）；系统面板 `onSysSetFlag/onSysDelFlag` 改走 `setEventFlag/delEventFlag`（不再直写 pluginData），`onSysReloadEvents` 顺带 `reloadFlags()`。

## 2. 三条硬约束（踩过的坑）

1. **任务不是事件**。事件引擎只有 `enter_map` / `interact` / `area_enter` 三个挂载点，`kill_count` 之类写了永不触发。
   所以任务进度全部落在插件的伤害/入包/对话链路上，地图集只提供**数据**（`quests.json`）+ **板子位置**。
2. **进度只认宿主**。`s.quests` 随 `sys_state` 落库；前端改了也会被下一次 tick 覆盖。面板只读 `s.questView`。
3. **护送的仪式感靠 `confirm: true`**。写成自动完成就没有「到达」按钮了；`confirm=false` 走进半径即完成。
4. **flag 只有一个真相源，但有两个「读的人」**。事件引擎（Vue）与插件后端（entry.js）都能写 `player_flags`。
   引擎侧有会话内缓存 → 后端写完必须让引擎「重新读」（本项目做法：切图 / 重载事件时清缓存）。
   另外 `state.events` 里由事件脚本 `ui.event()` 写的行是**前端本地 push**，会被下一次后端 tick 的整体 state 覆盖 →
   剧情推进的可观测落点请用 **flag + toast**，不要依赖 `state.events`（调试断言也别拿它当准）。
5. **dev-host 调试必须先等 `window.__STORY_SESSION_ID__` 就绪再开局**。它是 `loadStoryData()` 里异步注入的；
   早于它就开局，flag 会先落到 `sessionId="all"`，之后注入完成又改成故事会话 scope → 同一批 flag 分家，
   `enter_map` 的 `flag_check` 就会误判（表现为一次性开场事件反复触发、或任务 flag 读不到）。
