# 插件工作机制（2026-10-07 初版 · 2026-11-12 修订）

> 范围：以 `toonflow-field-survival`（野外生存 minigame 插件）为实例，描述**当前**（2026-11）插件的实际运行方式。
> 文件身份与"双入口"原始设计见 [`entry.js和entry.ts 的关系和说明.md`](./entry.js和entry.ts 的关系和说明.md)。
> **2026-11-12 修订**：补入内存态（权威）/ DB（快照）两层、共享执行层、O1~O4 优化、MCP 接入面（第三写入方）、
> 以及 dev-host 拟真宿主桩的工作方式。

## 一句话总结

**几乎所有游戏业务（距离判断/AI/伤害/掉落/存档/传送/NPC/物品/技能）都跑在后端**，**前端只负责"画"和"收输入"**。前端拿到的就是纯数据 state，自己唯一的"产出"是玩家输入（键鼠/点击）和少量本地视觉缓存。

## 三个进程的协作

```
┌──────────────┐   postMessage(tf_plugin_state 推回)
│  5175 宿主    │ ◀──────────────────────────────────────┐
│ Toonflow-web  │                                          │
│ (Vue+iframe)  │                                          │
└──────┬───────┘                                          │
       │ postMessage(tf_plugin_tick/action)                  │
       │ dispatch 玩家输入 + 游戏事件                       │
       │                                                    │
       ▼                                                    │
┌──────────────┐   POST /plugin/tick (axios)   ┌──────────────────┐
│  iframe      │ ─────────────────────────────▶ │  60002 后端      │
│ 60002        │   params={player, localEnemies,  │  toonflow-game-app│
│ getAsset     │           levelName, walkGrid,  │  (Express+tsx)   │
│ ui/game.html │           input}                │                  │
│ (vite内联JS) │ ◀───────────── state 推回 ──── │  entry.js         │
└──────────────┘                                  │  handle_action    │
                                                   └────────┬─────────┘
                                                            │ 读写
                                                            ▼
                                                   ┌──────────────────┐
                                                   │ sqlite            │
                                                   │ toonflow-app-     │
                                                   │ run-db/db.sqlite  │
                                                   │ t_plugin_session_ │
                                                   │ data (state/      │
                                                   │  物品/世界书等)   │
                                                   └──────────────────┘
```

**单帧周期**（10Hz）：

1. 玩家在浏览器里按键/点击 → `App.vue` 更新 `lastLocalPose` / `input.dx/dy/moveTo`
2. 浏览器 RAF 循环（`loop(ts)`）每 100ms 触发 `sendTick("tick", {...})`
3. `bridge.sendTick` 在父窗口 postMessage `{type:"tf_plugin_tick", action, params}`
4. 5175 宿主 `onPluginIframeMessage` 收 → `handlePluginTick` → `store.api.pluginTick` → axios POST `http://127.0.0.1:60002/plugin/tick`
5. 60002 路由 `routes/plugin/tick.ts` 验证 session / 加载 manifest / 调 `executePluginAction(ctx, action, params, prev)` → `entry.handle_action`
6. **entry.handle_action 是所有业务逻辑的入口**（`case "init"|"start"|"tick"|"skill"|"item"|"sys_*"|...`）
7. entry 改完 state → **共享执行层更新内存态（权威）** + 按 O2 节流写 DB 快照 → 把 state 返回给宿主
   （纯帧 tick 且状态无变化时按 O1 回 `state:null`，前端跳过合并，~48KB → ~1KB）
8. 5175 宿主 `pushPluginStateToIframe` → `frame.contentWindow.postMessage({type:"tf_plugin_state", state})`
9. 浏览器 `bridge.onHostState` 收 → 合并本地视觉缓存 → `state.value = incoming` → Vue 响应式重渲染 canvas/HUD/minimap

- **后端 60002**：`PluginExecutor.loadEntryModule` 按 `manifest.main`（`entry.ts`）拼路径，**优先 .js，回退 .ts**；**按 mtime 失效**（改了 entry.js 不用重启 60002，下一次 tick 自动重 import）。
- **前端（5175 浏览器）**：**完全不看 entry.js / entry.ts**。宿主用 `iframe.src = api.pluginAssetUrl(pluginId, "ui/game.html")`（PluginExecutor.ts:170-172 + toonflow.ts:1032-1037），加载 `ui/game.html`——它是 `vite build` 把 `vue/src/App.vue` 全部 vue 组件**内联打包**出来的 JS bundle（1.4-2.8MB）。`ui/game.html` 通过 `import` from `./bridge` 调到 `bridge.ts`（bridge.ts 维护通信协议）。
- **`entry.js` 在当前架构下只服务后端**，前端代码独立于 `entry.*`，跟 `ui/game.html` 是两套独立的产物。
- `manifest.json` 的 `main: "entry.ts"` 是 manifest 规范字段名（语义上"后端入口"），**不是 entry.js = entry.ts 编译产物的依据**——manifest 字段名沿用了 ts 后端的命名传统，但实际 import 的是 js。

## 前端是"纯渲染 + 输入采集"，但有一处**真的算业务**——mapmob 初始化

野怪的"几何数据来源"在前端：Tiled JSON 描述"森林地图上有一只哥布林在 tile (52,34) 位置"。`App.vue.switchLevel` 读 Tiled JSON，**前端自己 new 出 mapmob_ 实体**（id = `mapmob_<tiledId>_<ts>`，hp/atk 取自 MOB_ARCHETYPES）→ 塞进 `state.value.entities` → 通过 `localEnemiesPayload` 上报后端 → 后端 `applyLocalEnemies` 据此接管 AI。

**这是唯一的前端"业务数据生产"环节**——后端不读 Tiled JSON（只解 walkGrid）。Tiled 解析逻辑只在 App.vue。

**fix⑧ 的 bug 来源**：前端 mapmob 上报后端 → 后端跑 AI → state 推回前端 → 前端合并逻辑（onHostState 5340-5380）把"mapmob_* 前缀"当成"本图怪"全部回填 → 切图瞬间后端在推旧图 state → 旧图怪回流 → 前端认为"还是本图怪"再次上报 → 雪球。修复就是用 `currentMapMobTs` 世代时间戳把"本帧新建的怪"和"后端在途的旧图怪"区分开。

## 通信协议（bridge.ts 维护）

| 方向 | 消息 type | 内容 |
|---|---|---|
| iframe → parent | `tf_plugin_tick` | 每帧 `sendTick("tick", {input, player, localEnemies, walkGrid, levelName})` |
| iframe → parent | `tf_plugin_action` | 一次性动作 `sendToHost(action, params)`（start/skill/item/sys_*/page/exit/revive） |
| iframe → parent | `tf_plugin_chat` | NPC 对话请求/响应 |
| iframe → parent | `tf_plugin_loaded` | iframe 加载完成握手（5175 宿主重试 20 秒） |
| parent → iframe | `tf_plugin_state` | 推回 state（带 response/actions） |
| parent → iframe | `tf_plugin_tick_halted` | 409 连击防护，停发 tick（收到新的 tf_plugin_state 自动解除） |
| parent → iframe | `tf_plugin_data` | iframe 读 `t_plugin_session_data` 通道（仅插件侧） |

**关键设计**：iframe 与后端（60002）**不同源**（5175 iframe vs 60002），且 iframe 没有 JWT，所以**所有宿主侧操作都经 5175 代理**：iframe → 5175（postMessage）→ 60002（HTTP + JWT）→ 5175（state 推回）→ iframe（postMessage）。`bridge.ts` 只负责 iframe ↔ 5175 那一段。

**这条跨域链路带来的特殊问题**：
- iframe 没 JWT，鉴权由 5175 持有
- 跨域 postMessage 通信，事件源（`e.source`）校验要谨慎——bridge.ts 信任 `window.parent` 不校验（5175 同源）
- 高频 tick（10Hz × 2 进程 × 跨域 postMessage）有序列化成本——`JSON.parse(JSON.stringify(...))` 防 Vue Proxy DataCloneError（bridge.ts:36-46）

## 状态/存档（2026-11-12 重大修订：内存态是权威，DB 是快照）

### 两层状态模型

```
        ┌──────────── 内存态（权威，单进程 Map）────────────┐
        │  key = userId:sessionId:pluginId                 │
        │  PluginSessionDataService 的热态缓存               │
        │  ★ 每次请求都更新；进程重启后从 DB 快照冷启动        │
        └───┬───────────────────────────────────┬───────────┘
            │ 读（命中内存态就不查 DB）           │ 写（每次请求）
            ▼                                    ▼
      entry.handle_action                   内存态立即更新
      （拿 state 重建、推进一次）                 │
                                                │ O2 节流（2s）+ 脏检查
                                                ▼
                                    t_plugin_session_data
                                    （sqlite，仅供崩溃/刷新恢复）
```

**为什么必须这样**：`entry.handle_action` 是**无状态**的（每次拿传入 state 重建、只推进一次 step），
权威状态必须由宿主保管。若每请求都从 DB 读，O2 的 2s 落盘节流会把「未落库的中间状态」整体丢弃
→ **世界推进速率掉到 0.36Hz**（= 落盘速率），连带 CD 递减慢 2.7 倍、野怪 AI 变慢、死亡渐隐卡住、
「玩家已贴近野怪但 attack 说附近没有敌人」。
实测数据见 `md/test/toonflow-field-survival/即时交互测试报告_2026-11-12.md`。

### 写操作必须走共享执行层（防状态覆盖）

| 模块 | 职责 |
|---|---|
| `src/lib/plugins/PluginStateExecutor.ts` | **唯一写入口**：`executePluginActionWithState()`——读内存态 → 执行 entry → 宿主消费 writeback → 写内存态 → forceSync 判定 → O2 节流落盘；并持有会话串行锁注册表（fast/slow） |
| `src/lib/plugins/PluginExecutionContext.ts` | 会话加载 + ctx 组装（manifest / 动态卡 / 角色 / 世界名），tick 与 MCP 共用 |
| `src/lib/plugins/PluginSessionDataService.ts` | 内存态热缓存 + DB 读写 + `pluginScopeKey()` 统一 scope 键派生 |

**铁律**：任何新的写入方（未来的第三个接入面）都必须调 `executePluginActionWithState()`，
**不要另写一套「读 DB → 调 entry → 写 DB」**——否则会与 tick 互相覆盖。

### 其余状态约定

- **前端 state.value 是镜像**：每 tick 推回后经 `onHostState` 合并、赋给 `state.value`，触发 Vue 响应式重渲染
- **跨会话共享**：`sessionId="all"` 写入的 `t_plugin_session_data` 记录对所有会话可见（用于世界书、商城商品等全局数据）
- **回写 (writeback)**：entry 在 state 里写增量补丁 `state.writeback`（物品/技能/金钱变化），共享层消费后合到 `state.player.parameterCardJson`，下次 start 时用
- **结算写回**：`result.written` 标记防止重复写参数卡
- **删除也要清内存态**：`removePluginData` / `clearPluginDataBySession` 必须同步清热态，
  否则「#退出」删了 DB 行、内存态还在 → heal 守卫认为「游戏仍在进行」→ 面板死灰复燃

## 三个写入方（2026-11-12 新增 MCP 接入面）

| 写入方 | 入口 | 锁 | 落盘 |
|---|---|---|---|
| 帧 tick | `POST /plugin/tick` | fast 锁 | O2 节流（2s） |
| 慢命令 `sys_*` | `POST /plugin/tick` | slow 锁（与帧 tick 不互斥） | O2 节流 |
| **AI agent（MCP）** | `POST /plugin/mcp`（`tools/call`） | **同一把 fast 锁** | **forceSync：返回即落库** |

MCP 写操作走 entry 权威通道（`kill_mob` → `attack`、`clear_effect` → `ai_clear_vfx`、
`spawn_entity` → `ai_spawn`），**不在 MCP 层直接改 state**（否则绕过经验/掉落/任务计数的权威结算）。
设计细节见 [`插件的网络通信机制_v3.design.md`](../../toonflow-field-survival/网络通信/插件的网络通信机制_v3.design.md)。

## dev-host 拟真宿主桩（本地调试专用，3000 端口）

`plugins/<plugin>/vue` 的 vite dev server 自带 `--conn` 模式的拟真宿主桩：
浏览器打开 `http://localhost:3000/` → 选人 → 开始游戏，无需另起 5175 宿主。

| 特点 | 说明 |
|---|---|
| **自己就是前端 + 宿主** | iframe 加载插件本体（`?__inner=1`），桩页（顶层）代理所有 action |
| **tick 由客户端驱动** | 桩的 `_devHostInterval`（50ms 服务器 tick）在**收到客户端 `tf_plugin_tick` 消息**后才创建 |
| **自循环依赖（已知限制）** | 客户端不发 tick（前端 loop 早退）→ 桩不推进 → 不回推 state → 前端画面冻结。**这是桩的调试局限，不是产品缺陷** |
| 排查姿势 | 用 `window.__devHostState()` / `__devHostPluginState()` / `__devHostModify(patch)` / `tryEntryAction(action, params)` 直接驱动/观察桩内状态 |

> ⚠️ dev-host 桩**不接 60002 后端**：状态全在 vite 进程内存里（`entryState` 变量），
> 验证真实链路（含落库、鉴权、并发）必须打 60002。

## 修复一致性原则（fix 之间的互斥关系）

| 修复 | 触发条件 | 与其他修复的互斥 |
|---|---|---|
| fix⑤（缺口①）野怪/玩家 bounds 夹边 | 前端 tick 报 `localEnemies.bounds` | 与 fix⑥ 互锁：bounds 字段是"切图新图范围"标识 |
| fix⑥ applyLocalEnemies 忽略已接管清单 | epoch 相同（前端没结构性变化） | fix⑦ 在 epoch 相同时再检查实体是否真在——但 fix⑦ 是"丢失重建兜底"，应只在异常路径触发 |
| fix⑦ 实体丢失时重建 | 实体被 start/restoreSys/handleLevelChange 清空但 epoch 仍存 | 期望"切图清怪 = handleLevelChange 内部完成，前端不再上报旧怪"；fix⑧ 用世代时间戳保证这一点 |
| fix⑧ 切图雪球过滤 | switchLevel 前后端在途窗口 | 让 fix⑦ 永远不需要触发——正常切图前端不报旧怪，后端不重建 |

**任何"清除/重建"流程都要考虑 fix⑦ 的"丢失重建"语义**：因为 epoch 标记 + 实体实际状态可能因为多个路径（start/restoreSys/handleLevelChange/regionTick/...）不同步，**修复"丢失自动重建"虽然解决了 0 敌人死锁，但也可能让切图的"清旧"失败**。fix⑧ 是从"前端只报本图世代"根本上消解这个矛盾。

## 易错点

1. **"前端是只渲染"≠"前端没有任何业务数据"**——mapmob 清单由前端生成并初始化上报；切图时序错了就会雪球（fix⑧ 修的就是这个）
2. **"entry.js = entry.ts 编译产物"是观察结果而非设计**——前端不看 entry.js（用 ui/game.html），后端只看 entry.js。改 entry.ts 不重编译 = 前端不受影响、后端跑老代码
3. **"5175 宿主代理 iframe 调后端"不是代理——是 5175 持有 JWT 真做 HTTP 调用**。iframe 没 JWT，跨域 postMessage 只能跟 5175 通信
4. **state.version: 2/3/4 兼容**——entry.handle_action 入口会根据 version 决定是恢复还是重建 state（entry.ts:2640-2643）
5. **handle_action action 集合**：`init|start_init|start|tick|skill|item|page|exit|revive|sys_party|sys_teleport|sys_travel|sys_chat|sys_sellItem|sys_shop_refresh|sys_rest|agent_run|...`——不是只有 init/tick，其他业务都走这条

### 2026-11-12 新增易错点

6. **状态写操作只有一条路**：`executePluginActionWithState()`。自己写「读 DB → 调 entry → 写 DB」会与 tick 互相覆盖
   （AI 刚杀的怪被 tick 复活）。新增写入方（MCP 等）必须复用共享层。
7. **CD / 特效按真实经过时间衰减**，不是按 tick 次数（`entry.ts` 的 `tickDeltaMs()`：`_dec = round(dtMs/100)`，最小 1）。
   → 连续快速发 tick 不会让 CD 掉得更快；测试断言 CD 时必须按 100ms 真实节奏发请求，否则读到的值不可信。
8. **读状态也会推进状态**：读 CD/位置的那次 `tick` 请求**自己又推进了游戏**。
   要读权威值用不推进的通道（`MCP query_state` 读内存态），别用 DB 快照（O2 节流滞后 2s）。
9. **真实链路里 state 是权威的，不能改**：调试时想「把怪挪到玩家旁边」在 dev-host 桩里可行（内存对象），
   在 60002 真实链路里改不了——用 `MCP spawn_entity` 走 entry 权威通道生成测试目标。
10. **`npm run local` 才是本地开发启动方式**：NODE_ENV=local → `env/.env.local`（正确的 DB/上传目录）。
    裸 `npx tsx src/app.ts` 走 `env/.env.dev`（路径为空）→ 插件目录解析错误 → 「entry 模块加载失败」。
11. **安装副本路径用 manifest.id，不是文件夹名**：`toonflow-app-run-db/plugins/1/com.toonflow.minigame-field-survival/entry.js`。
    编译完忘了 cp 到安装副本 = 「改了不生效」最常见的原因。
12. **dev-host 桩（3000）不接 60002**：状态全在 vite 进程内存。验真实链路（落库/鉴权/并发）必须打 60002。
