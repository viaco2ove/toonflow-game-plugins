# 数据储存 · t_plugin_session_data

> 范围：描述**当前**（2026-10）插件数据的实际储存方式。以 `toonflow-field-survival`（野外生存）为实例。
> 表结构、访问链路、dataKey 清单均对照 `src/toon_plugins/toon_client.py`、`plugins/toonflow-field-survival/entry.ts`、`vue/src/*` 实际代码整理。

## 一句话总结

插件自己的运行时数据全部存在宿主的 **SQLite 表 `t_plugin_session_data`** 里，按
`(userId, sessionId, pluginId, dataKey)` 四维定位一行，`dataValue` 存 JSON；
`sessionId="all"` 表示跨会话共享。故事动态数据和系统配置数据**不进**这张表，走宿主自己的存储。

## 数据分三类（req.md 的顶层划分）

| 类型 | 存哪 | 内容 | 读写方 |
|---|---|---|---|
| 故事的动态数据 | 宿主故事库（动态角色卡 / 故事动态） | 角色卡、故事状态等 AI 故事侧数据 | 宿主 / toonflowJsApi 故事接口 |
| 系统的配置数据 | 宿主配置表（`t_config` 一类） | 模型接口配置等全局配置 | 宿主设置 |
| **插件数据** | **`t_plugin_session_data`** | 不太适合放进故事动态数据、又需要跨会话长期保留的运行时数据 | 插件 entry（后端）+ toonflowJsApi（前端）+ CLI |

插件数据 = "哪个插件、哪个故事会话、哪个用户"的独立存档，典型如生成的地图数据。

## 表结构

```
t_plugin_session_data
(id, userId, sessionId, pluginName, pluginId, dataKey, dataValue)
```

- `pluginId`：运行时按 **manifest.id**（如 `com.toonflow.minigame-field-survival`），不是文件夹名。
  CLI 的 `_resolve_plugin_id()` 会把 `-i toonflow-field-survival` 解析成 manifest.id，
  否则「写库用文件夹名、运行时读用 manifest.id」永远对不上。
- `sessionId`：宿主注入「当前故事会话」；`"all"` 为特殊值，后端跳过 `t_gameSession` 校验，跨会话共享。
- `dataValue`：JSON（对象 / 字符串 / 数字均可），get 返回 `{value, updatedAt}`。

## 访问链路（三条，落到同一张表）

```
后端 entry.js（node）          前端 iframe（浏览器）              CLI（python）
ctx.tsApi.pluginData            toonflowJsApi.pluginData          python -m toon_plugins plugin_session_data
  .get/.set/.remove               postMessage → 宿主转发              → POST /plugin/data
  .getTemplate("k")                （dev-host 由 vite mock 应答）        op = get/set/list/remove
        └──────────────┬────────────────────┴───────────────┘
                       ▼
              POST /plugin/data { sessionId, pluginId, op, dataKey?, value? }
                       ▼
              t_plugin_session_data（sqlite）
```

- **后端**：`entry.ts` 里 `context.tsApi.pluginData`（get/set/remove/getTemplate），
  `ensureMapData` / `ensureStoryVisualMap` / `persistSys` / `restoreSys` / 事件 flag 都走它。
- **前端**：`vue/src` 通过 `toonflowJsApi.pluginData`（eventEngine、storyMap、App.vue 手动上传地图）。
- **CLI**：`plugin_session_data` 子命令，`-u` 上传 .tbg 地图、`--list` 列 key、`-role` 看 AI 角色位置。

## dataKey 清单（field-survival 现状）

| dataKey | 内容 | 写入方 | 会话 scope |
|---|---|---|---|
| `map_visual:<story>` | 视觉地图模板（.tbg zip，base64）**v6 主 key** | CLI `-u` | `all`（跨会话共享） |
| `map_data:<story>` | 同上，旧 key，兼容 2026-10-13 前上传的模板 | CLI `-u` 同步写 | `all` |
| `map_visual` | **本会话**视觉地图（开局时从模板注入；用户手动上传优先，绝不覆盖） | entry `ensureStoryVisualMap` / App.vue | 当前会话 |
| `map_data` | 旧版 LLM 生成的地图数据（enemy_archetypes 等）；App.vue 手动上传也写这 | entry `ensureMapData` / App.vue | 当前会话 |
| `sys_state` | 系统存档（见下） | entry `persistSys`（每 20 tick ≈ 2s + 关键动作后即存） | 当前会话 |
| `ai_story_roles` | AI 故事角色位置/地图（game.md 对话窗口读） | entry `persistSys` 内联写 | 当前会话 |
| `quest_defs` | 任务定义表（`{version, quests[]}`），AI 新增任务按 id 合并回写 | CLI 上传 / entry 回写 | `all` |
| `player_flags` | 事件系统 flag（任务完成、剧情节拍判定） | entry `writePlayerFlag` / 前端 eventEngine | 当前会话 |

### `sys_state` 内部结构（一个 key 装整个玩家存档）

```
ring{items,skills} / party / npcCards / bagMeta / bagOrder / skillOrder /
shop / level / skillMeta / itemMeta /
card{items,money,level,exp,hp,mp,skills}   ← 2026-10-19 修复刷新丢物品/钱
questBoard / quests / parked / spriteGallery / spriteBinds
```

- `restoreSys` 反向灌回 `s.*`，且必须在 `buildItems/buildSkills` **之前**（物品/技能数量才对）。
- `spriteGallery` 是 base64 图，体积大 → `pluginData.set` 整体上传有上限考量，形象图库别无限涨。
- `parked` = ally/spectator 角色驻留在别的地图的位置，也靠它持久化。

## 已知坑（改存储相关代码前必读）

1. **dev-host mock**：`--conn` 模式下真实宿主不在，`vite.config.ts` 用 `window.__devHostPluginData`（Map）模拟整张表。
   两个归一化必须做：`pluginId` 缺省补 `ENTRY_PLUGIN_ID`、`sessionId` 缺省取故事会话（不是 `all`），
   否则前端写 / 后端读写不到同一个 key。
2. **命名空间**：CLI 传文件夹名能解析、运行时按 manifest.id 读——写读两侧 pluginId 必须一致。
3. **故事隔离**：地图模板 key 必须带 `:<story>` 后缀。`sessionId="all"` 下不带后缀会故事 A 覆盖故事 B。
4. **地图不进 plugin_state**：`plugin_state` 每帧全量写回，地图只在开局/维护时单独写。
5. **模板注入前提**（缺一个静默退化成「只有当前关」）：`ctx.worldName` 非空、后端有 `getTemplate`、模板里确有 `map_visual:<story>`。
6. **CLI 读兼容两种回包**：`{value,...}`（toonflow 后端）和 `{data:{value}}`（旧版/直返）。
7. **value 必须 JSON 可序列化**；base64 大图（形象图库）注意体积，落库失败不阻断玩法（persistSys 整体 try/catch）。
