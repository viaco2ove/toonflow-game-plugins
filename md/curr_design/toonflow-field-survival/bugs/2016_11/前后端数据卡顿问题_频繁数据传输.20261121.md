# ai托管后前后端数据发送过于频繁
改动内容（只改插件前端，vue/src/ai/spine.ts，+111/-19）
在命令出口加了命令级去重层——持续动作的语义本来是「设一次目标、服务端持续执行」，前端每拍重发纯属浪费：

动作	去重规则	原行为
move/interact→move	同坐标 5s 内只发一次	每 100ms 重发
attack	同目标 5s 内只发一次（服务端攻击结算走 3s CD，重发不加速）	每 100ms 重发
gather	同区域只发一次；reqId 只在真发时生成（原来每拍换新 reqId，去重形同虚设）	每 100ms 重发
follow	到位后不重发 stopMove；未到位时玩家偏移 >1.5m 或 5s 心跳才重发	每 100ms 重发
flee	目标按 1m 粒度 + 5s 窗口	每 100ms 重发
窗口外放行 = 心跳兜底（防服务端状态丢失后前端永远不发）；瞬发动作（useSkill/useItem/短信/台词）不经去重路径，行为不变。interact 去重还顺带修了一个隐患——原来每拍重发会重置 entry 侧 _aiInteract.startedTick，到点结算会被无限推迟。

# 过度依赖后端的弊端
跟野怪战斗我的感觉也是一卡一卡的，你这个修改会改善这个问题吗？
就算不勾选ai 托管。技能释放也是有各种奇怪问题。这个过度依赖后端导致的各种一卡一卡的现象甚至点击技能释放后技能不释放，释放了也是一卡一卡的，甚至特效不出来，出来后也不清除。
cd 技能冷却都不出来，出来了也不准。打野怪不扣血。扣血了也可能死不掉。
等等等。
## 原因
**主矛盾不在游戏引擎，在引擎外面的包装层**（2026-11-21 定量实测）：

| 测量项 | 数值 | 说明 |
|---|---|---|
| entry 引擎纯结算（本地基准，40怪4队友） | **0.06~0.3ms/拍** | 游戏引擎几乎免费（`.cache/tick-bench.mjs`） |
| 部署机 `/plugin/tick` 单拍 | **150~280ms**（极值 1136ms） | 是引擎的 **1000 倍** |
| 部署机 getSession（读一次） | 367ms，**stateJson 351KB** | 行里大头是故事运行时状态（插件状态早已外置） |
| 401 无 DB 基线 | 39~129ms | 网络+框架开销对照 |

每个 tick（名义 10Hz）的构成：`SELECT` 351KB stateJson → JSON.parse → 上下文组装
（worldName 两次查询 + manifest 磁盘读 + worldBook 80 行查询 + roles 构建）→
**entry 结算（0.1ms）** → JSON.stringify 351KB → `UPDATE` 写回 351KB → push。
而普通 tick 对这一行**逐字节无改动**（插件真实状态早已外置 `t_plugin_session_data`：
内存权威 + 2s 节流 + 304 回传去重）——每拍读写是纯浪费。

**机理链（用户的每一条体感都能对上）**：
- 单拍 150~280ms > 100ms 预算 → driver `driverBusy` 跳拍 → **世界实际 3~8Hz 强抖动** → 前端插值间隔 100/300ms 地跳 → 「跟野怪战斗一卡一卡」
- 玩家技能与 tick **共用同一把会话锁** → 技能 action 排在 tick 后面等 100~300ms → 「点击技能后不释放」
- 本地 CD 递减 10Hz vs 服务端实际 3~8Hz，push 每拍用服务端值覆盖本地 cdLeft → 「CD 出来了也不准」；本地 CD 先递减完而服务端还没结清 → 点击被服务端「冷却中」拒绝且无提示 → 「点了不放」「特效不出来/一闪而过」（乐观特效交接失败）
- 伤害全在服务端结算，推送滞后 300ms → 「打野怪不扣血」观感，然后血量突然跳；怪死亡+2s 复活冷却 → 「死不掉」
- AI 托管每拍重发 ai_command（上一节已修）是在这条已经被 tick 占满的锁上再踩——所以不勾托管也卡

## 解决
**影子缓存 + 脏写门闸**（app 仓 4 文件，+191/-25，2026-11-21 已实施并实测通过）：

| 文件 | 改动 |
|---|---|
| `src/lib/plugins/PluginTickCore.ts` | 故事行影子缓存：每拍只查 `updateTime/worldId` 小列（不读 351KB blob），与影子一致 → 复用已解析对象（跳过 SELECT+parse）；失配（外部写入方）→ 全量重读对齐。脏写门闸：仅 writeback 消费 / over 结算 / 指针自愈 / 玩家卡清洗 / phase·status 变化 / 非 tick 命令才落库，普通拍直接跳过。map-diag 日志降频 60s |
| `src/lib/plugins/PluginExecutionContext.ts` | `cachedRow` 快路径（跳全行 SELECT+parse+worldName 两次查询）+ bundle 回传 rowUpdateTime/rowWorldId/playerCardCleaned + worldBookDigest 60s TTL 缓存（原来每拍查 80 行世界书） |
| `src/lib/plugins/PluginStateExecutor.ts` | 结果暴露 `hostStateMutated`（writeback/结算动了宿主行 → 调用方必须落库） |
| `src/modules/game-runtime/services/SessionMemoryWorker.ts` | 补 updateTime（原本漏带——漏写会导致记忆 worker 的改动被脏写门闸覆盖） |

**一致性保证**：全部读写都在既有会话锁内；自写后把 updateTime 记回影子（下拍命中快路径）；所有外部写入方（故事轮次/记忆 worker/MCP tool）都带 updateTime → 探测必然失配 → 全量重读，不会用脏缓存覆盖别人。今天每拍写的本来就是相同字节，跳过写对外部读取方（getSession 等）零差异。

**验证**：
- 类型检查：改动 4 文件零错误（仓库存量报错与本次无关）
- 隔离沙箱（拷贝 DB + PREFER_PROCESS_ENV=1 覆盖端口/DB_PATH）：冷拍 57ms → 影子快拍 p50=20ms / min=9ms，12 拍后 updateTime 纹丝不动（零落库）
- 5175 浏览器实测（重启本地后端加载新代码后，bsk 走完 主页→我的→赦夜→野外生存 playing）：世界推进 ~56 拍期间 updateTime 全程冻结；世界速率 ~9-10Hz；API 直发 skill 回执「暗核共鸣（空放）」code=0、cdLeft 24→20 递减、结算 22ms；skill action（非 tick）后 updateTime 正常更新（必要写没被门闸吞）

**生效条件**：
- 本地：✅ 已重启生效（原进程 tsx 直启无 watch，必须手动重启）
- 部署机：⏳ 待把 app 仓改动部署过去并重启后端——用户体感的「一卡一卡」主战场在部署机（150~280ms 那个环境），部署后收益最大
- 插件前端 AI 托管去重（上一节）：⏳ 待重传插件 + rebuild

## 部署后：171ms
ai 测试部署后171ms 耗时。要求更新部署进行测试
**perf(plugins): 优化插件 manifest 缓存及移除无用序列化代码（无效果）**

- 引入 manifest TTL 缓存，减少频繁读取 manifest 文件，提升性能
- 实现缓存淘汰策略，限制缓存大小为 32 条目
- 描述缓存刷新机制及其对插件安装和更新的影响
- 删除无用的全量 JSON 序列化代码，避免每帧多余 CPU 开销
- 通过减少不必要的数据处理，提高插件状态执行效率
结论：manifest 缓存的假设没兑现，依然171ms

**probe 探测节流优化（无效果）**

- 新增影子新鲜期常量 SHADOW_PROBE_FRESH_MS(500ms)，降低数据库 probe 频率
- 利用影子缓存 lastProbeAt 时间判断探测列是否刷新，减少不必要查询
- 仅在影子新鲜期外进行 SQLite 查询，显著减少每拍查询开销
- 保持外部写入数据最大延迟在一个新鲜期内，避免旧行为带来的性能问题
- 调整缓存影子数据的更新时间以反映最新探测时间，维护缓存一致性
结论： 几乎没动，且分布均匀——要么节流没生效，要么每拍有一块 ~150ms 的固定开销与查询无关。


**优化插件加载与探测节流减少同步调用**

- loadEntryModule 中增加 mtime 检查节流，避免频繁同步 stat 调用
- entryModuleCache 新增 checkedAt 字段记录最后校验时间，提升热重载性能
- PluginTickCore 插件钩子加入临时分段计时日志，辅助诊断性能瓶颈
- 减少影子探测数据库查询频率，实现 SHADOW_PROBE_FRESH_MS 缓存机制
- 删除插件 manifest 无用序列化代码，优化插件状态执行效率
- 部署机实际测试发现 manifest 缓存无明显性能提升，继续优化探测节流机制
