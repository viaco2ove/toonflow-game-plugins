# 插件的拟真安装一致性问题

> 2026-10-07 修复「野怪不攻击」（fix⑦，见[为何插件安装后野怪不攻击](为何插件安装后野怪不攻击.md)）过程中暴露的系统性问题。
> **这不是一个 bug，是四类"同一份代码、四条运行链路、互不同步"的结构性一致性缺陷。**

## 问题总述

`npm run debug -- --story xxx --conn`（拟真测试）跑通的代码，**安装后不一定生效**——因为"开发态的 entry"和"安装后的 entry"是**两份物理文件、两条加载链路、两层缓存**，没有任何机制保证它们一致。AI 在反复排障中自然会把两套链路的差异误判为"entry.ts 和 entry.js 分工不清晰"——其实分工是清晰的（ts=源码，js=编译产物），不清晰的是**同步责任**。

## 全景：一份插件代码，四条运行链路

```

        ┌──────────────────────────────┼──────────────────────────────┐
        ▼                              ▼                              ▼
```

## 四类不一致（按危害排序）

### 1. 源码 → 编译产物不同步（本次野怪 bug 的直接背景）

- **运行时只加载 entry.js，人改的是 entry.ts**。不跑 `npx esbuild entry.ts --outfile=entry.js`，改了等于没改。
- 仓库里还有 `entry.js.bak_20261005`、`entry.js.bak_before_tsc_20261006_1830`、`entry.js.new` 三个手工备份——历史上已经至少两次因为直接编辑 entry.js / 忘了重编译埋过坑。
- **ui/game.html 同理**：`vue/src` 改完必须 `vite build`（CLI 安装时 install_cmd 会现场 build，见 cli.py:338-388，但日常调试链路不会）。

### 2. 仓库 → 安装副本不同步（本次排查的核心）

- 60002 后端 `getPluginDir(userId, pluginId)` 永远读**安装副本**（`toonflow-app-run-db/plugins/<userId>/...`），从不读仓库。
- 改完仓库后必须：**重编译 → 手动拷贝 entry.js/entry.ts（最好连 ui/game.html、manifest.json 一起）到安装副本 → 重启 60002**。三步缺一不可，且没有任何工具一键完成。
- 多账号（user 1/7/8）各有独立副本，升一次级要拷 N 份。
- **网页安装 / CLI 安装走的都是 zip 全量覆盖**（`POST /plugin/install-raw` → 解压覆盖同目录），所以**重新安装一次 = 同步**。但没有"检测仓库有更新就提示重装"的机制，装没装新版全靠人记。

### 3. 进程级模块缓存（用户问的 entryModuleCache）

两处独立缓存，都是"改了文件不重启就白改"：

| 缓存 | 位置 | 失效条件 |
|---|---|---|
| `entryModuleCache`（PluginExecutor.ts:59） | 60002 后端进程内，`Map<pluginDir, module>` | **重启 60002 进程** |
| `entryMod`（vite.config.ts:544-551） | dev-host 的 vite 进程内 | **重启 vite** |

它们的存在是合理的（每 tick 动态 import 太贵），**问题是没有失效入口**：没有 `clearEntryCache` API、没有按文件 mtime 失效、没有日志提示"插件文件已更新但仍在用缓存"。排障时会看到"我明明改了代码为什么没生效"——本轮 3000 dev-host 排障时反复撞到。

### 4. 拟真测试链路 ≠ 安装链路（"拟真"名不副实）

| | dev-host（`npm run debug --conn`） | 安装后 |
|---|---|---|
| entry 加载 | 仓库 `entry.js`（ENTRY_PATH 直引） | 安装副本 `entry.js` |
| ui | vite dev server 实时编译 `vue/src` | 安装时的 `ui/game.html` 静态快照 |
| 宿主 | vite.config.ts 内嵌桩（3000） | Toonflow-game-web ScenePlay.vue（5175） |
| tick 链 | postMessage → 桩 → entry.js（同进程） | postMessage → 宿主 → HTTP `/plugin/tick` → 后端 → entry.js（跨 3 进程） |
| state 持久化 | 内存 | sqlite `t_plugin_session_data`（每 tick 落库） |
| agent/世界书/参数卡 | 桩内 mock / 部分代理 | 完整走 db + 编排 |

- dev-host 的 `queueEntryAction` 与后端 `executePluginAction` 是**两份对 entry.js 的调用封装**，语义对齐靠人工维护（vite.config.ts 注释多次出现"与「安装后」路径一致""同口径"字样——即靠注释自觉）。
- 本轮实证：dev-host 下 mockHost 的独立逻辑（波次刷怪、安全区推出）让"野怪不动"在 dev-host 和安装后**表现完全不同**，在 dev-host 上测通过不代表安装后通过，反之亦然。

## 解决方向（建议，未实施）

按性价比排序：

1. **一键同步脚本**（最小改动，立刻消除 70% 痛点）：
   `sync-plugin.ps1` = `esbuild entry.ts --outfile=entry.js` + `vite build`（如 vue/src 有变）+ 拷贝 entry.js/entry.ts/ui/manifest 到 `toonflow-app-run-db/plugins/*/` 所有账号 + 提示需重启 60002。放进 `package.json scripts.sync`。
2. **dev-host 直连安装副本**（根治"测的不是装的"）：vite.config.ts 的 ENTRY_PATH 从 `../entry.js` 改为优先读 `toonflow-app-run-db/plugins/1/.../entry.js`（存在才回退仓库），dev-host 从此与安装链路同源。代价：每次调试前要先装一次。
3. **缓存失效入口**：PluginExecutor 暴露 `POST /admin/plugin/reload`（按 pluginDir 清 entryModuleCache）；vite 桩对 entry.js 做 mtime 检查自动重载。加一行日志"entry.js mtime 变化，已重载"。
4. **拟真度对齐**：dev-host 的 mockHost 波次刷怪/安全区逻辑标 `@mock-only` 并默认关闭，行为尽量回落到 entry.js（桩只做网络代理，不做游戏逻辑——vite.config.ts:88 注释本来就是这个意图，但 mockHost.ts 里还有大量兜底游戏逻辑）。
5. **多账号副本收敛**：安装副本按 pluginId 全局共享一份（`plugins/_shared/<pluginId>`），userId 只留启用状态/数据。多账号各持一份代码副本是纯负担。

## entryModuleCache 缓存
这又是啥玩意？
### 安装 + 同时在 plugins_tbg/ 保存 .tpg
python -m toon_plugins plugins --install-all

### 指定单个插件
python -m toon_plugins plugins -i toonflow-field-survival

和网页上安装插件会有缓存？啥玩意？

1. "entry.ts 和 entry.js 分工不清晰”？——分工其实清晰：ts 是源码，js 是编译产物，运行时只加载 js。不清晰的是同步责任：改了 ts 必须手动 esbuild 重编译 + 手动拷到安装副本 + 重启后端，三步全靠人记，漏一步就是“改了没生效”。AI 反复说“分工不清晰”是因为它在两条链路上看到的行为不一致，误判成了代码分工问题。
2. “entryModuleCache 是啥玩意？”——60002 后端进程内的 Map<pluginDir, 模块>（PluginExecutor.ts:59），第一次加载 entry.js 后缓存，之后每次 tick 直接用缓存。失效条件只有一个：重启 60002 进程。没有清缓存 API、没有 mtime 检测。所以覆盖了安装副本的 entry.js，不重启就拿不到新代码。vite dev-host 里还有个一模一样的 entryMod 缓存。
3. “CLI 安装和网页安装会有缓存？"——安装本身没有缓存问题（都是 zip 全量覆盖同一目录），缓存在安装之后：覆盖完文件，后端 entryModuleCache 还拿着旧模块。这就是“装了新版还跑旧逻辑"的原因。

实测一致性现状（文档里有表）：同一台机器 4 个位置 3 个版本——仓库（117KB 新）、user 1 安装副本（本次手动同步后一致）、user 7/8 副本（176KB 旧版）、toonflow-game-app/Toonflow-game/ 残留（124KB 更旧的另一份）。
