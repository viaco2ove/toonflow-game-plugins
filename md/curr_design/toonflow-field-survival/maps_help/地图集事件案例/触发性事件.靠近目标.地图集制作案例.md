# 触发性事件 · 靠近目标 · 地图集制作案例

> **一句话**：玩家走近某个对象 → HUD 自动弹出**这个设施专属的按钮**（🔨锻造 / 🔥炼丹 / ⚔对打 / 你自定义的）
> → 点击 → 跑你写的脚本 → 弹出面板或选择框。
>
> 本文不只是「怎么做」，而是完整回答四件事：
> **① 插件提供了什么函数和接口** → §1；**② 地图集怎么用它们** → §2；
> **③ 有没有遵守 [规范.md](../规范.md)、怎么更遵守** → §4；**④ 插件还需不需要补接口** → §5。
>
> 参照地图集：`workshops/toonflow-field-survival/map_design/通天传授-收徒系统/`
> 接口细节：[../API文档.md](../API文档.md)；硬约束：[../规范.md](../规范.md) §4。
> 本文所有「实现状态」以 **2026-10-28 的代码**为准（核对过 `_ctx.ts` / `eventEngine.ts` / `App.vue` / `validate_events.mjs`）。

## 0. 效果分镜（先看清要做什么）

| 步 | 玩家看到 | 谁决定 | 对应接口 |
|----|----------|--------|----------|
| 1 | 走到某对象 2.8 米内 | 地图里那个对象的坐标 + 事件里的 `radius` | 地图 Actors 层 + `trigger.radius` |
| 2 | 屏幕下方出现按钮「🔨 锻造」 | 事件**顶层**的 `proximity{label, icon, hint}` | `EventDef.proximity` |
| 3 | 点击按钮 | 引擎把这次点击当成「与这个 uid 交互」→ 匹配同 uid 的事件 | `onInteract(tiledId)` |
| 4 | 弹出多标签面板 / 选择框 / 确认框 | 你的 TS 脚本里调 `ctx.ui.*` | `ctx.ui.openShopPanel` / `select` / `confirm` |
| 5 | 关掉面板，还能再点开 | 事件写了 `repeat: true` | `EventDef.repeat` |

**要做三件事**：地图里放对象 → 事件 JSON 声明 proximity → TS 脚本写点击后干什么。

```
① maps/<map>.json                  Actors 层放一个对象，记住它的 id（= uid）
② events/maps/<map>.events.json    trigger.type="proximity" + 顶层 proximity{...}
③ events/scripts/<前缀>_xxx.ts      default export main(ctx) 里调 ctx.ui.*
```

## 1. 插件提供了什么：三层接口模型

插件对地图集的开放面不是「一堆函数」，而是**三层各管一段**的结构。搞清分层，就知道某个需求该落在哪一层——这也是 [规范.md](../规范.md) 说「地图集自己的业务写在地图集里」的技术依据。

```
┌─ 第 3 层  故事包数据层   <故事>/data/*.json
│           货单/文案表/配置，随故事包走
│           读法：ctx.story.readJson("data/x.json")
│           ▲ 地图集自己的业务数据只能放这层
├─ 第 2 层  脚本层        <故事>/events/scripts/*.ts
│           default export async main(ctx) → ctx.*
│           复杂逻辑（分支/随机/循环/多步 UI）
│           ▲ 插件提供 ctx 对象，地图集提供实现
└─ 第 1 层  声明层        <故事>/events/maps/<map>.events.json
            trigger + conditions + actions
            ▲ 引擎提供 schema 白名单，地图集填内容
```

| 层 | 插件提供 | 地图集提供 | 能做什么 / 不能做什么 |
|----|----------|-----------|---------------------|
| 声明层 | 10 种 trigger（实现 5）、4 种 condition（实现 1）、12 种 action 的**白名单与执行器** | 具体 JSON 内容 | 能做「到什么位置、满足什么 flag、播什么提示、传送到哪」；**不能**做分支/随机/循环 |
| 脚本层 | `ctx` 对象（约 30 个方法，见 §1.4） | `main(ctx)` 实现 | 能做任意 TS 逻辑；**不能**直写 pluginData、不能 `while(true)` |
| 数据层 | `ctx.story.readJson` 读通道（dev 走 `/story-data`，安装态走 `.tbg`） | `data/*.json` 文件 | 能放任意业务数据；**不能**被 `import` 进脚本（会被编进 `ui/game.html`） |

### 1.1 第一层：trigger（10 种声明，引擎实现 5 种）

| type | 参数 | 实现 | 触发时机 | 靠近目标用它？ |
|------|------|------|----------|---------------|
| `proximity` | `uid` + `radius?` | ✅ | 玩家进入半径 → 弹**专属按钮** → 点击 | ★ **本案例主角** |
| `interact` | `uid` | ✅ | 走近弹「💬 聊天」→ 点击 | 需要「又能聊天又能开面板」时 |
| `enter_map` | 无 | ✅ | 切图后顺序 fire | 进图旁白 |
| `area_enter` | `zone` + `ai?{gather}` | ✅ | 玩家**新进入**区域那一拍 | 采集、区域剧情 |
| `interval` | `everyMs` + `when?` | ✅ | 定时器到期（`everyMs≥2000`，单图≤3 个） | AI 心跳，不是「靠近」 |
| `step_on` / `flag_set` / `kill_count` / `turn_count` / `custom` | — | ❌ | **写了是死事件**（不报错、不触发） | 不要用 |

**`interact` 与 `proximity` 的取舍**（这是本案例第一个决策点）：

| | `interact` | `proximity` |
|---|---|---|
| 玩家侧入口 | 通用「💬 聊天」按钮 | 事件自定义按钮（🔨锻造 / 🔥炼丹 / ⚔对打） |
| 挂了 proximity 的实体 | — | **不再显示「💬 聊天」**（`eventUidsHas` 把这类 uid 排除） |
| 适合 | 剧情对话、拾取、门 | 功能设施、可反复使用的交互点 |
| 代价 | 按钮文案不能定制 | 一个 uid 只有一种入口，**不能既聊天又开面板** |

> 想「既能聊天又能开面板」：只挂 `interact`，脚本里用 `ctx.ui.select` 让玩家选「闲聊 / 用设施」。
> 这是引擎的硬约束（[规范.md](../规范.md) §4 #14），不是配置问题。

### 1.2 第二层：conditions（4 种声明，只有 1 种生效）

| type | 参数 | 实现 |
|------|------|------|
| `flag_check` | `key` + `value?` + `op?`（`eq`/`ne`/`exists`/`missing`） | ✅ 唯一可用 |
| `phase_done` / `level_gte` / `random` | — | ❌ 不判定（**恒真通过**，别依赖） |

`op` 缺省规则：`value !== undefined ? "eq" : "exists"`。所以：

```json
{ "type": "flag_check", "key": "phase_1_done", "op": "missing" }   // flag 不存在才通过
{ "type": "flag_check", "key": "met_luwenzhao", "value": true }     // 必须 === true
```

⚠️ 要随机、要等级判断、要多条件组合逻辑 → **只能写进 TS 脚本**，condition 层没有。

### 1.3 第三层：actions（12 种）

| type | 参数 | 实现 | 备注 |
|------|------|------|------|
| `set_flag` / `del_flag` | `key`, `value` | ✅ | flag 落玩家卡 |
| `toast` | `text`, `color?` | ✅ | 右下角飘字 |
| `subtitle` | `text`, `duration?` | ✅ | 顶部字幕 |
| `event_log` | `text` | ✅ | HUD 事件流 |
| `teleport` | `map`（**关卡英文名**）, `x`, `y`（世界米） | ✅ | 写中文名 → 静默失败 |
| `run_script` | `script`（不含 .ts） | ⚠️ 执行已实现，**`args` 不透传** | 见 §5.2 缺口 G2 |
| `wait` | `ms` | ✅ | 顺序阻塞 |
| `ai_trigger` | `priority?`, `reason?`, `target?` | ✅ | 唤醒 AI 托管大脑 |
| `ai_interval` | `engaged?`/`skirmish?`/`idle?`/`all?` | ✅ | 覆盖本图 AI 间隔 |
| `call_action` | `name`, `args?` | ❌ | `registerAction` 也是 no-op |
| `llm_speak` | `npcId`, `npcName`, `userText` | ⚠️ 占位，返回空串 | NPC 对话用 toast/subtitle |

> **本案例只需要 `run_script`**。其余动作在「靠近目标」这个场景里用不上——这是设计得好的地方：
> 按钮点开后干什么，全部交给脚本，声明层保持极薄。

### 1.4 第三层：TS 脚本 ctx API（全量，权威来源 `_ctx.ts`）

`ctx` 是引擎构造、传给脚本的唯一入口。下表是**完整清单**（不是节选），带真实签名与坑：

**身份与上下文**

| API | 签名 | 坑 |
|-----|------|-----|
| `ctx.player` | `Entity`（只读快照） | 改数值无效，要走 `save` / `ctx.cmd`；取不到时有兜底假对象（`hp=1,maxHp=1,x=0,y=0`） |
| `ctx.mapName` | `string` | 当前地图文件名，不含 `.json` |
| `ctx.actor` | `{roleId, ai, name}` | ★ 执行者。`roleId=""` = 玩家；非空 = AI 托管。见 §1.7 |
| `ctx.event` | `{id, uid?, args}` | ★ **当前触发事件上下文**。`id`=事件 id；`uid`=触发实体 id（仅 interact/proximity）；`args`=run_script 透传参数（非对象归空 `{}`）。见 §5.3 |
| `ctx.playerCard` | `{level, money, hp, maxHp}` | ★ 玩家卡**只读快照**。改数值无效，要走 `save`/`ctx.cmd`；取不到时 `{level:1,money:0,hp:0,maxHp:0}` |

**flag 存档**（唯一来源 `t_plugin_session_data.player_flags`）

| API | 签名 |
|-----|------|
| `ctx.save.getFlag<T>(key)` | `Promise<T \| null>` |
| `ctx.save.setFlag(key, value)` | `Promise<void>` |
| `ctx.save.delFlag(key)` | `Promise<void>` |
| `ctx.save.all()` | `Promise<Record<string, unknown>>` |

**实体**

| API | 签名 | 坑 |
|-----|------|-----|
| `ctx.npc.byUid(uid)` | `Entity \| null` | 返回**快照**；改它不影响游戏 |
| `ctx.npc.setField(uid, patch)` | `boolean` | ★ 唯一能改实体的方法（走 `entityRef` 可变引用）；返回是否成功 |
| `ctx.npc.setLabel` / `move` / `faceTo` | — | ❌ **空实现**，调用不报错但什么都不发生 |

**UI**

| API | 签名 | AI 执行时 |
|-----|------|----------|
| `ctx.ui.toast(text, color?)` | `void` | 照常飘字 |
| `ctx.ui.subtitle(text, ms?)` | `void` | 照常 |
| `ctx.ui.event(text)` | `void` | 照常记日志 |
| `ctx.ui.confirm({title, detail?, confirmText?, cancelText?})` | `Promise<boolean>` | **自动 true** |
| `ctx.ui.select({title, detail?, options:[{label,value,desc?}]})` | `Promise<string \| null>` | **自动选第一个** |
| `ctx.ui.prompt({title, detail?, placeholder?, defaultValue?})` | `Promise<string \| null>` | **自动返回 defaultValue/空串** |
| `ctx.ui.openShopPanel({mode, tab?, goods?})` | `void` | **自动忽略** |
| `ctx.ui.notice({title, detail?, confirmText?})` | `Promise<void>` | ★ **结果模态弹窗**（必须点确认）。**自动跳过**（立即 resolve） |

**数据 / AI / 背包 / 关卡 / 其它**

| API | 签名 | 坑 |
|-----|------|-----|
| `ctx.story.readJson<T>(path)` | `Promise<T \| null>` | 路径相对故事根；**不存在返回 `null`**，脚本必须兜底 |
| `ctx.ai.generate(agent, prompt, opts?)` | `Promise<string>` | 失败返回空串 |
| `ctx.bag.give(name, count?)` | `void` | AI 时进该角色 `_aiBag` |
| `ctx.bag.list()` | `Promise<Item[]>` | AI 时读它自己的私藏 |
| `ctx.bag.remove(name, count?)` | `Promise<boolean>` | AI 时跳过返回 false |
| `ctx.level.switchTo(mapFile, x, y)` | `void` | 吃关卡英文名；会夹边界/避墙 |
| `ctx.level.setLocked(mapFile, locked)` | `void` | 写 flag `map_locked_<mapFile>` |
| `ctx.cmd(action, params?)` | `Promise<string>` | ★ **不等后端回执**（立即 resolve 空串） |
| `ctx.audio.play(name)` | `void` | ❌ no-op |
| `ctx.llm.speak(...)` | `Promise<string>` | ⚠️ 占位返回空串 |
| `ctx.registerAction(name, fn)` | `void` | ❌ no-op |

### 1.5 故事包数据通道（地图集业务数据的唯一入口）

```ts
const raw = await ctx.story.readJson<{ goods?: ShopGood[] } | ShopGood[]>("data/shop.forge.json");
```

| 项 | 说明 |
|----|------|
| 路径 | **相对故事根目录**：`"data/shop.forge.json"`、`"maps/mulberryTown.json"` |
| dev 通道 | `fetch /story-data/toonflow-field-survival/map_design/<story>/<path>` |
| 安装态通道 | 读 `map_visual` 的 `.tbg` 包内同名条目 |
| 缓存 | **按 path 缓存一局**——改了 `data/*.json` 要刷页面；安装态还要重建 `.tbg` |
| 失败 | 返回 `null`（不抛错），脚本自己决定降级 |

**为什么必须走这条通道**：脚本会被构建期内联进 `ui/game.html`，一旦 `import` 数据文件，数据就被复制进插件产物 → 改货单要重编插件，且污染其他故事。这正是 [规范.md](../规范.md) 头号「严重违规事项」。

### 1.6 后端命令 `sys_*`（`ctx.cmd` 的目标）

| 命令 | 作用 |
|------|------|
| `sys_item_add` / `sys_bag_remove` | 发/扣物品（`bag.give` 底层） |
| `sys_shop_buy` | 购买（`good` 必须带地图集货单那件商品） |
| `sys_forge_create` / `sys_alchemy_create` | 打造 / 炼丹（`blueprint` 由后端扣） |
| `sys_item_upgrade` / `sys_item_dissolve` | 升级 / 溶解 |
| `sys_dummy_reward` | 假人击碎奖励 |
| `sys_quest_board` / `_accept` / `_turnin` / `_arrive` / `_ask` / `_generate` | 任务板 |
| `sys_rest` / `sys_teleport` / `sys_party` / `sys_use_item` | 杂项 |

⚠️ `ctx.cmd` **不等回执**。要拿后端结果（钱不够、物品不在背包）必须在**前端**实现
（参照 `vue/src/forgeOps.ts` 的 `sendSysCmdAwait`）。所以「点按钮买东西」这类必须有明确回执的操作，
不要指望脚本里 `await ctx.cmd(...)` 拿到结果——那是空串。

### 1.7 AI 托管分流（同一份脚本，两种执行者）

玩家触发与 AI 托管角色触发走**同一条链**（`fireEvent` → `runActions` → `runScript`），差别只在 `ctx.actor`：

| | 玩家（`roleId=""`） | AI 托管（`roleId` 非空） |
|----|---------------------|--------------------------|
| `ctx.actor.ai` | false | true |
| `confirm` / `select` / `prompt` | 真弹窗等玩家 | 自动通过 / 选第一个 / 返回默认值 |
| `openShopPanel` | 真开面板 | 自动忽略 |
| `ai.generate` | 真调模型 | 返回空串 |
| `bag.give` | 进玩家背包 | 进该角色 `_aiBag` |
| `bag.remove` | 真扣 | 跳过 |
| `cmd` | 真发命令 | 只记日志 |
| 叙事人称 | 「你」 | 用 `ctx.actor.name` |

```ts
const who = ctx.actor.ai ? ctx.actor.name : "你";
```

> **靠近目标这个场景为什么必须知道这条**：设施按钮只由玩家点（AI 不会点按钮），
> 所以 `openShopPanel` 天然只在玩家侧执行。但如果你在同一个脚本里顺手写了采集逻辑，
> 就必须处理 AI 分支，否则 AI 会把面板「打开失败」记成日志、或在 `confirm` 上永远悬着。

### 1.8 校验器白名单：能调什么，机器说了算

`.cache/validate_events.mjs` 的 `CTX_API` 集合是**运行时可调 API 的机器可读白名单**，
脚本里出现白名单外的 `ctx.*` 直接 `error`：

```
save.getFlag/setFlag/delFlag/all
npc.byUid/setLabel/move/faceTo/setField
ui.toast/subtitle/event/confirm/select/prompt/openShopPanel/notice
ai.generate
bag.give/list/remove
story.readJson
level.switchTo/setLocked
audio.play   llm.speak   registerAction
actor.roleId/ai/name
event.id/event.uid/event.args
playerCard.level/playerCard.money/playerCard.hp/playerCard.maxHp
```

> ⚠️ 白名单里包含 `npc.setLabel/move/faceTo`、`audio.play`、`llm.speak`、`registerAction`
> 这些**空实现/占位**。校验器只查「名字在不在表里」，不查「有没有真效果」——
> 所以「校验通过」不等于「功能可用」。这是 §5 要讨论的接口质量问题。

## 2. 地图集怎么用：以 `通天传授-收徒系统` 实做

### 2.1 这个地图集实际用了哪些接口（盘点）

`events/maps/mulberryTown.events.json` 共 13 条事件：

| 事件 id | trigger | 用到的能力 |
|---------|---------|-----------|
| `E01_bind_system` | `enter_map` | 开局过场 + 双 `flag_check` |
| `E02_broom_pickup` | `area_enter`(祖师堂) | 区域触发 + flag 条件 |
| `E03_xuanchen_bainian` | `interact`(uid=225) | 对话链 |
| `E05_open_forest` | `interact`(uid=219) | `toast` + `teleport` |
| `E10_fishing_at` | `area_enter`(喷水池) + `ai.gather=fish` | `repeat` + 采集声明 |
| `E11_herb_at` | `area_enter`(农田) + `ai.gather=herb` | 同上 |
| `E12_wood_at` | `area_enter`(木材堆) + `ai.gather=wood` | 同上 |
| `E50_forge_master` | **`proximity`**(uid=256) | ★ 靠近弹「🔨锻造」 |
| `E60_alchemy_furnace` | **`proximity`**(uid=257) | ★ 靠近弹「🔥炼丹」 |
| `E70_dummy_1~4` | **`proximity`**(uid=251~254) | ★ 靠近弹「⚔对打」，4 条共用一个脚本 |

**脚本层实际调用统计**（`events/scripts/*.ts` 全文扫描，共 14 种 API）：

| 调用 | 次数 | | 调用 | 次数 |
|------|------|---|------|------|
| `ui.toast` | 39 | | `save.getFlag` | 3 |
| `ui.event` | 22 | | `ui.openShopPanel` | 2 |
| `bag.give` | 8 | | `story.readJson` | 2 |
| `npc.byUid` | 6 | | `npc.setField` | 2 |
| `ui.subtitle` | 5 | | `ai.generate` | 2 |
| `save.setFlag` | 5 | | `ui.select` | 1 |
| `ui.confirm` | 3 | | `save.delFlag` | 1 |

**完全没被用到的能力**（可作为后续扩展的备选）：`ui.prompt`、`bag.list`、`bag.remove`、
`save.all`、`level.switchTo`、`level.setLocked`、`cmd`、`audio.play`、`llm.speak`、
`registerAction`、`npc.setLabel/move/faceTo`，以及声明层的 `interval` 触发器与
`ai_trigger` / `ai_interval` 动作。

也就是说这个地图集覆盖了约一半的接口面——**这不是问题**，靠近目标本来就用不到定时器、
AI 心跳、切图与音效。但反过来看：**「插件提供了 30 个方法」和「一个真实地图集只用了 14 个」
之间的差，正是接口设计是否合理的信号**（见 §5）。

### 2.2 第一步：在地图里放目标对象

在 `Actors` 对象层放一个对象，**必须确认三件事**：

| 要素 | 说明 | 错了会怎样 |
|------|------|-----------|
| `id` | Tiled 自动分配的对象 id（251、256…），**事件里的 `uid` 就是它** | uid 对不上 → 按钮永不出现，且校验器报 error |
| `gid` | 对象**顶层** `gid` = tileId + firstgid，决定**长什么样** | `gid=0` → 用 `entity_type` 默认贴图（假人就是骷髅） |
| `properties.entity_type` | 决定**行为类** | 写成野怪白名单类型又没写 `camp` → 被当怪刷出来 |

功能设施的推荐配法：

- 人形设施 → `entity_type: "NPC"` + `camp: "neutral"`

### 2.3 第二步：写事件（声明「靠近弹什么按钮」）

文件：`events/maps/mulberryTown.events.json`（**文件名必须与地图 JSON 主名一致**）。

```json
{
  "id": "E50_forge_master",
  "comment": "走近锻造大师：走进即弹「锻造」按钮",
  "trigger": { "type": "proximity", "uid": "256", "radius": 2.8 },
  "proximity": { "label": "锻造", "icon": "🔨", "hint": "走近锻造大师" },
  "repeat": true,
  "actions": [{ "type": "run_script", "script": "E50_forge_master" }]
}
```

逐字段：

| 字段 | 必填 | 说明 |
|------|------|------|
| `trigger.type` | ✅ | 固定 `"proximity"`（不是 `interact`！`interact` 走「💬 聊天」通道） |
| `trigger.uid` | ✅ | Tiled 对象 id，写成字符串最保险（引擎两边 `String()` 后比较） |
| `trigger.radius` | — | 触发半径（**世界米**）。缺省 **2.8**；写小于 **0.8** 会被钳制到 0.8 |
| `proximity.label` | ✅ | 按钮文字，缺省「交互」 |
| `proximity.icon` | | 按钮图标，缺省「✦」 |
| `proximity.hint` | | 悬停提示；缺省 `与<实体名>交互` |
| `repeat` | ✅ | **设施类必填**。不写 → 这张图只 fire 一次，第二次点没反应 |
| `actions` | ✅ | 通常只有一条 `run_script` |

⚠️ **`proximity` 是事件顶层字段，不是 trigger 里的**。写进 trigger → 按钮显示默认的「✦ 交互」。

**一个脚本服务多个对象**（假人 251~254 就是这么写的）：4 条事件指向同一个脚本。

```json
{ "id": "E70_dummy_1", "trigger": { "type": "proximity", "uid": "251", "radius": 2.8 },
  "proximity": { "label": "对打", "icon": "⚔", "hint": "走近练习假人1" },
  "repeat": true, "actions": [{ "type": "run_script", "script": "E70_training_dummy" }] }
```

⚠️ 这种写法有**真实代价**：`run_script` 的 `args` 不透传（§5.2 缺口 G2），
脚本拿不到「是哪个 uid 触发的」，只能自己找「半径内最近的假人」。见 §2.6。

### 2.4 第三步：写脚本（点击之后干什么）

文件：`events/scripts/E50_forge_master.ts`（全插件共用一个脚本目录，**必须加故事前缀**）。

```ts
/**
 * E50_forge_master — 锻造大师：点击「🔨 锻造」→ 打开锻造面板
 * trigger: proximity(uid=256)；数据: data/shop.forge.json
 */
import type { Ctx, ShopGood } from "../shared/_ctx";

export default async function main(ctx: Ctx): Promise<void> {
  // ① 读本地图集自己的数据（路径相对故事根目录，安装态从 .tbg 里读）
  const raw = await ctx.story.readJson<{ goods?: ShopGood[] } | ShopGood[]>("data/shop.forge.json");
  const goods: ShopGood[] = Array.isArray(raw) ? raw : Array.isArray(raw?.goods) ? raw.goods : [];
  if (!goods.length) {
    // 缺数据就明说，不要静默开一个空货架
    ctx.ui.toast("货架空了：故事包缺少 data/shop.forge.json", "red");
  }

  // ② 打开多标签面板（forge = 售卖/打造/升级/溶解）
  ctx.ui.openShopPanel({ mode: "forge", tab: "sell", goods });

  // ③ HUD 事件流留一条记录，方便排查
  ctx.ui.event(`打开锻造面板（${goods.length} 件商品）`);
}
```

脚本硬性要求（校验器会扫）：

1. **`export default async function main(ctx: Ctx)`**，返回 `Promise<void>`。
2. `import type { Ctx } from "../shared/_ctx"`（type-only）。同步到 `vue/src/eventScripts/` 时改成 `"./_ctx"`。
3. 只调 §1.8 白名单里的 `ctx.*`，否则校验器 error。
4. 不许 `while(true)` / `for(;;)`；需要循环用 `setInterval` 并自己清理。

### 2.5 面板里能放什么（4 种 UI，选一个或组合）

| API | 长相 | 返回 | 玩家取消时 | AI 托管执行时 |
|-----|------|------|-----------|--------------|
| `ctx.ui.openShopPanel({mode, tab, goods})` | 多标签大面板（锻造 4 页 / 炼丹 3 页） | 无（`void`） | 玩家自己关 | **自动忽略** |
| `ctx.ui.select({title, detail?, options})` | 竖排选项卡片 | `string \| null` | `null` | **自动选第一个** |
| `ctx.ui.confirm({title, detail?})` | 确认框 | `boolean` | `false` | **自动 true** |
| `ctx.ui.prompt({title, detail?})` | 单行输入框 | `string \| null` | `null` | **自动返回 defaultValue/空串** |

配套反馈：`toast`（右下角飘字）/ `subtitle`（顶部字幕）/ `event`（HUD 事件流，EventPanel 可见）。

> 需要「点了之后必须有明确回执」的操作（买/卖/打造），不要自己在脚本里算——
> 面板已经把这类操作交给 `forgeOps.ts` + 后端命令，结果用**模态弹窗**告诉玩家。
> 详见 [锻造师or炼丹炉.地图集制作案例.md](锻造师or炼丹炉.地图集制作案例.md)。

### 2.6 一个脚本服务多个对象：写法与代价

假人脚本过去必须自己找目标，因为引擎不告诉它 uid。**现在引擎已经透传了**（P0-1 已落地）：

```ts
// ✅ 现在（推荐）：直接用引擎透传的 uid，不用猜
const target = ctx.event.uid ? ctx.npc.byUid(ctx.event.uid) : null;
const mode = String(ctx.event.args.mode || "stand");
```

```ts
// 旧写法（引擎未透传时）：靠「半径内最近的假人」反推
const me = ctx.player;
const cands = ["251", "252", "253", "254"]
```

## 3. 按钮的运行时行为（照着设计不会踩坑）

| 行为 | 实现细节（`App.vue:updateNearInteraction`） |
|------|------|
| 谁被算作「候选」 | 事件里所有 `proximity` 点 → 按 uid 找实体：`mapnpc_<uid>` / `mapnpc_<uid>_*` / `mapmob_<uid>` / `mapmob_<uid>_*` |
| 取哪个 | 半径内**最近**的那个；同屏多个设施只显示一个按钮 |
| 实体死了还弹吗 | 不弹（`ent.alive === false` 直接 `continue`） |
| 会不会同时弹「💬 聊天」 | **不会**。`eventUidsHas` 把挂 proximity 的 uid 排除在聊天候选外 |
| 按钮什么时候消失 | 走出 `radius` 即消失 |
| 点击后 | `nearInteraction=null` + `interactionDismissed=true`；**下一帧重新计算**（仍在半径内 → 按钮又出现） |
| 连点两次 | `repeat: true` 有 **3 秒冷却**（`repeatCooldown.set(ev.id, now+3000)`），冷却内点击被静默丢弃 |
| 点一次就永久没了 | 忘了 `repeat: true`（非 repeat 事件每张图只 fire 一次，`firedIds` 切图时重置） |

**冷却与「条件不满足」的联动坑**：`repeat` 事件**条件不满足也进冷却**
（[规范.md](../规范.md) §4 #8）。所以设施类事件**不要叠 `conditions`**——
想「解锁后才能用」，把判断写进脚本，用 `toast` 告诉玩家为什么不能用。

## 5. 插件是否需要提供更多函数和接口

### 5.1 判定标准：什么该进插件，什么不该

规范说「插件尽量不改，改也得按着**通用函数和接口**的方向修改」。落到判据上是三条：

| 判据 | 该进插件 | 不该进插件 |
|------|---------|-----------|
| **复用性** | 两个以上地图集会用到 | 只有一个故事用 |
| **能力性** | 需要引擎内部状态/通道（`state.entities`、`sendTick`、`.tbg`） | 纯数据/纯文案 |
| **通用性** | 签名里不出现故事名、设施名、商品名 | 参数写死某故事的 id |

按这三条筛，下面 §5.2 的缺口**全部符合**（都是引擎内部能力，且任何地图集都会撞上）。

### 5.2 现有缺口（附源码位置）

> **状态列说明**：✅ = 已落地（P0，2026-10-28 已实现并随 v1.0.25 构建）；⏳ = 待排期。

| # | 缺口 | 状态 | 证据 | 影响 |

| **G3** | **脚本读不到金钱 / 等级** | ✅ **已实现** | `eventEngine.ts` `EventHooks.playerCard?()` + `makeCtx().playerCard`；`App.vue` 注入 `playerCard` | 设施门槛判断（钱/等级/血量）不再需要后端往返 |

| **G5** | **`proximity` 文案不可动态改** | ⏳ 待排期 | `label/icon/hint` 只从静态 JSON 读（`getProximityPoints`） | 无法表达「已解锁 🔨锻造」vs「未解锁 🔒需拜师」；只能靠脚本里 toast 事后解释 |
| **G6** | 4 个空实现混在白名单里 | ⏳ 待排期 | `npc.setLabel/move/faceTo`、`audio.play`、`llm.speak`、`registerAction` | 校验器放行、运行时无声失败（§1.8），新人极容易踩 |
| **G7** | 同一 uid 不能「既聊天又开面板」 | ⏳ 待排期 | `eventUidsHas` 把 proximity uid 从聊天候选排除 | 功能设施想保留闲聊能力必须改挂 `interact` + `select` 兜一层，交互多一次点击 |

### 5.3 建议新增（按优先级）

**P0 —— 直接影响「靠近目标」这一类做法（✅ 已于 2026-10-28 落地，随 v1.0.25 构建）**

1. **`run_script` 透传 `args`**（修 G2）✅
   ```json
   { "type": "run_script", "script": "E70_training_dummy", "args": { "mode": "duel" } }
   ```
   签名不变（`main(ctx)`），另给 `ctx.event: { id, uid?, args }`。
   *收益*：删掉所有「找最近实体」的猜逻辑；一个脚本天然服务 N 个对象；地图集不用为每个对象写死参数。
   *风险*：低（纯新增字段，旧事件不传 args 行为不变）。

   **已实现的实际用法**：
   ```ts
   // events/scripts/xxx.ts
   export default async function (ctx: Ctx) {
     const uid = ctx.event.uid;                          // 触发实体的 Tiled 对象 id
     const mode = String(ctx.event.args.mode || "stand"); // run_script 里配的参数
     const target = uid ? ctx.npc.byUid(uid) : null;
     ...
   }
   ```
   - `uid` 只有 `interact` / `proximity` 触发时才有；`enter_map` / `area_enter` / `interval` 为 `undefined`。
   - `args` 非对象（字符串/数组）会被引擎归一为 `{}`。

2. **暴露 `ctx.ui.notice`**（修 G1）✅
   ```ts
   notice(opts: { title: string; detail?: string; confirmText?: string }): Promise<void>;
   ```
   *用法*：`await ctx.ui.notice({ title: "打造成功", detail: "获得【精铁剑】×1" })`。
   **AI 执行者自动跳过**（立即 resolve），不会打断 AI 托管流程。
   *收益*：脚本侧也能做「结果必须点确认」的反馈，与面板操作体验一致。

3. **暴露 `ctx.playerCard`（只读）：`{ level, money, hp, maxHp }`**（修 G3）✅
   *用法*：
   ```ts
   if (ctx.playerCard.level >= 20) { ... }
   else if (ctx.playerCard.money < 100) { ctx.ui.toast("盘缠不足", "red"); }
   ```
   *注意*：这是**只读快照**，改数值要走 `ctx.cmd` / `ctx.save`；AI 执行者拿到的也是同一个玩家卡快照。
   *收益*：设施门槛判断（钱/等级）不再需要后端往返；也让脚本能做「按玩家等级给不同货单」。

> G1/G2/G3 已加入 `validate_events.mjs` 的 `CTX_API` 白名单：
> `ui.notice` / `event.id` / `event.uid` / `event.args` /
> `playerCard.level` / `playerCard.money` / `playerCard.hp` / `playerCard.maxHp`。
> 完整说明见 [API文档.md §2.8](../API文档.md)。

**P1 —— 让 proximity 表达力跟上设计需求**

4. **`proximity` 支持 `maxUses` / `cooldownMs`**（修 G4）
   ```json
   "proximity": { "label": "开箱", "icon": "📦", "maxUses": 1 }
   ```
   引擎侧用 flag 记 `prox_used_<eventId>`，用完自动从 `getProximityPoints` 剔除（按钮消失而不是点了没反应）。
   *收益*：一次性宝箱/限次设施不用手搓 flag；且「按钮消失」比「点击被丢弃」对玩家友好得多。

5. **`proximity.label` 支持占位符或脚本回填**（修 G5）
   最小实现：允许 `label: "{lock}锻造"`，脚本通过 `ctx.npc.setField` 之外的新 API `ctx.ui.setProximityLabel(uid, text)` 覆盖。
   *收益*：解锁态可视化，不必点进去才知道没资格。

6. **空实现标记进类型**（修 G6）
   把 `npc.setLabel/move/faceTo`、`audio.play`、`llm.speak`、`registerAction` 在 `_ctx.ts` 上打 `@deprecated /** 未实现 */`，
   并让 `validate_events.mjs` 对它们从 `pass` 降级为 `warn`。
   *收益*：机器提示替代口口相传，减少「校验通过但没效果」的排查时间。

**P2 —— 锦上添花**

7. `proximity.conditionText`：条件不满足时按钮仍显示但置灰，悬停显示原因（替代现在的「脚本里 toast 解释」）。
8. `ctx.ui.notice` 之外的 `ctx.ui.toast` 支持 `duration`（现在固定时长，长文案看不完）。
9. `ctx.cmdAwait(action, params, timeoutMs)`（把 `forgeOps.ts` 的 `sendSysCmdAwait` 上收到引擎，修 §1.6 的回执问题）。
   *注意*：这条与「插件尽量不改」有张力，属于**能力缺口**而非风格偏好，建议单独立项评估。

### 5.4 明确**不该**加进插件的

| 想法 | 为什么不加 |
|------|-----------|
| `ctx.forge.open()` / `ctx.alchemy.open()` 之类的业务语义 API | 业务在货单，`openShopPanel` 已足够通用；加语义 API 等于把某故事的玩法写进插件 |
| 把「锻造大师/炼丹炉/假人」的默认配置内置成插件常量 | 直接违反 §严重违规第 1 条 |
| 为某个故事加 `proximity` 的专属 `label` 映射表 | key 是跨故事共享的 uid/事件 id，写死会打坏别的故事 |
| 在插件里预置 `data/` 模板 | 数据必须随故事包走，插件里一放就变成「第二正本」 |

> **一句话结论**：插件该补的是 **G1/G2/G3 这三个「能力缺口」**（都是引擎内部状态/通道，无法在地图集侧绕过），
> 以及 **G4/G5 这两个「proximity 表达力缺口」**（贴近本案例主题）。
> 其余（G6/G7、P2 各项）属于体验优化，可排期。
> **不要**因为某个故事的玩法需要，就往插件里加业务语义 API——那正是规范头号禁令。

## 6. 校验 + 调试

```bash
# 1) 静态校验（必跑，0 error 才算写完）
node .cache/validate_events.mjs 通天传授-收徒系统

# 2) dev 起服，进图实测
cd plugins/toonflow-field-survival/vue && npm run debug -- --story 通天传授-收徒系统 --conn
```

校验器会检查：事件 JSON schema、`uid` 是否真的在 `maps/<map>.json` 的 Actors 层里、
`run_script` 指向的 .ts 是否存在、脚本里有没有白名单外的 `ctx.*`、
以及**插件内副本是否落后于 workshops 正本**（⚠ warn）。

游戏内调试：HUD 的 EventPanel 能看到「已加载事件 / 已触发（fired）/ 手动 fire」，
手动 fire 会临时清掉 firedIds 与冷却，可以反复点。

> ⚠️ 校验通过 ≠ 功能可用：白名单里含空实现（§1.8），且校验器不检查 `proximity` 的
> 半径是否合理、文案是否写对位置。这两项只能靠实测。

## 7. 常见坑（按现象查）

| 现象 | 原因 |
|------|------|
| 走近什么都不弹 | ① `trigger.type` 写成了 `interact`；② uid 写错（必须是 Tiled 对象 id）；③ 实体 `alive=false`；④ 事件文件名与地图主名不一致 → 整份没加载 |
| 按钮显示「✦ 交互」 | `proximity{label,icon,hint}` 写进 `trigger` 里了，要放**事件顶层** |
| 按钮出现但点了没反应 | ① 脚本没写 `export default async main`；② 脚本抛异常（console 有 `[eventEngine] 事件执行异常`）；③ 3 秒冷却内连点 |
| 第一次能点，后面点不动 | 漏 `repeat: true` |
| 同一个 NPC 又弹聊天又弹按钮 | 给同一 uid 同时写了 `interact` 和 `proximity` |
| 加了 condition 后按钮「时灵时不灵」 | `repeat` 事件条件不满足也进冷却（§4 #8）；设施类不要叠 condition |
| 脚本改了实体但游戏里没变 | 改了 `ctx.npc.byUid()` 返回的**快照**；必须用 `ctx.npc.setField` |
| 点了假人 A，B 的状态变了 | 脚本「找最近」猜错目标（§2.6）；加距离守卫，或等 args 透传 |
| 脚本里 `await ctx.cmd(...)` 拿不到结果 | `cmd` 不等回执（立即 resolve 空串）；需要结果写在前端 `forgeOps.ts` |
| dev 好用、真机没反应 | 改了 workshops 没同步插件副本 / 没重建 `.tbg`（[规范.md](../规范.md) §8） |
| 按钮出现了但实体是「隐形」的 | 对象 `gid=0` 且 `entity_type` 没有默认贴图；给对象设 gid |
