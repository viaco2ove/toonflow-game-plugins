### 连点干粮卡死（2026-11-14，用户二次实测「连按依然卡顿，动都动不了」）——真正根因

**排除过程**（longtask 实测定位，不是猜）：
1. top 主线程 longtask=0 → 桩的 handle_action 不卡
2. select 态连点 15 次 → **渲染器卡死**（CDP Page.getFrameTree 10s 超时、90 秒无响应）→ 卡在**通用消息链**
3. playing 态 3 次点击 → 又卡死 → 逐条消息触发
4. **localStorage 取证**（渲染器卡死不影响已写入数据）：`post size = 2.4MB / 9.2MB / 13MB / 7.5MB...` —— **每条 state 回推 2.4~13MB**（正常应 ~48KB），且体积持续增长

**根因**：`state` 总体积 **24MB**（fieldSizes 探针实测）——
- `playerCard` 7.34MB + `items` 7.34MB + `writeback` 7.34MB：**参数卡第 7 条物品「北境烈酒（致幻中和剂）（致幻中和剂）…」的名字被往返拼接注记膨胀到 7.3MB**（46 万层）
- 放大链：`parseItemRaw` **对象分支不剥注记**（name 原样带「（致幻中和剂）」）→ `serializeBag` 写回 `${b.name}（${desc}）` **再拼一层** → 每次操作名字翻倍（指数）
- 每条 tick/点击回推 = structured clone 24MB + iframe Vue 解析 24MB → 主线程被吃光 →「动都动不了」
- 附带：`syncCardFromContext` 每帧 `sig()` 对比要 stringify 7MB×2

**修复**（entry.ts，三处清洗形成闭环）：
1. 新增 `cleanItemName()`：≤60 字符不碰；>60 判异常 → 反复剥结尾「（…）」层 + 限长 40 + 清理未闭合尾巴
2. `parseItemRaw` **两个分支**（对象分支此前完全不剥）都过清洗 → 毒名进不了 state
3. `serializeBag` 写回清洗 → **服务器参数卡随玩家操作自愈**
4. `syncCardFromContext` 的 base.items 清洗 + **检测毒（体积骤降>50KB）主动写 writeback** → 宿主消费写回服务器参数卡 → **第一次 tick 即自愈**，不等玩家操作

**验证**：node harness 毒卡实测 3136KB→0KB（干粮功能正常、毒物品保留名字清洗）；全套 121+5 项断言全绿；浏览器实测连点 15 次 post 体积 24MB→~2MB（稳定 1.95MB = npcCards 740K + spriteGallery 491K + spriteBinds 491K + entities 156K 的正常内容）、页面保持响应。

**遗留优化项**（非本次卡死根因，记录）：`spriteBinds`（491KB）与 `spriteGallery`（491KB）等大 —— binds 疑似复制了整份 base64 形象图，应只存引用；`npcCards` 740KB 偏大。两者都修可把 state 回推压到 ~100KB。

**教训**：①「特效堆积」只是表象，真正根因在**数据体积**——用户报卡顿时先用 PerformanceObserver/体积探针量化，别在表象层修。②渲染器卡死时 CDP 全废，**localStorage 取证**是唯一能穿越卡死的手段。③AI 编排会改写参数卡——凡是从参数卡读的字符串字段都要有长度护栏。

### 「一进去就卡」（2026-11-14，用户三次实测）——第一版清洗自身成为每 tick 热点

上一轮部署 cleanItemName 清洗闭环后，用户报告**进游戏就卡**（连点都不用点）。

**复现与定位**（node harness `.cache/perf-probe-poison-name.mjs`，构造 7.3MB 毒名 playerCard 每 tick 下发）：
- **每 tick 13~17 秒 CPU**（实测连续 5 tick 均 12~17s）→ 10Hz tick 主线程彻底打死
- 开销拆解：
  1. `cleanItemName` 剥层正则 `[（(][^）)]*[）)]$` 对 N 层毒串**每轮 replace 全串 O(n) 扫描**，400 轮 × 7.3MB ≈ 数秒
  2. `syncCardFromContext` 的毒检测 `JSON.stringify(base.items)` ×2 每 tick 白扫 7.3MB
  3. 关键：这段清洗在 `sig()` 短路**之前** → 就算 state 已自愈、ctx 每 tick 仍下发毒卡，白清洗照样全跑
  4. `parseItemRaw` 字符串分支的 ×N 路径 name **不过 cleanItemName**（「毒名…×7」形态原样进 bag = 放大入口之二）

**修复**（entry.ts，性能版清洗）：
1. `cleanItemName(raw, forcePoison)`：>4KB 判毒直接 `slice(0, 64)` 再剥层（毒名主体一定在开头）→ O(64)；毒串先清截断残留的未闭合「（致幻中」尾巴再剥**到底**（非毒名保持旧语义剥到 ≤40）
2. `parseItemRaw` 字符串分支 >512 走毒快路径：尾部摘 ×N（防截断丢数量）→ `cleanItemName(forcePoison)` → O(512)；**×N 分支 name 补过 cleanItemName**
3. `syncCardFromContext` 毒检测改**零 stringify**：近似体积=Σ(字符串 .length)，仅存在 >4KB 条目才认定毒卡写 writeback —— 正常卡全程零 stringify
4. `cleanSkillName` / `cleanName` / `splitSkillList` 同款 >4096 守卫（技能名/物品 key/逐字符迭代防同款膨胀）
5. `slice(0, 40)` 截断可能切在「（」上 → 截后再清一次未闭合尾巴

**验证**：
- 性能探针：每 tick **13~17 秒 → 3~15ms**（~3000 倍）；writeback=Y 自愈保留
- 语义检查 `.cache/sem-check-clean.mjs` 13/13：正常名+注记放行（「银鲤×3」数量正确）/纯注记名原样/毒名剥底干净（「北境烈酒×2」纯主体）/毒串「×7」数量保留/无未闭合尾巴
- 回归：v2-fx 55 项 + v2-geo 8 项 + v2-item-spam 8 项全绿
- esbuild esm 部署；真机（60002）用户卡顿会话 `gs_1789458006016_e0d4ebf114` tick **31~76ms**、items 7 条 0.1KB
- DB 取证：毒名已自愈——`t_gameSession.stateJson` 中该物品名从 7.3MB → ~60 字符（≤60 旧语义放行不再膨胀，仅残留注记层属显示问题）

**教训**：①修复热路径前先写**性能 harness 计时**——「自愈了还卡」说明白开销在 sig/消费短路之前（每 tick 都跑的代码不能有 O(n) 大串操作）。②清洗/守卫类修复自身也要过性能关：对超长串的**任何正则、逐字符迭代、stringify 都要先截断再处理**。③正则带 `$` 锚定 + 回溯源（`[^）)]*`）在大串上极易 O(n)×轮数放大。

### R4 buff 徽章不消失修复（2026-11-14，用户验收 fail + 问「buff 生效时间是多久」）

**结论：设计时长 = 30 秒，但实际挂了 ~5 分钟**——`buffUntilTick = tick + 300` 是 **tickUntil 型
计时器**，挂机档 3 秒无输入掉 1Hz 后 300 tick = **300 秒**（「挂机档计时器慢 10 倍」的
同款漏网：cd/飘字/特效当年已改 `_dec` 折算，buff 用 tick 绝对值漏了）。清理链路本身
完好（到期清 buffs + clearHeadBadge），纯粹是「到点」太晚。

**修复（三桩同步）**：
- entry.ts：新增 `Entity.buffUntilMs`（Date.now 基准）+ `BUFF_DURATION_MS = 30000`；
  `applyBuff` 主计时写 `buffUntilMs`（durationMs 参数，旧 durationTicks 按 100ms/tick 兼容折算）；
  tick 循环到期判断改 `Date.now() >= buffUntilMs`（buffUntilTick 保留兼容旧存档）；
  徽章 expireTick 按 `_tickDeltaMs`（step 缓存的真实节奏）折算，仅作前端渐隐参考
- v2Stub.ts / vite.config PAGE：`v2ApplyBuff` + 到期清理同款改 ms
- 回归适配：v2-fx §4「模拟过期」从推 tick 改为把 buffUntilMs 设到过去（新增断言
  「buffUntilMs 真实时间戳存在」）

**验证**：v2-fx 56 项 + v2-item-spam 8 项全绿；entry.js esm 部署；ui/game.html 重建。

**附带发现（未修，记录）**：≤60 字符放行语义下，「北境烈酒」名会被 serializeBag 的
desc 拼接逐层生长到 **60 字符顶格**（实测 8 层「（致幻中和剂）」）——有界不再膨胀但
显示难看；彻底洗净需把「重复注记层检测」下沉到 ≤60 区间（风险：误伤正常注记名）。

**教训**：**tickUntil 型计时器（X = tick + N）在变频 tick 下全部不可靠**——凡「时长」语义
一律用真实时间戳（Date.now 基准）或 `_dec` 折算；本项目已有三次同类事故（cooldown/
飘字/特效、实体 cooldown、buff），新计时字段落地前先问「挂机档 1Hz 时它多长」。
