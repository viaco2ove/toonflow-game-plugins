# mcp 支持双向即时传输的嘛？
💩mcp 支持双向即时传输的嘛？

一句话结论：MCP（Model Context Protocol）协议层本身支持双向即时消息；但要看你用哪种 transport，标准的两个内置 transport 表现不一样

1. stdio（本地子进程）✅ 原生双向即时

stdin：client → server

stdout：server → client

是全双工流，两边随时发 JSON-RPC 消息（request / notification），没有轮询，实时性很好；本地开发最稳

2. Streamable HTTP（现在标准远程 transport）⚠️ 是“伪全双工”

Client → Server：HTTP POST

Server → Client：SSE 长流（GET）

不是一条 WebSocket 那种单条全双工通道：上行每次 POST，下行走 SSE 推消息；可以做到双向即时收发，但底层是两个方向分开，延迟比 stdio 高一点

协议上允许 server 主动发 request / notification 给 client（比如 sampling、资源变更通知），不是只能 client 问 server 答

3. 关键区分：协议语义 vs 传输通道

MCP 基于 JSON-RPC 2.0：

任意一方都可以发起请求、发通知（notification，不需要回复）

支持服务端主动推送事件（订阅 subscriptions/listen），做实时更新

协议本身不绑定传输，你完全可以自己写 WebSocket / WebTransport 自定义 transport，实现真正单通道全双工双向流

简单对比

Transport	双向即时	通道类型	适用
stdio	✅ 很好	原生全双工	本地进程（Claude Desktop 这类）
Streamable HTTP	✅ 可以，但分两条方向	POST + SSE	网络远程服务
WebSocket（自定义）	✅ 最佳	单条全双工	自己封装

如果你想要像 WebSocket 一样一条连接两边随时发数据、低延迟双向流，内置 transport 里没有，要自己实现自定义 transport；但业务层面“双向即时交互、服务端主动推事件”MCP 本身是支持的。

要不要我给你一段极简示意，看 stdio 和 streamable http 下 server 主动发通知给 client 的消息样例？

stdio？网页端连接后端可以使用的嘛？

核心结论

网页前端（浏览器）不能直接用 stdio transport 连 MCP Server

stdio = 标准输入输出，是操作系统进程间管道（stdin/stdout），浏览器环境根本没有这个能力，浏览器拿不到另一个进程的 stdin/stdout 句柄。

梳理清楚几条路线

stdio：只适合本地同机器进程调用
 典型场景：Claude Desktop / 本地客户端程序，启动一个 mcp-server 子进程，父子进程通过 stdin/stdout 互通。

浏览器 JS、前端页面 ❌ 无法直接使用 stdio transport。

网页端原生能用的官方 MCP transport：Streamable HTTP（POST + SSE）

上行：POST 发 JSON-RPC 请求

下行：GET 建立 SSE 长连接，接收服务端推送通知、主动消息

就是 MCP 官方设计给远程访问、Web 场景的方案

缺点：上行每次是独立 POST，不是一条流；但协议语义上仍然支持双向交互、服务端主动通知（MCP sampling、日志推送、资源变更都可以跑）

如果你想要网页端“单通道全双工”体验（类似 stdio 的流畅双向流）
 两种方案：

方案A：自己封装 WebSocket 自定义 Transport
后端开 WS 服务，在 WS 通道里跑 MCP JSON-RPC 报文。一条连接双向随时收发，体验最接近 stdio，延迟更低。不属于官方内置 transport，要自己实现两端的 transport 层。

方案B：中间加一层中转代理
浏览器 <--(SSE/WS)--> 你的代理服务 <--(stdio)--> MCP Server
✅ 这个很常用！
代理服务（Node/Python/Java）本地 spawn 启动 mcp-server 子进程，用 stdio 和它通信；同时对外暴露 HTTP/SSE 或者 WebSocket 给网页。

相当于把 stdio 包一层网络，给浏览器用。

选型速记

接入方式	浏览器直连	特点
stdio	❌ 不行	本地进程管道
Streamable HTTP（官方）	✅ 可以	POST + SSE，开箱标准，不用自己定义协议
WebSocket 自定义 transport	✅ 可以	单通道全双工，性能更好，需要自己编 transport
代理转发 stdio	✅ 可以	复用现成 stdio 版 MCP Server，代理做桥

一个常见坑

很多现成的 MCP Server 只提供 stdio 模式，没有内置 Streamable HTTP。

这种想给网页用，就必须搭上面说的中转代理，把 stdio 转成 SSE / WS。

如果你打算做网页端 MCP 客户端，我可以给你一个最简的 Node 桥接示例：代理接收浏览器 SSE 请求，内部 spawn mcp-server，走 stdio 转发报文。

Streamable HTTP vs WebSocket（自定义）

一句话总纲

Streamable HTTP：MCP 官方标准，基于 HTTP，每个上行消息独立 POST，下行在本次请求的响应里走 SSE；开箱兼容所有 MCP SDK，但不是“一条通道随便双向发”。WebSocket（自定义）：单条 TCP 全双工长连接，随时双向发 JSON-RPC，延迟更低、高频交互舒服，但不属于官方 transport，两端都要自己写传输层

注意：最新 2026-07-28 版本 Streamable HTTP 已经去掉独立 GET SSE 流、协议 session-id；SSE 流是绑定在单次 POST 请求的响应上，不是全局长推流；server 主动消息（sampling、订阅变更）是靠 subscriptions/listen 这类请求拉起的流，不是脱离请求随便发

对比表

维度	Streamable HTTP（官方）	WebSocket（自定义 MCP transport）
是否标准	✅ MCP 内置标准 transport	❌ 自定义扩展，不在 spec 内置
底层模型	每次客户端发消息 = 一次 POST；响应可以是 JSON 或者 SSE 流（绑定本次请求）	握手后单条持久全双工通道，两边随时发帧，无请求-响应绑定
上行开销	每次消息都有 HTTP 头、握手、可能跨域预检；高频发消息开销明显	连接建立后几乎无额外头，高频指令更省
延迟	中等，每次 POST 有开销	更低，接近 stdio
服务端主动推送	不能脱离请求随便推；只能在某个请求的 SSE 响应流里推送（订阅流）	✅ 任意时刻主动发 request / notification，和 stdio 语义一致
基础设施友好	极强：CDN、负载均衡、网关、鉴权、日志、trace、缓存全部原生支持；无特殊代理要求	弱：很多 CDN、防火墙、反向代理对 WS 长连接有限制、超时、断连、不支持分片
无服务/Serverless	✅ 友好，单次请求可以跑在 Lambda / SCF	❌ 非常不友好，需要常驻连接服务
断线重连	天然按请求隔离，断了重发 POST；订阅流断了客户端重新发起 subscriptions/listen	需要自己实现心跳、重连、消息队列、丢包补偿
浏览器兼容性	✅ 原生 Fetch + EventSource	✅ 原生 WebSocket API
SDK 支持	主流 MCP SDK 直接支持，不用写 transport	几乎所有 SDK 都要自己实现 Transport 接口
适合消息频率	中低频：工具调用、资源查询、Agent 轮次交互	高频：连续实时指令、实时打断、流式交互、低延迟双向推送

核心坑点（非常容易踩）

Streamable HTTP 不是自由全双工
很多人误以为它和旧版独立 /sse 端点一样，服务端可以随便往外发消息。新版规范下：所有 server→client 的消息，必须依附在某一个 client 发起的请求的响应流里面。
如果你想要服务端“无缘无故”主动推一条通知给客户端，Streamable HTTP 做不到；必须客户端先开一个 subscriptions/listen 长流请求，所有变更从这个流出来。

WebSocket 只是一根管道，MCP JSON-RPC 语义完全不变
你在 WS 里跑的还是同一套 MCP 消息（initialize、tools/call、notifications 等），只是换了传输层；MCP 上层逻辑不用改，只是 transport 层自己写编解码、分包、心跳。

鉴权、CORS

Streamable HTTP：Bearer token、Cookie、OAuth、Origin 校验，就是普通 HTTP 那一套，运维最熟

WebSocket：握手阶段带鉴权，握手之后通道里很难再动态换凭证；很多企业防火墙对 wss 单独策略

选型建议

✅ 选 Streamable HTTP：网页端正式上线、走云函数/Serverless、需要CDN/网关、不想维护自定义transport、交互频率不算爆炸、优先遵循官方标准，对接第三方现成MCP服务

✅ 选 自定义 WebSocket Transport：你自己同时掌控前后端、追求贴近 stdio 的流畅双向、大量高频实时消息、需要随时 server 主动推送、愿意自己维护 transport 层（心跳、重连、消息排序）

补充一个和你前面需求相关的结论

如果你是做网页端 MCP 客户端：

快速上线、复用现有 SDK：Streamable HTTP

想要体验和本地 stdio 几乎一样（随时双向发、低延迟、可以随时打断、高频推送）：WebSocket 自定义 transport

WebSocket Transport 是不是要用独立端口

不一定非要独立端口，两种做法都可行：同端口复用 / 单独端口，看你的后端架构。

1. 同端口（推荐，生产优先）

HTTP 和 WebSocket 可以共用同一个端口，靠路径区分：

POST /mcp → 普通 HTTP 接口

GET /mcp/ws → 升级为 WebSocket（Upgrade: websocket 握手）

原理：WebSocket 握手本身就是一次标准 HTTP GET 请求，服务器在同一个端口上判断：

带 Upgrade 头 → 升级协议，交给 WS handler

没有 → 走普通 HTTP 逻辑

好处：

只开一个端口，防火墙、Nginx/反向代理、域名证书、CORS 都统一配置，不用多开端口、多域名

域名就是 wss://xxx.com/mcp/ws，和 [https://xxx.com](https://xxx.com) 同一个域名

Nginx、SpringBoot、Node、FastAPI 全都支持这种多路复用。

2. 独立端口（开发简单，但上线麻烦）

比如主服务 8080，WS 单独跑 8081：

[http://127.0.0.1:8080](http://127.0.0.1:8080)

ws://127.0.0.1:8081/mcp

适合本地调试、快速写 demo； 缺点：

上线要额外开放端口、安全组、防火墙策略

浏览器跨域、证书、CDN 配置变麻烦（wss 端口和 https 不一样）

很多托管平台（部分 Serverless、云函数）不支持额外长连接端口

结合 MCP 的场景重点提醒

你做的是自定义 WebSocket Transport 跑 MCP JSON-RPC：

协议层面不关心端口，只关心连接；端口是 HTTP 服务器的事

如果你同时还准备保留 Streamable HTTP，强烈建议：同端口，路径区分

https://host/mcp → Streamable HTTP

wss://host/mcp/ws → WebSocket transport

一个常见误区

很多人以为 WebSocket 必须单独端口，是早年很多 demo 直接开一个独立 ws server 导致的习惯，不是规范要求。

补充：Nginx 同端口配置示意（极简）

server {
    listen 443 ssl;
    server_name your.domain;

    location /mcp/ws {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
    location /mcp {
        proxy_pass http://backend;
    }
}
