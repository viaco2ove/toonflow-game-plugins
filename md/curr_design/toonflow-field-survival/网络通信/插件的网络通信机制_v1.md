# 插件的网络通信机制 —— 为什么是高频 tick，以及优化路线

> v2.0 · 2026-11-01
> 基于对 `Toonflow-game-web/src/components/ScenePlay.vue`（5175 宿主）、
> `toonflow-game-app/src/routes/plugin/tick.ts`（60002 后端）、
> `plugins/toonflow-field-survival/vue/src/App.vue`（插件前端）的实际代码分析。

---

## 一、现状：一次 tick 的完整旅程

```
插件前端 (iframe, 60002 game.html)
  │  requestAnimationFrame 循环（60fps 渲染）
  │  每 TICK_MS=100ms：localTick() 本地推进 + 每 SEND_MS=100ms（移动端 200ms）
  ▼  postMessage({type:'tf_plugin_tick', action:'tick', params:{...}})
宿主 (5175, ScenePlay.vue onPluginIframeMessage)
  │  handlePluginTick() → store.api.pluginTick()
  ▼  POST /plugin/tick （10Hz · 每秒 10 次 HTTP 请求）
后端 (60002, routes/plugin/tick.ts)
  │  ① 会话串行锁（tickLocks，按 sessionId 排队）
  │  ② 读 session.stateJson（整份 JSON parse）
  │  ③ 读 plugin_state（t_plugin_session_data 表，~48KB JSON parse）
  │  ④ entry.js step()：宿主代跑游戏逻辑（敌怪 AI/碰撞/结算）
  │  ⑤ applyFieldSurvivalWriteback + applyPlayerCardPatch（写回故事动态数据）
  │  ⑥ setPluginData(PLUGIN_STATE_KEY)  ← UPSERT 写库
  │  ⑦ 部分 scene 条件下 UPDATE session.stateJson  ← 第二次写库
  ▼  返回完整 resultState（~48KB JSON）
宿主
  ▼  postMessage({type:'tf_plugin_state', state}) → 插件渲染
```

### 关键参数（实测代码值）

| 参数 | 值 | 位置 |
|---|---|---|
| TICK_MS（逻辑推进周期） | 100ms（10Hz） | 插件 App.vue:6646 |
| SEND_MS（上报周期） | 桌面 100ms / 移动端 200ms | 插件 App.vue:4624 |
| 渲染帧率 | 桌面 60fps / 移动端封顶 33ms | App.vue:4622 |
| 单次 tick 响应体积 | ~48KB（完整 plugin_state） | 宿主日志 `POST /plugin/tick 200 36ms - 48577` |
| 每 tick 数据库写入 | **2 次**（plugin_state UPSERT + stateJson UPDATE） | tick.ts:263/297 |
| 会话并发控制 | 串行锁（同 sessionId 排队） | tick.ts:23 |

**即：每个进行中的游戏会话，稳态流量 ≈ 10 req/s × (48KB 上行 state + 请求) ≈ 每秒 ~500KB 的 JSON 序列化/反序列化 + 每秒 20 次磁盘写。**

## 二、为什么这么做（设计动机 —— 大多是合理的）

### 1. 权威状态在后端（防作弊 + 多端一致）
`plugin_state` 存在数据库而非 iframe 内存。iframe 与后端**不同源且拿不到 JWT**
（ScenePlay.vue:1518 注释原文），插件自身无法直连 API——必须由宿主代发。
把游戏逻辑放后端 step() 里跑，意味着：

- 玩家改前端内存作弊无效（权威数值在后端）；
- 换端/刷新/重进游戏，进度不丢（state 持久化）；
- 编排器（故事引擎）复写 stateJson 不会毁掉进行中的游戏（v5 已把 plugin_state 拆到独立表，根治 clobber 竞态）。

### 2. 宿主是"哑管道"（thin proxy）
5175 剧场宿主对插件游戏内容零理解——它只做 `iframe → POST /plugin/tick → 回推`。
这让插件可以自带任意游戏逻辑（entry.js 是任意 JS），宿主不用为每个插件写集成代码。
**这是"插件生态"能成立的基础**：插件作者只需要实现 handle_action 协议。

### 3. tick 粒度 = 游戏逻辑粒度
10Hz 的选择来自游戏手感：`TICK_DT = 0.1`（秒），移动速度、碰撞、技能冷却都按 100ms
标定。帧率（60fps）只管渲染插值，逻辑固定 10Hz——这是标准游戏架构（渲染/逻辑分离），
本身没错。

### 4. 前端已做过的优化（说明作者有性能意识）
- 本地预推进 `localTick()`：输入在本地即时反馈，宿主只镜像位姿（消除坐标双写）；
- `localEnemies` 按世代号（epoch）只在结构性变化时上报整份清单；
- `walkGrid` 仅切图那一次上报；
- 移动端 SEND_MS 翻倍到 200ms、渲染封顶 30fps；
- 页面隐藏（`document.hidden`）时完全停发；
- 409 连击防护（失败 5 次暂停 + 状态探测自愈）。

### 5. 历史路径依赖
这套机制从「小游戏 = 实时动作游戏（野外生存）」长出来。动作游戏确实需要 10Hz
权威模拟。问题在于：**协议被泛化成了所有插件小游戏的唯一通道**——
哪怕一个纯回合制的卡牌插件，也得为"挂机时敌怪不动"的实时语义付 10Hz 的成本。

## 三、成本清单（问题在哪）

| # | 成本 | 量级 | 说明 |
|---|---|---|---|
| C1 | **无效轮询** | 稳态 100% | 玩家挂机/无输入时，10Hz 照发——后端 step() 大部分是"无人移动、敌怪待机"的空转 |
| C2 | **全量状态回传** | ~48KB/次 | state 里 90% 字段（entities/chests/potions/vfx…）每次原样往返，变化的可能只有 2-3 个坐标 |
| C3 | **双写库** | 20 写/秒/会话 | plugin_state UPSERT + stateJson UPDATE，SQLite 单写者锁下多会话会互相排队 |
| C4 | **序列化 CPU** | 2×48KB parse+stringify × 10Hz | JSON.parse/JSON.stringify 每秒 ~1MB 的字符串处理 |
| C5 | **串行锁排队** | P99 延迟 | 同会话 tick 排队本身是对的，但 sys_brain（LLM 决策，1-5s）也走同一把锁——AI 决策期间所有帧 tick 被堵（此前短信超时的帮凶之一） |
| C6 | **HTTP 开销** | 10 req/s | 连接头/TLS（同源部署下较小，但仍是固定成本） |
| C7 | **断线体验** | — | HTTP 轮询断线后只能靠 failStreak 探测，恢复靠重试 |

---

## 四、优化方案（不动架构，按 ROI 排序）

### O1. 脏检查 + 增量回传（省 C2/C4，收益最大、改动最小）★推荐先做
后端 step() 后对比上帧 state，只把**变化字段**放进响应：

```ts
// tick.ts 伪码
const next = resultState;
const patch = diffState(lastSent, next);   // 深比较，只留变化的路径
if (isEmpty(patch) && !next.forceFullSync) {
  return { code: 0, state: null }          // ★ 304 语义：state 无变化，回 null
  //                        宿主 postMessage 时跳过 → 前端零渲染
}
lastSent = next;
return { code: 0, state: next, patch };    // 首帧/切图仍全量
```

- 稳态挂机流量从 48KB/次 → **0**；战斗中只回 entities 里动了的那几个。
- 前端已有 epoch 机制（localEnemies），patch 语义与现有代码同构。
- `forceFullSync`：切图/sys 命令/前端显式请求时置位。

### O2. 写库降频（省 C3，一行配置）
plugin_state 是"崩溃恢复用"的快照，不需要每帧落盘：

```ts
// 现状：每 tick await setPluginData(...)（同步阻塞在请求路径上）
// 改为：脏标记 + 定时落盘
markDirty(scope);
// 每 2~5s（或 N 个脏 tick）才真正 UPSERT；退出/切图/结算时 flush
```

- 玩家刷新最多丢 2-5 秒进度（对动作小游戏可接受，游戏本来就有"退出结算"）。
- stateJson 的 UPDATE 同理：writeback 变化本来就是低频事件，可直接挂脏标记。
- **进一步**：稳态无变化时（配合 O1）连脏标记都不设 → 挂机时写库归零。

### O3. 动态降频（省 C1/C6，自适应）
按游戏活跃度分档 tick：

| 场景 | SEND_MS | 触发条件 |
|---|---|---|
| 活跃（有输入/战斗中） | 100ms | dx/dy≠0、有攻击目标、3s 内有交互 |
| 挂机（无输入无战斗） | 500ms~1s | 3s 无输入且无敌怪接战 |
| 后台标签页 | 0（停发） | `document.hidden`（已有） |

前端 5 行代码；后端 O1 生效后，低频 tick 的响应也是空 patch，双保险。

### O4. sys_* 慢命令与帧 tick 分道（省 C5）
sys_brain（LLM 1-5s）和帧 tick 抢同一把串行锁 → AI 决策期间游戏帧被堵。
拆两把锁（或慢命令完全不走锁）：

```ts
// tick.ts
const fastLock = withSessionLock(sessionId, ...)   // 帧 tick / 移动 / 技能
const slowLock = withSlowLock(sessionId, ...)      // sys_brain / sys_chat / 商城生成
```

- 慢命令的 chatResult 已经通过 plugin_state 回流，不需要和帧 tick 串行。
- **注意**：两者都会写 plugin_state → 保留"写库互斥"（fastLock 内的 UPSERT 与 slowLock 的最终 flush 仍要互斥），只是不让慢命令占着帧锁。

### O5. 长 连 接 替 代 轮询（省 C6/C7，中期）
WebSocket（宿主已持有 iframe 通道，天然可以升级）：

```
iframe ──ws──► 宿主 wsHub ──内部队列──► /plugin/tick（保持现有后端不动）
```

- 宿主 wsHub 聚合 10Hz tick 为内部调用（去掉 HTTP 头开销）；
- 断线由 ws 重连语义处理（替代 failStreak 探测）；
- 后端路由零改动（wsHub 只是另一个"宿主"）。
- 收益相对 O1-O4 小（同源 HTTP/1.1 keep-alive 下头开销不大），放中期。

### O6. 二进制/压缩传输（远期，通常不必要）
48KB JSON → msgpack + gzip ≈ 6-10KB。在 O1 做完后增量 patch 本来就小，此项收益锐减；
仅当出现"大规模同屏实体"类插件时再考虑。

## 五、"更好的机制"——按插件形态分流（架构级答案）

高频 tick 不是错的，**错的是它是唯一通道**。按游戏形态分三种协议：

### P1. 实时动作型（野外生存 / 假人对打）—— 保留现有 tick
- 确实需要 10Hz 权威模拟。
- 施加 O1-O4 后，成本可控：挂机归零、战斗增量、写库降频。

### P2. 回合/指令型（卡牌、种田、经营、RPG 对话选段）—— **指令-结算协议**
```
iframe ── postMessage({action:'play_card', card:xx}) ──► 宿主 ──► POST /plugin/action
                                                              └─ 后端结算一次，返回完整结果
```
- 无轮询：状态只在玩家出招时变化，通信量 = 玩家操作次数。
- 插件 manifest 声明 `interaction: "turn-based"`，宿主不启 tick 镜像。
- **实现成本极低**：`/plugin/tick` 已经支持任意 action——所谓回合制协议就是"前端不发 tick"而已。真正要做的只是：
  1. manifest 加个声明字段；
  2. ScenePlay 按 `interaction` 类型决定是否启动 tick 代发循环（现在循环在插件前端自己手里，其实只需插件模板提供一个"回合制模板"，天然不发 tick）；
  3. 宿主在无 tick 时也不需要做任何事。

### P3. 通知/挂机型（宠物养成、离线收益、成就推送）—— **事件推送协议**
```
后端 ──事件产生──► 存队列/直接写 plugin_data
前端 ──低频轮询(30s~5min) 或 宿主 ws 推送──► 拉取增量
```
- 通信量趋近于零；数据一致性由后端事件保证。
- 适合"AI 角色主动给玩家发短信"这类场景：**AI 决策在后端定时器里跑**（而非前端 tick 唤醒），产生短信 → 落 plugin_data → 前端低频拉取。
- 这也是短信功能未来最合理的形态：现在"玩家发短信 → 前端 P0 唤醒 LLM"是对的；但"AI 主动发短信"若靠前端 tick 心跳驱动，就是 P3 反面教材。

### 决策表

| 你的插件是... | 用哪个协议 | tick 频率 |
|---|---|---|
| 实时动作/射击/走位 | P1（tick，加 O1-O4） | 10Hz 活跃档 |
| 回合制/策略/卡牌 | P2（action-结算） | 0 |
| 挂机/通知/异步养成 | P3（事件推送） | 0（拉取 30s+） |

## 六、推荐落地顺序

| 阶段 | 内容 | 预期收益 | 改动面 |
|---|---|---|---|
| **第一步** | O2 写库降频（脏标记+2s 落盘） | 写库 -90% | tick.ts ~20 行 |
| **第二步** | O1 增量回传（304 语义） | 挂机带宽/序列化 → ~0 | tick.ts diff + 前端判空 |
| **第三步** | O3 动态降频 | 挂机请求 -80% | 插件 App.vue ~10 行 |
| **第四步** | O4 慢命令拆锁 | sys_brain 不再堵帧 | tick.ts 锁拆分 |
| **第五步** | P2/P3 分流协议 + 插件模板 | 新插件按需选型 | manifest + 模板 |
| 远期 | O5 WebSocket | 断线体验 | 宿主 wsHub |

### 一步验证基准（动手前先量化）
改之前先测三个数，避免无的放矢：
1. 单会话稳态：`POST /plugin/tick` 的 P50/P95 延迟与响应字节数（宿主日志已带 `- 48577` 字样）；
2. 多会话（3-5 个同时）下 SQLite 写锁竞争情况（观察 tick P95 抖动）；
3. sys_brain 期间帧 tick 的 P99 延迟（验证 C5 影响）。

## 七、一个重要的"不要做"

- **不要把游戏逻辑搬回前端**（"前端自己跑，只在退出时上报"）——这会丢掉权威状态/防作弊/多端一致三大收益，是开倒车。
- **不要用 WebSocket 重写整条链路**来"顺便"解决轮询问题——O1/O2 已拿走 90% 成本，ws 的边际收益主要在断线体验。
- **不要让 diff 变成新协议负担**：O1 的 patch 只用于传输优化，前端合并语义必须是"整包替换 or 逐字段覆盖"二选一且全链路一致，避免出现"半新半旧 state"。
