## 0. 一句话结论

**给后端加一个 MCP endpoint，让本机的 AI agent（ZCode / workbuddy）用工具调用的方式即时操控游戏世界**；
不碰前端↔后端的实时同步链路（那是 v2 O1~O4 已经解决的事）。

---

## 1. 这份设计要解决什么

原始需求（`插件的网络通信机制_v3.me.md`）列的是一串「即时交互能力」：

- 技能特效是否即时清除
- 连续点击技能 / 连续点击物品加血时，特效是否即时清除、能不能走动、会不会卡顿
- 野怪被杀是否即时清除
- 技能冷却是否正常（快速连点 1/2/3，以及间隔 1s 依次点 1/2/3）
- 其他即时交互能力

**先分清这批需求归谁管**，这是 v3 设计的起点：

| 需求 | 归属 | 结论 |
|---|---|---|
| 特效即时清除 / 连点不卡顿 / 技能冷却 / 野怪死亡即时消失 | **前端↔后端 tick 链路** | 属 v2 范畴。实测结论：**修复前有真 bug，已修**（见 §4） |
| **AI agent 也要能改游戏世界**（这是 v3 新增的部分） | **AI 接入面** | 现有架构下 AI 只能靠改 DB / 调内部接口，缺一个正规、受控、可审计的入口 → **MCP endpoint** |

所以 v3 的标题「MCP 接入层」指的不是「用 MCP 重做即时交互」，而是
**在修好即时交互之后，再给 AI 开一个正规入口**。

---

## 2. 定位：谁连谁

| 场景 | client | server | 结论 |
|---|---|---|---|
| **A. AI 操控游戏**（本设计） | AI agent（ZCode / workbuddy，本机） | 60002 后端 `/plugin/mcp` | ✅ MCP 的本职：工具调用 |
| B. 前端↔后端实时同步 | 插件 iframe → 5175 宿主 → 60002 | — | ❌ 不需要 MCP，tick 链路已覆盖 |

### 为什么 B 不走 MCP（红线）

v2 已经论证过「不为边际收益动传输层」。把 MCP 用来做前端实时同步，等于**把已搁置的 T4 SSE 换个协议外壳**，坑一个不少：

- iframe 拿不到 JWT → 长流开不了，还要绕宿主 5175 中继 postMessage；
- 多背一层 JSON-RPC 封装与**强制 header 校验**（`MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name`，body↔header 不一致必须 400 `-32020`）；
- 而现架构下活跃档的端到端延迟已经 ≤100ms（O1 增量回传），**换通道换不来延迟收益**。

一句话：**MCP 解决的是「AI 需要一个受控入口」，不是「延迟不够快」**。

## 3. 规范取舍：2026-07-28 + 手写薄层

MCP 规范基线取 **2026-07-28**（当前最新版）。几条对本设计有决定性影响的条款：

| 条款 | 内容 | 对设计的影响 |
|---|---|---|
| 传输模型 | 单一 endpoint，每条 JSON-RPC 消息一次 POST，响应为 JSON 或 request-scoped SSE | 实现简单：60002 同端口一个 `/plugin/mcp` 路由 + POST handler |
| **GET 长流已移除** | 删除 GET stream endpoint 与协议级 session（`Mcp-Session-Id`） | ❌ 不能靠「开一条 GET SSE」做推送；旧 client 的 GET/DELETE → 405 |
| server 主动通知 | 仅剩 `subscriptions/listen`（POST 发起，响应为长期 SSE 流） | 一期不依赖；二期若要 world-change 事件流再上（M5） |
| server 不得发独立 request | sampling / elicitation 改为 MRTR（`InputRequiredResult`） | 一期 tools 无需反向交互，不涉及 |
| 强制 header | `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name` 必填；body↔header 不一致 → 400 `-32020` | 协议层单独成模块（见 §6.1） |
| 安全 | MUST 校验 Origin；SHOULD 鉴权；本地服务 SHOULD 只绑 127.0.0.1 | 本机 agent → 绑回环 + 复用全局 JWT + Origin 默认全拒 |
| 旧版兼容 | 旧 client（≤2025-11-25）的 GET / DELETE / Session-Id：405 / 405 / 忽略 | 照做即可兼容老 client |

### 为什么手写薄层而不用官方 TS SDK

官方 SDK 的 transport 实现可能落后于 2026-07-28（仍带 session / GET stream 行为就**不符规范**）。
而本项目需要的只是「一个路由 + header 校验 + JSON-RPC 分发」，手写薄层成本极低，
**绝不能为了迁就 SDK 而引入过时语义**（那就变成「用 MCP 2026-07-28 的名字行 2025-03-26 的事」）。

实现见 `src/lib/mcp/protocol.ts`（协议层，约 240 行）+ `src/routes/plugin/mcp.ts`（路由层）。

## 4. 设计中最关键的一条：状态必须是同一份

这是整份设计**最容易做错、错了就全盘失效**的地方，也是 v3 相对 v2 最实质的增量。

### 4.1 问题的来源

entry 的 `handle_action` 是**无状态**的：每次请求拿传入的 state 重建、只推进一次 step。
因此「权威状态」必须由**宿主**保管。修复前的架构里（v2 §3.5 之前），权威状态只在 DB：

> MCP 用 `kill_mob` 杀掉一只怪 → 工具返回成功 →
> 下一个 tick 从 DB 读到工具写之前的状态（那只怪还活着）→ **怪复活了**。

而且这个症状在修复前**更严重**：DB 落盘被 O2 节流到 2s 一次，世界推进速率直接掉到 **0.36Hz**（= 落盘速率），
CD 递减慢 2.7 倍、野怪 AI 变慢、死亡渐隐卡住、「玩家已贴近野怪但 attack 说附近没有敌人」。
根因与实测详见 v2 §3.5 与 `md/test/toonflow-field-survival/即时交互测试报告_2026-11-12.md`。

### 4.2 设计决定：内存态是权威，DB 是快照

```
        ┌────────────────── 内存态（权威，进程内 Map）──────────────────┐
        │  key = userId:sessionId:pluginId                            │
        │  每次请求都更新；进程重启后从 DB 快照冷启动                    │
        └───┬──────────────────────────────────────────────┬───────────┘
            │ 读（命中内存态就不查 DB）                    │ 写（每次请求）
            ▼                                              ▼
      entry.handle_action                          内存态立即更新
      （拿 state 重建、推进一次）                        │
                                                       │ 按 O2 节流（2s）落快照
                                                       ▼
                                                 t_plugin_session_data
                                                 （仅供崩溃/刷新恢复）
```

由此推出四条**硬性要求**（缺一条就会出现「AI 写的状态被 tick 覆盖」）：

| 要求 | 落地方式 |
|---|---|
| MCP tool 必须**读内存态**，不查 DB | `getHotPluginState(scope)`（M2-5：读操作免锁） |
| MCP tool 写完必须**更新内存态** | `setHotPluginState(scope, resultState)`（每次请求都更新） |
| MCP tool 与 tick 必须**共用同一把会话串行锁** | 锁注册表下沉到 `PluginStateExecutor`（M2-2） |
| scope 键必须与 tick 一致 | `userId:sessionId:pluginId`，统一由 `pluginScopeKey()` 派生（M2-4） |

### 4.3 落地方式：抽公共函数，而不是复制粘贴

最容易出事的写法是「MCP 路由里另写一套读 DB → 调 entry → 写 DB」。所以设计上强制抽一层：

```
src/lib/plugins/PluginStateExecutor.ts
  export async function executePluginActionWithState(opts)
      读内存态(miss→DB→legacy迁移→回灌) → executePluginAction →
      宿主消费(writeback/结算奖励) → 写内存态 → forceSync 判定 → O2 节流落盘
      opts.lock: "fast"(默认) | "slow" | "none"(调用方已持锁)

src/lib/plugins/PluginExecutionContext.ts
  export async function preparePluginExecutionContext({userId, sessionId, pluginId})
      会话加载 → stateJson 解析 → manifest/动态卡/角色/世界名/世界书 → PluginGameContext
```

**tick 路由与 MCP 路由调的是同一个函数**，且 lock 注册表只有一份。
这是「防 clobber」唯一的可靠做法——靠约定不靠自觉。

### 4.4 附带收益

- **forceSync 语义自然成立**：MCP tool 属「非 tick 命令」→ 判定下沉到共享层后，工具返回时状态必定已落库，
  不被 O2 的 2s 节流吞掉（这是验收项 1 的前提）。
- **O1 增量回传不受影响**：tick 的「状态无变化则回 state:null」由共享层按 O2 记账判定，行为零变化（R/T 回归证明）。

## 5. 工具设计：能转发就不重写

权威游戏逻辑在 `entry.ts`（运行时是 esbuild 编译出的 `entry.js`）。
**MCP 层绝不直接改 state** —— 否则绕过经验/掉落/任务计数的权威结算。

| tool | 类型 | 落点 | 权威路径 |
|---|---|---|---|
| `query_state` | 读 | `readPluginStateSnapshot()`（内存态，免锁） | 只读快照，不执行 entry |
| `kill_mob` | 写 | `executePluginActionWithState(action="attack", {targetId})` | 与玩家点击普攻**同一条**结算链 |
| `clear_effect` | 写 | `action="ai_clear_vfx"`（entry 新增） | 权威 `s.vfx` 移除 |
| `spawn_entity` | 写 | `action="ai_spawn"`（entry 新增） | 与 `spawnWave` 同一条 `makeEntity` 构造链 |
| `plugin_events_push` | 写 | 直调既有 `pushPluginEvent()` | 复用 P3 事件队列 |

**错误分层**（面向 AI 的可用性）：

- **协议级**（缺参、未知 tool、未知方法）→ JSON-RPC error（`-32602` / `-32601`），带结构化 data；
- **业务级**（目标不存在、太远、没有活局、图鉴外类型）→ `isError: true` 的 tool result，
  文本说明**为什么失败、下一步怎么改**（例：「目标 X 不存在或已死亡（可用 query_state 查看当前存活敌人）」）。

| 改动 | 说明 |
|---|---|

### 6.3 安全边界

| 项 | 措施 |
|---|---|
| 网络可达性 | 仅回环（`req.socket.remoteAddress` 判定），非本机 → 403 |
| 鉴权 | 复用 app 级 JWT 中间件（`Authorization: Bearer`），无 token → 401 |
| Origin | 默认**拒绝一切**带 Origin 的浏览器请求（防 DNS rebinding）；需放行用 env `MCP_ALLOWED_ORIGINS`（逗号分隔） |
| 错误泄露 | 业务错误只回可读文案，不回堆栈；调试细节走服务端日志 |

> ⚠️ token 即会话操作权，**不要把带 token 的 curl 贴到共享环境**。

## 7. 验收（量化）

见 `v3.md` §7 的 8 条验收标准；实测结果见测试报告（49 项断言：协议 12 + 握手 4 + tools 11 + M4 3 + R 6 + T 12，全绿）。

最关键的三条：

| # | 验收项 | 判据 | 实测 |
|---|---|---|---|
| 2b | **无状态覆盖** | tool 写入后连续 5 个帧 tick，状态变化仍存在（怪不被复活） | ✅ 被杀怪 5 帧均未复活 |
| 2 | **玩家可见即时** | 写 tool 返回后 ≤2 个帧 tick（≤250ms）玩家可见 | ✅ 第 1~2 帧内渐隐启动 |
| 3 | **并发安全** | 并发写 tool + 10Hz tick 压测，state 无丢失/回退 | ✅ 12 并发 kill + 持续 tick：0 次 5xx、0 次 tick 回退，kills 增量逐一吻合 |

## 8. 明确不做（边界）

| 项 | 原因 |
|---|---|
| 用 MCP 做前端↔后端实时同步 | §2：现有 tick 链路已覆盖，活跃档 ≤100ms |
| 改用 WebSocket transport | §3：官方规范已移除 GET 长流；自定义 transport 收益为边际（调研见 `pre.mcp.md` 的对比表） |
| MCP 层直接改 state | §5：绕过 entry 权威结算（经验/掉落/任务计数会漏） |
| 二进制协议 / 字段级 patch | v2 红线 |
| 协议级 session / GET SSE 长流 | 2026-07-28 已移除；推送走 `subscriptions/listen`（M5 搁置） |
| 多进程部署下的内存态共享 | 当前单进程；多实例部署时必须改 Redis 或 DB 读穿（§4.2 末尾已注明） |

## 9. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| MCP 路由另写一套状态读写 | AI 写的状态被 tick 覆盖（怪复活） | §4.3 强制抽公共函数；验收项 2b 盯着 |
| 后端改多进程/多实例 | 内存态不共享 → 「即时写入」保证失效 | 已写明；届时改共享存储 |
| SDK 版本落后 2026-07-28 | 引入过时语义（session / GET stream） | §3 手写薄层，不引入 SDK 依赖 |
| MCP endpoint 暴露到非本机 | AI token 泄漏 | §6.3 回环限定 + token + Origin 三重 |
| entry.js 是编译产物被当源码改 | 改动不生效 / 被下次编译覆盖 | 只改 `entry.ts` → esbuild → cp 安装副本（v2 §3.5.2 铁律） |

| 5 | kill_mob 假 id 只回「附近没有敌人」 | 可用性 | 空分支先判 targetId，给精确原因 |
| 6 | `v3.design.md` 只有 1 行标题就入库（内容全在 v3.md） | 文档缺陷 | 补齐设计说明 + 两文档分工约定 |

> 压测中还观察到一个「**游戏逻辑正确但测试设计不当**」的现象：30 只怪刷在玩家 1m 处，10Hz 围殴 ~1s 团灭玩家 →
> `phase=over` 后一切渐隐/结算冻结。测试改为 `revive` 前置 + 刷在 3.5m（可 kill 但离攻击范围还有 ~1.4s 路程）。

## 11. 收益

### 11.1 面向用户（玩家）：即时交互的三个真 bug 被修掉

这些是 v3 立项时顺手挖出来的——「AI 接入面」的需求暴露出底层链路本就有问题：

| 症状（修复前） | 修复后 | 收益 |
|---|---|---|
| 技能 CD 归零要 **6.5s**（设计 2.4s） | **2.8s** | 冷却节奏回到设计值 |
| 野怪死亡后渐隐**卡住**，尸体不消失 | 4 帧内移除（0.4s） | 战场画面干净 |
| 玩家已贴近野怪，点普攻说**「附近没有敌人」** | 带实时位姿即命中 | 战斗手感正常 |
| 世界推进只有 **0.36Hz** | **10Hz** | AI 行为、动画、掉落节奏全部正常 |

> 根因是同一个：**DB 落盘节流（O2）把「未落库的中间状态」整体丢弃**，而 entry 的 `handle_action` 无状态
> → 每请求从 DB 读 = 只能以落盘频率推进世界。修法是**内存态权威、DB 退化为快照**。

### 11.2 面向 AI agent：有了正规、可控、可审计的操作入口

| 能力 | 之前 | 现在 |
|---|---|---|
| AI 改游戏世界 | 只能改 DB / 调内部接口（绕权威结算、易覆盖状态） | `tools/call` 走 entry 权威结算链，与玩家点击**同一路径** |
| 感知世界 | 读 DB 快照（最多滞后 2s，会误判「怪还活着」） | `query_state` 读内存态，**零滞后** |
| 写入的持久性 | 不确定（可能被下一个 tick 覆盖） | 非 tick 命令 → forceSync，**返回即落库** |
| 并发安全 | 无（与 10Hz tick 竞争） | 与 tick **共用同一把会话锁**，压测零丢失 |
| 错误可读性 | — | 业务失败给「为什么失败 + 下一步怎么改」，协议级回 JSON-RPC error |

### 11.3 面向工程：结构收益（这次重构顺带拿到）

1. **tick.ts 净减 106 行**（305 → 199）：状态读写、writeback 消费、锁与 O2 记账全部下沉到共享层，
   路由只剩「编排 + 响应」。同一时刻 MCP 路由也变薄了。
2. **一份状态真源**：`PluginStateExecutor` + `PluginExecutionContext` 让「插件状态怎么读、怎么写、
   怎么落盘、怎么加锁」只有一处实现 —— 未来再加第三个写入方（比如未来的 `subscriptions/listen`）
   不会再复制第二套状态读写。
3. **回归资产可复用**：三套断言脚本（R1~R5 / T1~T3 / MCP 31 项）成为常驻护栏，
   以后任何改动都能一键验证「行为没变」。
4. **部署踩坑写进文档**：entry.js 是编译产物、本地必须 `npm run local` 起（`env/.env.dev` 路径为空会导致插件加载失败）。

### 11.4 投入产出小结

| | 投入 | 产出 |
|---|---|---|
| 后端 | 新增 ~1241 行 + tick.ts 重构 | MCP endpoint + 共享执行层 + 可复用回归护栏 |
| 插件 | entry.ts +98 行 | 3 个权威 action（AI 可用）+ 3 个玩家侧真 bug 修复 |
| 测试 | 3 套脚本 / 49 项断言 | 协议合规、可审计、并发安全、零覆盖的**量化证据** |
| 文档 | v2 §3.5 + v3 design/v3/报告 | 后续加写入方时有明确的设计与验收模板 |

**净收益**：AI 获得了正规入口，玩家侧三个即时交互 bug 被修复，tick 路由瘦身 1/3，
并留下 49 项断言作为后续改动的安全网。
