## 0. 一句话结论

- MCP 在本项目的角色：**AI agent ↔ 插件后端的工具调用协议**（client = AI agent，server = 60002 后端）；
- **不做**前端↔后端的实时状态同步——现有 10Hz tick + O1 增量回传活跃档 ≤100ms，已覆盖"即时"体验；
- "即时"的验收定义：**tool 返回时状态已落库，玩家下一个 tick（活跃档 ≤100ms）可见**；
- 关键新风险：MCP tool handler 必须与 tick 走**同一把会话串行锁**，否则并发 clobber plugin_state；
- **前置依赖（2026-11-12 新增，见 §5.1）**：MCP 必须读写**同一份内存态**，
  否则 AI 写完的状态会被下一个 tick 从 DB 读到的旧快照覆盖（「AI 刚杀掉的怪被 tick 复活」）；
- 规范基线：**MCP 2026-07-28 版**——GET 独立 SSE 长流已移除，server 主动通知只剩 `subscriptions/listen` 一条路（一期不依赖它）。

## 2. 为什么不用 MCP 做前端实时同步

v3 草案里的三个"即时"项，在现架构下的真实延迟：

| "即时"项 | 现架构路径 | 延迟 | 需要新通道吗 |
|---|---|---|---|
| 野怪被杀（玩家攻击） | tick 内结算 → O1 回传 | 活跃档 ≤100ms | ❌ |
| 技能特效清除 | 前端本地特效生命周期 | 0（与网络无关） | ❌ |
| 后端/编排器改状态（AI 杀怪） | 玩家下一个 tick 拉到 | 活跃 ≤100ms / 挂机 ≤1s | ❌ |
| 页面隐藏档 | 停发 tick | 分钟级 | — 用户没在看屏幕，无体验意义 |

结论：与 v2 §8 搁置 T4 SSE 同一逻辑。**用 MCP 重做这条链路 = 把已搁置的 T4 换个协议外壳，坑一个不少**（iframe 无 JWT 开不了长流、宿主 5175 中继 postMessage），还多背一层 JSON-RPC 封装与强制 header 校验。

## 3. 规范依据（MCP 2026-07-28）

已联网核实（官方 spec，链接见文末），对设计有直接影响的条款：

| 条款 | 内容 | 对本项目的影响 |
|---|---|---|
| 传输模型 | 单一 MCP endpoint，每条 JSON-RPC 消息一次 POST；响应为 JSON 或 request-scoped SSE | 实现简单：60002 同端口一个 `/mcp` 路由 + POST handler |
| **GET 长流已移除** | 2026-07-28 删除 GET stream endpoint 与协议级 session（`Mcp-Session-Id`） | ❌ 不能靠"开一条 GET SSE"做推送 |
| server 主动通知 | 仅剩 `subscriptions/listen`（POST 发起，响应为长期 SSE 流） | 一期不依赖；二期若需要"world-change 事件流"再上 |
| server 不得发独立 request | sampling/elicitation 改为 MRTR（嵌入 `InputRequiredResult`） | 一期 tools 无需反向交互，不涉及 |
| 强制 header | `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name`（REQUIRED）；body↔header 不一致必须 400（`-32020 HeaderMismatch`） | 服务端校验清单，见 §7 |
| 安全 | MUST 校验 Origin；SHOULD 鉴权；本地服务 SHOULD 只绑 127.0.0.1 | client 全在本机 → 绑 localhost + bearer token |
| 旧版兼容 | 旧 client（≤2025-11-25）的 GET / DELETE / Session-Id：405 / 405 / 忽略 | 服务端按此处理即可兼容老 client |

**SDK 注意**：官方 TS SDK 的 transport 实现版本可能落后于 2026-07-28（如仍带 session / GET stream 行为）。实施时先核对 SDK 支持的 protocolVersion；若不符，JSON-RPC-over-POST 的手写薄层代价很低（一个路由 + header 校验），可自行实现。

## 4. 架构与数据流

```
AI agent（ZCode / workbuddy，本机）
  │  MCP Streamable HTTP：JSON-RPC over POST（单 endpoint http://127.0.0.1:60002/mcp）
  ▼
60002 后端 MCP 模块（新增，与 tick.ts 同进程）
  │  ① 校验 Origin + token + 强制 header（MCP-Protocol-Version / Mcp-Method / Mcp-Name）
  │  ② tools/call → 按 tool 名分流
  │  ③ 【关键】写操作与 tick 走同一把会话串行锁（fastLock 族，见 §5）
  │  ④ 【关键】读写与 tick **同一份内存态**（见 §5.1），不直接查 DB
  │  ⑤ 权威逻辑：转发 entry.js handle_action（不重写游戏逻辑）
  │  ⑥ 内存态更新（立即）+ DB 快照落盘（按 O2 节流，非 tick 命令 forceSync）
  ▼
tool 返回（此刻状态已在内存态生效并落库）
  │
  ▼
玩家侧：插件前端下一个 tick（活跃档 ≤100ms）拉到新状态并渲染
```

**"即时"的定义就此闭环**：MCP 只保证「写入即时生效」；「玩家可见」复用既有 tick 链路，**前端零改动**。

## 5. 并发安全（关键新风险）

v2 O4 已拆 fastLock（帧 tick）/ slowLock（sys_* 慢命令）。MCP 是第三类写入方，规则：

| MCP tool 类型 | 锁策略 | 说明 |
|---|---|---|
| 写操作（kill_mob / spawn_entity / clear_effect…） | **必须走会话串行锁**（与 tick 同锁族） | 若不走锁，MCP 写入与 10Hz tick 并发 = v2 未覆盖的 clobber 源；O2 的节流记账兜不住乱序写 |
| 读操作（query_state…） | 无锁直读 | 只读不改状态；容忍读到 tick 中间态（AI 感知场景可接受） |
| 慢操作（未来接 LLM 决策类 tool） | slowLock | 与 sys_* 同族 |

**落盘约定**：MCP 写 tool 按"非 tick 命令"路径走 writeback——tick.ts 既有规则里非 tick 命令天然 forceSync，tool 返回时状态必定已落盘，不被 O2 的 2s 节流延迟吞掉；这是 §7 验收项 1 成立的前提。

### 5.1 状态来源：必须与 tick 共享同一份内存态（2026-11-12 新增，必读）

**问题**：v2 §3.5 修复前，插件状态是**只存在于 DB** 的（每请求读 DB、节流落盘）。
在那个架构下，MCP tool 写入 DB 后，**下一个 tick 会从 DB 读到 tool 写之前的状态**——
若 tool 的写没有立刻落库（DB 快照滞后 2s），就会被旧快照**整个覆盖**：

> 典型症状：AI 用 `kill_mob` 杀掉一只野怪 → tool 返回成功 →
> 下一个 tick 读 DB 拿到 2s 前的快照（那只怪还活着）→ **怪复活了**。

**修复后（v2 §3.5.2 已落地）**：`PluginSessionDataService` 提供了内存态
（`getHotPluginState` / `setHotPluginState`），**内存态是权威，DB 只是快照**。

**因此 MCP 的硬性要求**：

| 要求 | 说明 |
|---|---|
| **MCP tool 必须读内存态，不查 DB** | 复用 `getHotPluginState(scope)`，与 `/plugin/tick` 同一来源 |
| **MCP tool 写完必须更新内存态** | 复用 `setHotPluginState(scope, resultState)`；DB 落盘可继续按节流（但 tool 是非 tick 命令 → forceSync 立即落盘） |
| **MCP tool 与 tick 必须共用同一把锁** | 否则两个写入方各自基于旧快照构造 state，互相覆盖（§5 的锁规则） |
| **MCP 的 scope 键必须与 tick.ts 一致** | `userId:sessionId:pluginId`（`hotKey` 的构造方式），否则读不到同一份内存态 |

**实现建议**：MCP 模块不要自己实现状态读写，直接复用
`PluginSessionDataService` 的热态 API + `tick.ts` 里已有的锁与 forceSync 判定逻辑，
把「读内存态 → 执行 entry → 写内存态 → 落盘」抽成一个公共函数（如
`executePluginActionWithState(ctx, action, params, scope)`），让 tick 路由与 MCP 路由都调它 ——
**避免两处各自实现一套状态读写逻辑**（这是最容易出 clobber 的地方）。

**并发模型提醒**：内存态是**单进程**内存（后端 `tsx src/app.ts` 单进程运行）。
若将来后端改成多进程/多实例部署，内存态不共享 → 必须改为共享存储（Redis）或 DB 读穿，
MCP 的「即时写入」保证会随之失效。**这一条要写进部署文档。**

## 6. 首批 Tool 清单

原则：**能转发既有 handle_action 的绝不重写逻辑**（权威游戏逻辑在 `entry.ts`，
运行时用 esbuild 编译出的 `entry.js`）。

| tool | 类型 | 实现 | 说明 |
|---|---|---|---|
| `query_state` | 读 | 读**内存态**（`getHotPluginState`）摘要 | 野怪 / 特效 / 玩家 / phase；供 AI 感知世界 |
| `kill_mob` | 写 | 转发 handle_action（与攻击结算同路径） | mobId 必填；结算走权威逻辑 |
| `clear_effect` | 写 | 转发 handle_action 或清 effects 列表 | effectId / all |
| `spawn_entity` | 写 | 转发 handle_action | entityType / 坐标；复用 ENGINE_NON_MOB_ENTITY_TYPES 校验 |
| `plugin_events_push` | 写 | 直调既有 `pushPluginEvent()` | 复用 P3 事件队列，AI 主动短信场景 |

（首批以插件 `entry.ts` 实际暴露的 action 为准，实施时对齐；上表为形态示例。）

> ⚠️ **读操作也要走内存态**：`query_state` 若查 DB，会读到最多 2s 前的快照 ——
> AI 拿到的世界信息会滞后（以为怪还活着，其实刚被杀）。见 §5.1。

## 7. 验收标准（量化）

| # | 验收项 | 判据 |
|---|---|---|
| 1 | 写 tool 落库即时 | tool 返回时 `plugin_state` 已更新（updatedAt 当次变化） |
| 2 | **玩家可见即时** | 写 tool 返回后，玩家在 **≤2 个帧 tick（≤250ms）** 内看到状态变化。<br/>依据：世界推进实测 10Hz（v2 §3.5.3）→ 2 tick = 200ms，留 50ms 余量。<br/>⚠️ 前提：v2 §3.5 的内存态修复已生效（R1 断言通过）；若世界推进 <8Hz，本项直接判 FAIL |
| 2b | **无状态覆盖** | tool 写入后**连续 5 个帧 tick**，该状态变化仍然存在（不被 DB 旧快照覆盖）。<br/>这是 §5.1 的核心断言：AI 杀掉的怪不能被 tick 复活 |
| 3 | 并发安全 | MCP 写 tool 与 10Hz tick 并发压测（如 10s 内 50 次 kill_mob + 持续 tick），state 无丢失 / 回退 |
| 4 | 协议合规 | 缺 `MCP-Protocol-Version` header → 400；header↔body method/name 不一致 → 400 `-32020` |
| 5 | 环境安全 | 服务只绑 127.0.0.1；无 token 请求 → 401 |
| 6 | 旧 client 兼容 | GET /mcp → 405；带 `Mcp-Session-Id` → 忽略且正常响应 |
| 7 | **前置回归** | v2 §3.5.5 的 R1~R5 五条断言全部通过（`test_regression.py`）——<br/>MCP 上线前世界推进速率必须是 10Hz 级，否则「即时」无从谈起 |

## 11. 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| MCP 路由另写一套状态读写 | AI 写的状态被 tick 覆盖（怪复活） | M2-1 强制抽公共函数；验收项 2b 盯着 |
| 后端改多进程/多实例部署 | 内存态不共享 → 「即时写入」保证失效 | §5.1 已写明；届时改 Redis 或 DB 读穿 |
| SDK 版本落后 2026-07-28 | 引入过时语义（session / GET stream） | M1-1 前先核对；不符就手写薄层 |
| MCP endpoint 暴露到非本机 | AI token 泄漏 | M1-3 只绑 127.0.0.1 + token |
| 前端 iframe 拿不到 JWT | （不适用）MCP client 是本机 agent，不走 iframe | — |

**外部依赖**：M1~M4 依赖 v2 §3.5 的内存态修复（✅ M0 已完成）；
M4 的端到端演示依赖真实 5175 宿主 + 60002 后端同时在线。
