> **本文档角色**：v3.1 **设计说明**——回答「为什么 HTTP tick 轮询必须被替换、新通道长什么样、为什么这样换」。
> 前序文档：`_v2.md`（tick 链路 + 内存态权威）、`_v3.design.md`（MCP 接入层）、
> `插件的网络通信机制.pre.mcp.md`（transport 调研）。
> 状态：**设计定稿，待实施**（2026-11-14）。
> 触发背景：局域网部署实测（ARM 盒 + WiFi）HTTP tick 轮询全面失守——
> 技能点击 10s+ 不触发、tick 推进掉到 1Hz、pluginData 全线超时（详见 §2）。

---

## 0. 一句话结论

**宿主 web ↔ 后端换成 WebSocket 全双工，并把「世界推进」搬进后端（服务端权威 tick 循环）**：
iframe ↔ 宿主维持 postMessage（本地零网络，不动）；HTTP `/plugin/tick` 路由保留为
回退通道与测试/MCP 通道；**entry.ts 零改动**（三桩纪律不破）。

一句话对比：

| | HTTP tick 轮询（现状） | WS 全双工 + 服务端 tick（v3.1） |
|---|---|---|
| 世界推进 | 每推进一步 = 客户端发起一次完整 HTTP 往返 | 服务端 10Hz 自推进，无往返 |
| 上行 | 每帧一条请求（含 CORS preflight 双倍） | pose 合并 latest-wins，≤10 条/秒小帧；动作即时单发 |
| 下行 | 空转也回全量（304 修复后空转 125B，但战斗仍 12KB+×10Hz） | 无变化不推；有变化推送（deflate 压缩）；慢消费者 latest-wins |
| 技能点击 | 与帧 tick 同队列排队（弱网 10s+） | 动作消息即时上行，下一个 tick 边界结算（≤100ms）+ ack 回执 |
| 可观测性 | 「点了没反应」无从得知 | click→queued→acked→applied 时间线（调试 HUD） |
| 弱网断线 | 请求堆积雪崩 | 自动回退 HTTP tick；重连后状态重同步 |

## 1. 为什么 v3.1 推翻 v2 的「不动传输层」红线

v2 当时的结论是「不为边际收益动传输层」，依据是**本地 127.0.0.1 实测活跃档端到端 ≤100ms**。
这个结论的前提——「带宽/延迟充裕」——在**部署形态**下不成立：

| 实测项（192.168.0.104 部署机，WiFi 客户端） | 数值 |
|---|---|
| ping RTT | 91~185ms（均值 124ms，抖动大）；空闲期复测 3~47ms |
| 一次 trivial 请求（/other/version）偶发 | **7.6s**（服务器事件循环被大包处理阻塞时的尖峰） |
| 110s 游戏会话累计传输 | **90.2 MB / 155 请求** |
| tick 推进速率 | 10Hz 设计 → 实测 ~1Hz |
| Network 面板 | 8+ 条 tick 同时 (pending)；pluginData 10s 超时刷屏 |
| 技能点击 | 点了 **数秒才触发，且看不到任何进行中迹象** |

2026-11-14 已落的止血修复（宿主在途丢弃帧 tick、后端 304 剥离 `s.tick`、gzip、大包超时 60s）
把空转下行压掉了 99%，但**轮询模型本身**没有变：每推进一步仍要一次完整 HTTP 往返，
玩家动作仍与帧 tick 共享同一条拥挤的请求通道。弱网下这不收敛。

**结论**：传输层升级的收益从「边际」变成「决定性」——红线修订，v3.1 立项。
同时必须守住两条不动：iframe↔宿主 postMessage（本地链路没有问题）、entry.ts（三桩纪律）。

## 2. 症状 → 根因对照（实测存证）

| 症状 | 直接根因 | v3.1 对应解法 |
|---|---|---|
| 技能点了几秒才触发 | 动作与帧 tick 共用 HTTP 队列；浏览器 6 连接被帧 tick 占满，动作排队 | §5.2 动作走 WS 独立上行 + 服务端 tick 边界结算 |
| 「不知道在干嘛」 | 无任何 click→结算 的可视路径 | §5.2 ack 时间线 + 调试 HUD |
| tick 掉到 1Hz | 每帧 tick 一次 HTTP 往返，RTT×2(preflight)+排队 > 100ms 预算 | §5.1 服务端自推进，无往返 |
| 下行打满 | 战斗时每 tick 全量 state ×10Hz（s.tick 每 tick 必变） | §5.3 无变化不推 + deflate + latest-wins |
| pluginData 超时刷屏 | 连接池被 tick 挤占，其它请求饿死 | WS 承载实时流后，HTTP 连接池还给低频请求 |
| 大包读取慢/失败 | 9.2MB 无压缩 × 轮询通道 | gzip 已落（9.2MB→6.75MB）；大包仍走 HTTP 一次性拉取（可缓存），不进 WS |

## 3. 目标与非目标

### 目标（量化验收，见 §7）

| # | 目标 | 判据 |
|---|---|---|
| G1 | 技能点击→结算确认延迟 | 局域网 ≤200ms；Chrome 弱网模拟（RTT 200ms/带宽 1Mbps）≤500ms |
| G2 | WS 激活后 HTTP tick 请求 | = 0（仅断线回退期间允许） |
| G3 | 下行流量 | 空转 ≤1 msg/s；战斗 ≤10 msg/s 且单条 ≤50KB（deflate 后） |
| G4 | 断线韧性 | 重连 ≤1s 完成状态重同步；断线期间自动回退 HTTP tick 不掉世界推进 |
| G5 | 触发可观测 | 调试 HUD 可见 click→ack 毫秒级时间线与当前队列状态 |
| G6 | 回归不变性 | R1~R5、MCP 49 项、v2-fx 61 项全绿（HTTP 路径行为零变化） |

### 非目标（明确不做）

- iframe↔宿主换通道：postMessage 是本地零网络调用，没问题不修；
- 改 entry.ts / 三桩同步：世界推进逻辑不变，只换「谁在什么时候调它」；
- 状态 delta / 二进制协议：v2 红线仍有效（先靠「无变化不推 + deflate」达标，不够再说）；
- 多人同屏广播：当前单玩家会话语义不变；
- 鉴权重做：复用全局 JWT（WS upgrade 走 query token，与分镜 WS 同模式）。

## 4. 架构：谁连谁、什么走什么通道

```
┌─────────────┐  postMessage（不变，本地零网络）
│  插件 iframe │ ──────────────────────────────▶ ┌──────────┐
│  (game.html) │ ◀──────────────────────────────  │ 宿主 web  │
└─────────────┘   tf_plugin_state / ack 时间线     └────┬─────┘
        │  ▲                                          │  ▲
        │  │ 玩家动作/位姿（iframe→宿主照旧）           │  │
        ▼  │                                          ▼  │
   【WS /plugin/realtime（新，全双工）】                     │
   up:  pose(合并 latest-wins) / action(带 actionId)        │
   down: sync(全量) / push(变化才推,deflate) / ack / ping   │
        │                                            ▼
        ▼                                    【HTTP /plugin/tick】
┌──────────────────┐   同一把会话串行锁   （回退通道：WS 断开时自动启用；
│ PluginStateExecutor│◀────共用───────  dev-host / MCP / 回归测试也走这里）
│  内存态（权威）     │
│  → O2 节流落 DB    │
└──────────────────┘
```

| 链路 | 通道 | 频率 | 内容 |
|---|---|---|---|
| iframe ↔ 宿主 | postMessage（**不变**） | 照旧（移动端 5Hz / 本地 10Hz / 挂机 1Hz） | `tf_plugin_tick{action,params}` / `tf_plugin_state` |
| 宿主 → 后端 up | **WS**（新） | pose ≤10 条/s（合并）；动作即时单发 | `pose` / `action{actionId,action,params}` |
| 后端 → 宿主 down | **WS**（新） | 无变化不推；变化 ≤10 条/s | `sync` / `push{state}` / `ack{actionId,...}` / `ping{ts}` |
| 宿主 ↔ 后端 | HTTP `/plugin/tick`（**保留**） | 仅回退期 | 与现状完全一致 |
| 后端 → DB | `t_plugin_session_data`（**不变**） | O2 节流 2s + forceSync | plugin_state 快照 |

## 5. 核心机制

### 5.1 服务端权威 tick 循环——世界推进搬进后端

这是 v3.1 的灵魂：**轮询模型里「世界推进」由客户端请求驱动；v3.1 改为由服务端定时驱动**。

```
TickDriver（后端，每会话一个）：
  条件：phase=playing 且 ≥1 个 WS 客户端在线
  每 100ms：
    1. 取 latestPose（WS pose 消息 latest-wins 缓存，见 5.3）
    2. executePluginActionWithState({action:"tick", params:{player: latestPose}, lock:"fast"})
       ★ 与 HTTP tick / MCP tools 共用同一把会话串行锁（v3 §4.2 硬性要求）
    3. 若 state 有效变化（O1b 口径）→ push 给该会话所有 WS 客户端
  无客户端在线 → 循环暂停（省 ARM 盒 CPU）；重连时 resync 恢复
```

为什么安全：

- 内存态本来就是权威（v2 §3.5 / v3 §4.2 已定）——tick 循环只是把「每 100ms 一次的
  entry 调用」从客户端发起改为服务端发起，**调用的函数、锁、落库策略全部复用**；
- HTTP tick 路由不删：回退期客户端仍按现状发——与 tick 循环由同一把锁串行，
  最坏情况是「循环推进一次 + HTTP tick 推进一次」交替，不会互相覆盖；
- entry.handle_action 依旧无状态、每次推进一步——**entry.ts 零改动**。

### 5.2 动作即时性与确认——「点了几秒才触发」的根治 + 「不知道在干嘛」的终结

```
玩家点技能
  iframe：立即本地预测（画指示区/技能图标反馈，不等服务器）＋ postMessage 动作
  宿主：WS 发 {type:"action", actionId:"a_169...", action:"skill", params:{...}}   ←≤RTT 上行
  后端：入会话动作队列（锁内串行）；**下一个 tick 边界（≤100ms）结算**
  后端：push 变化后的 state ＋ ack {actionId, ok, response:"源之力（空放）", serverTick, ts}
  宿主：把 ack 时间线回传 iframe（调试 HUD 显示；正式版仅 toast 失败原因）
```

要点：

- **动作与帧 tick 分离**：动作消息即时发出（不排队等帧 tick），帧 tick 消失（服务端自推进）；
- **actionId 全程追踪**：客户端生成单调 id，ack 对账 → 每次点击都有
  `click → sent → acked(applied/refused)` 三点时间戳，「不知道在干嘛」变成可量化数据；
- **本地预测 + 对账**：点击瞬间先给视觉反馈（指示区/图标闪烁），ack 回来后以服务端结果
  为准修正（命中/空放/冷却中）——手感与权威性兼得；
- 冷却中/无效目标等业务失败，ack 带 `ok:false + response` 文案，直接透出。

### 5.3 状态推送策略——把下行带宽压到「有变化才推」

复用并前移 O1b 口径（剥离 `tick/_tickAtMs/_tickDeltaMs/writeback` 后对比）：

- 每次 tick 循环推进后：`compareNow` 与「上次已推送」比 → **未变不推**（空转零下行）；
- 变了 → 推全量 state（`permessage-deflate` 压缩；JSON 文本压缩率 ~80%，12KB→~3KB）；
- 推送节流：同会话推送间隔下限 50ms（防御 tick 10Hz × 客户端消费慢的放大）；
- **慢消费者保护（latest-wins）**：每会话只保留「最新待推快照」，socket 忙/发失败即
  丢弃当前帧（下一帧必然更新），**绝不排队**——这是与 HTTP 模型最本质的区别之一；
- 心跳：无变化 ≥1s 推 `ping{ts}`（保活 + 实时 RTT 测量，喂给调试 HUD）。

### 5.4 连接生命周期与回退

```
建立：ws://<backend>/plugin/realtime?token=<jwt>&sessionId=&pluginId=
  → 后端 upgrade 校验（全局 JWT 中间件对 upgrade 同样生效，query token 模式与分镜 WS 相同）
  → Origin 白名单（8088 / 5175 / 本地 dev），其余拒绝
  → 客户端发 hello{lastTick?} → 服务端回 sync{全量 state, serverTick}
  → 宿主停掉 HTTP tick 循环（pluginTickPaused 语义复用），进入 WS 驱动

断线：
  → 宿主检测 close/error → 立即回退 HTTP tick（现有 handlePluginTick 路径原样启用）
  → 1s 指数退避重连（500ms/1s/2s/4s，上限 5s）
  → 重连成功 → sync 重同步 → 停 HTTP 回退

服务器重启：内存态丢 → hello 后从 DB 快照冷启动（现状语义不变）
服务降级：WS 握手失败（代理不支持/端口不通）→ 永久回退 HTTP 模式（现状行为）
```

回退通道是「现状代码原样保留」——已落地的止血修复（帧 tick 在途丢弃、O1b、gzip）
正是回退期的行为基线。**WS 挂了系统退化到今天已修好的状态，而不是退化到事故状态。**

### 5.5 安全与限流

| 项 | 措施 |
|---|---|
| 鉴权 | upgrade 阶段全局 JWT（query token）；hello 再校验 sessionId 归属 |
| Origin | 白名单：部署机 8088、本地 5175、localhost dev；默认拒绝 |
| 限流 | 上行 >50 msg/s 断开（防失控循环）；单连接只绑一个 scope |
| 泄露 | 与 HTTP 同口径：业务错误回可读文案 |

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| ARM 盒 perMessageDeflate CPU | 推送延迟上升 | ws 参数可关；先压测（12KB JSON deflate <5ms 量级，预计无虞）；必要时仅对 >8KB 消息启用 |
| 双 tick 源（WS 循环 + 回退期 HTTP tick）并发 | 状态竞争 | 同一会话串行锁天然串行（机制已在 v3 验证过）；回退期宿主停发帧 tick 即无双源 |
| 代理/网闸掐空闲 WS | 静默断线 | 心跳 1s 保活；close/error 即回退，用户无感 |
| express-ws 多实例部署 | 内存态/连接不共享 | 当前单进程；多实例时需粘性会话或外置 hub（v3 §8 已有同样注记） |
| 客户端旧版本（无 WS 支持） | 行为回退 | 服务端 WS 是纯增量路由；旧客户端继续走 HTTP，零影响 |
| tick 循环占用 ARM CPU | 世界推进变慢 | tick 本来就要跑（现在是客户端拉）；循环只在 phase=playing 且有连接时跑，挂机自动降频沿用 entry 内 `_dec` 折算 |
