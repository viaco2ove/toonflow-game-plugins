# 群聊功能
## 加个@角色的功能
##  然后我在群聊发了消息，npc 是怎么样的回复机制
群聊发消息后 NPC 的回复机制（现状链路）

text
你发消息 → sendPlayerMessage 落库
        → 给群里每个 AI 成员登记「待回复」
        → wakeAiForPlayerSms 立即逐个唤醒（不等 20s 心跳）
             ↓
每个 NPC 成员独立跑一次 LLM 决策（callBrainDetailed）
  - 在场用真实实体（位置/血量/周围环境进 prompt）
  - 不在场（切图/存档角色）构造「幽灵实体」纯回短信
  - 未托管也能回（被动应答不需要托管）
             ↓
决策输出带 message 字段 → 发到群里（校验：必须真在群里）
  没带 message → 该 NPC 这次选择不回，登记保留，20s 心跳再兜底
  闸门被占（LLM 单槽位）→ 1.5s 后重试，最多等 25s
所以你截图里「全部人 12 人」发一条，只有苏晚晴/赵大川回了，原因是组合效应：

12 个成员是串行抢同一个 LLM 闸门的，每个人都要等前一个
每个 NPC 自主决定回不回——prompt 里有「不想回可以不发」，很多成员选择沉默
部分成员可能被冷却（同角色短时间不重复发言）、不在场降级等挡掉
两条回复内容几乎一样（“目前大家都在安全采集”）——因为 12 个角色看到的是同一份环境感知，prompt 趋同
@ 功能正好解决这个吵的问题：点名谁谁回，别的人闭嘴。

# 短信与群聊功能优化
问题：等半天没人回复，回复的内容也很机械。
用户发言后-》群聊编排器agent->那些人发言，发言顺序->界面先显示沉默的角色头像(沉默：xxx,xxx,xxx)->发言人逐个发言（每个角色独立发言的流式台词生成，有打字效果）
->触发追加发言（随机，机率调小于40%）-》群聊编排器agent-》。。。
@角色名 这个角色先发言->触发追加发言（随机，机率调小于40%）-》群聊编排器agent-》。。。

角色发言的智能度对其 宿主的故事模式，使用同个模型和增加一些故事模式发言的入参。

## 落地实现（2026-11-22）

### 为什么旧链路「等半天 + 机械」
- **没有编排器**：玩家发一条 → 群里每个 AI 成员**各自**跑一次 brain LLM，
  顺序 = 抢 `state.chatResult` **单槽位**闸门（`App.vue` 的 `brainBusy`）的顺序
  → 12 人串行排队 → 用户体感「等半天」。
- **回复机械**：所有成员看到同一份感知 prompt → 输出趋同 → 两次回复几乎一样。
- **没有发言顺序数据结构**：`Conversation.members` 只是 `string[]`；
  群消息还有 3 分钟冷却（`GROUP_MSG_COOLDOWN_MS`）→ 逐个发言必被挡。
- **没对齐宿主故事模式**：brain 走 `storyMiniGameModel`，宿主剧情模式走
  `storyOrchestratorModel` —— 不是同一个模型；`globalBackground` / 世界书 /
  角色卡 **从未进入任何 brain prompt**。

### 新链路
```
玩家在群里发一条
      ↓
App.vue onSysSmsSend：群聊 → runGroupOrchestration（单聊仍走原 brain 路径）
      ↓
编排器（插件业务 src/agents/groupOrchestrator.ts）
      ├─ 组装 userPrompt：成员角色卡 + 玩家原话 + 群历史(8条)
      │              + 故事全局背景 + 常驻世界书 + 故事动态数据
      ├─ 调宿主**通用** LLM 通道 "plugin-llm"，aiConfigKey = storyOrchestratorModel
      │  （= 与宿主剧情模式同一个模型）
      └─ 校验输出：roleId 必须是群成员 / text 非空 / 不重复 / 限量
      ↓
speakers 有序入队 conv.pendingSpeaking
      ↓
界面立刻显示：队首「正在输入…」气泡 + 后续成员灰色沉默头像
      ↓
每 900ms 揭示一条 → 消息一个个冒泡
      ↓
一轮结束掷骰：P < 0.35（<40%）→ 带新上下文再跑一轮，最多 3 轮
```
- **@点名**：被点名的角色排第一（编排器输出后由插件层再兜一层排序）。
- **群聊不再逐人登记待回复**：否则心跳兜底会再各自跑一次 brain → 重复发言。

### 插件 / 宿主职责边界
| 层 | 负责 |
|---|---|
| **插件仓**（本插件） | 群聊编排器 agent：提示词、编排规则、入参组装、输出校验、发言队列、界面渲染 |
| **宿主（app 仓）** | 只提供通用能力：① `plugin-llm` 通道（按插件给的 prompt 调一次模型、JSON 直通）② `ctx.globalBackground` / `worldBookDigest` 故事上下文 ③ `agent.run` 的 `aiConfigKey` 透传 |

宿主**不认识**任何插件业务 agent —— 插件自己的 agent 全在插件仓。

## 单聊台词质量对齐（2026-11-23 补）

**问题**：编排器上线后，群聊质量上来了，但**单聊**还是旧 brain 链路 ——
玩家问「现在的世界格局是怎么样的」，回复只有「目前各方都未交战，我正去食堂补给区待命。」
（brain 的感知 prompt 里全是 HP/敌人/背包，零故事背景 → 模型只能复读游戏状态）。
而宿主故事模式同一个问题能答出「黑雾封城/神幕/二选一/逆选会/裁判」+ 动作神态描写。

**修复**（对齐宿主 TaskSpeakerAgent 的喂法）：
1. **编排器提示词重写**：删掉「≤40 字，1 句」；改为「（动作/神态描写。）+ 台词正文，
   40~140 字，必须引用故事背景里的具体设定名词，三人切入点互不雷同」。
   实测同一问题输出：苏晚晴（医疗视角）/赵大川（派系视角）/陈南璇（神幕规律视角），
   全部带括号动作描写 + 世界观专有名词。
2. **单聊改走「角色发言器」**（`speakAsCharacter`，同插件模块）：
   `sys_sms_speak` → storyOrchestratorModel + 角色卡 + 故事全局背景 + 动态背景（记忆摘要）
   + 世界书 + 单聊往来 → 输出一段带动作描写的台词（纯文本，不走决策 JSON）。
   失败回退旧 brain 链路保底。
3. **宿主通用通道增强**：`plugin-llm` 解析不出 JSON 时回退原文（`{text: 原文}`）——
   通道更通用，单聊台词不再被 JSON 解析卡死。
4. **ctx 注入 dynamicGlobalBackground**（state.memorySummary，含影子缓存快路径）。
5. **dev-host 桩**：storyData 带上 `world.settings.globalBackground` + 顶层
   `dynamicGlobalBackground`（storyInfo 已返回），entryCtx 注入 —— 之前桩下编排器拿到的
   故事背景是「（无）」。

**注意**：后端（60002）是 tsx 直跑不热重载 —— 本次 PluginAgentRunner /
PluginExecutionContext 改动需要**重启后端**才生效；entry.js 走 mtime 影子重载无需重启。

## 消息复制 / 引用（2026-11-23）

短信（单聊/群聊）的台词气泡支持 **PC 右键点击 / 手机长按 500ms** → 弹出操作菜单
（2026-11-23 改：PC 由左键改为右键 —— 左键保留给未来的选中/滚动等交互，右键更符合桌面习惯；`@contextmenu.prevent` 屏蔽系统菜单）：

- **复制**：clipboard API 优先，老环境回退 `execCommand`。
- **引用**：输入框上方出现引用条（可 ✕ 取消），发送时拼
  `「回复 @名字：原话摘要」
用户输入` 前缀 —— `@名字` 让**点名机制自动生效**
  （群聊被引用者必回且第一个发言；单聊被引用者回复）。

配套改动：`@点名` 正则排除全角/半角冒号（`：:`）—— 否则
`回复 @苏晚晴：xxx` 会把「苏晚晴：xxx」整段当名字匹配不上。
气泡 `user-select:none + -webkit-touch-callout:none`：复制统一走自定义菜单，
避免手机系统长按弹层与页面滚动冲突。system 消息与「正在输入」占位不响应。

## 沉默占位（2026-11-23 补）

**问题**：编排器调 LLM 要 10~25s，这段时间界面完全空白（用户发完消息没有任何反馈），
直到编排返回才出现「正在输入」气泡。

**修复**：玩家发完消息**立刻**显示「灰色头像一排 + 沉默：A、B、C」占位行
（`conv.silentPlaceholder`，含群聊全部 AI 成员；单聊显示 1 人）。
- 群聊：`runGroupOrchestration` 每轮调 LLM 前 set、返回后 clear（追加轮同样有占位）；
- 单聊：`speakPrivateReply` 调发言器前 set、返回后 clear；
- 编排返回后占位行隐藏，由「正在输入」气泡 + 排队灰色头像接管；
- 占位是会话内瞬态，不落库（刷新丢弃）。

## 沉默语义修正（2026-11-23 二次）

用户纠正：**沉默 = 本轮回合里没有发言的成员**，不是「等待中的全员」。

- 等待 LLM 期间的瞬态占位行文案改为「思考中：全员」（不再叫"沉默"，避免误导）；
- 每轮发言人**冒泡结束后**，追加一条**持久**的 `system` 消息（带 `silent` 成员数组）：
  渲染为一排灰头像 + 「沉默：A、B、C」，**永久留在消息流里**（落库、刷新不丢）；
- 全员都发言 → 不追加；多轮编排 → 每轮各追加一条（每轮沉默者不同）；
- `Message.silent?: {roleId, roleName}[]`，normalizeConv 落库透传。

## ★ 二次重构：编排只定名单，台词逐人独立生成（2026-11-23 三次）

**用户判定**：一次调用产出全部台词 → 同一上下文出来 → 口吻/字数/结构雷同
（「字数差不多，内容差不多」）。推翻该方案。

**现行链路**（= 用户文档 2026-11-23 版）：
```
玩家发言 → 编排器（一次 LLM，只决定「谁发言 + 顺序」，不写台词）
        → 界面先追加持久的「沉默：xxx」行（= 本轮没被编排到的成员）
        → 发言人逐个【独立】调 speakAsCharacter（每角色一次 LLM）：
            各自角色卡 + 群聊最新历史（含前面人刚说的话）+ 故事背景
        → 打字机逐字上屏（streaming 消息 + ▍光标），一条说完 ≥3s 再到下一条
        → 掷骰 <35% → 追加轮（重新编排）
```
- 独立调用 = 个性真正分化；每次带最新历史 = 后发言者接得住。
- @点名：编排器名单排第一；模型漏掉时插件层**注入**补上（点名必回）。
- streamGroupSpeech → sys_sms_speak → speakAsCharacter（单聊/群聊同一发言器）。
- store 新增 begin/append/endStreamingMessage（打字机高频 append 不落库，结束统一存）；
  Message.streaming 落库 normalize 强制 false。
- GROUP_SPEAK：SPEAK_GAP_MS=3000（发言间隔下限）、TYPE_CHUNK=2/TYPE_INTERVAL_MS=50（打字机节奏）。
- pendingSpeaking「先全部生成再揭示」机制废弃（不再使用）。
