# 通信(短信) 设计评审意见

> 评审对象：`通信(短信).design.md`、`原型图/通信面板原型.html`、`原型图/界面与接口对接说明.md`
> 评审依据：`req.md` 四个问题 + 插件实际代码（`vue/src/ai/brain.ts`、`vue/src/SystemPanel.vue`、`vue/src/App.vue`、`vue/src/toonflowJsApi.ts`、`md/curr_design/plugins_docs/插件补充/数据储存.t_plugin_session_data.md`）
> 结论：**结构与方向正确，可以开工；但有 3 个「不做就会做错」的硬伤 + 1 组规范冲突，必须先补齐再实现。**

---

## 一、总评

| 维度 | 评价 |
|---|---|
| 需求覆盖 | 4 个问题全部有明确回答（未读清零 / AI 主动发信 / 群聊单聊 / 存储位置），✅ |
| 存储选型 | 选 `t_plugin_session_data` 而不是 AI 台词列表，**判断正确**（台词列表是地图集静态内容，短信是运行时动态数据），✅ |
| 数据结构 | 够用，但缺 ID 约定、缺长度上限、缺"谁负责写"的责任边界 |
| AI 链路 | 触发时机设计合理，**但只设计了 AI→玩家，没设计 玩家→AI**，❌ 最大硬伤 |
| 未读机制 | 规则表清晰，但**计算公式会把玩家自己发的消息算成未读**，❌ |
| 视觉原型 | 信息架构对，但**结构与落地形态冲突**（独立面板 vs 系统面板内 tab），且尺寸写死 |
| 工程对齐 | 改了哪些文件写得很清楚，但**漏了链路上的关键一环（谁把 message 写进存储）** |

**一句话**：这份设计"想清楚了 80%"，剩下的 20% 恰好是会导致返工的接线细节。

## 二、必须修的硬伤（阻断实现）

### 🔴 H1. 玩家发的短信，AI 根本看不到 —— 聊天退化成单向广播

设计 §6.3 只往 prompt 里注入了「**群聊**最近消息」，玩家在单聊里写的任何内容**完全没有进入 AI 的 prompt**。

后果：
- 玩家在短信面板给"萧肿"发"药圃在哪"，AI 永远不会回；
- `to: "player"` 的单聊只能是"AI 单向发消息"，不是聊天。

修法（建议）：
1. `buildUserPrompt()` 注入**未回复的玩家短信**，单聊和群聊都要：
   ```
   ### 短信往来（最近 5 条，其中未回你的用 ★ 标注）
   - [单聊·萧肿] 玩家 14:22: 药圃在哪
   ```
2. 玩家发消息 → `notifyAIEvent(entityId, "dialog", ...)` 或直接置 `pendingTriggerPriority = "P0"`，
   让 AI **立刻**决策一次回复，而不是等 20s 心跳。
3. prompt 里给出明确回复契约：
   ```
   如果有 ★ 标记的玩家消息，你必须回复；其余情况下不要重复回应已回复过的消息。
   ```

### 🔴 H2. 未读数把玩家自己发的消息也算进去了

现有公式：
```ts
const lastReadIdx = conv.messages.findIndex(m => m.id === conv.lastReadMsgId);
return sum + (conv.messages.length - 1 - lastReadIdx);
```
两个错：
1. `lastReadMsgId === null` → `findIndex` 返回 -1 → 结果 = `messages.length`，**把玩家自己发的消息算进未读**。
   例：`[AI1, 玩家1]` → 未读 2（应为 1）。
2. 公式是「位置差」而不是「条数差」，玩家在中间插话时会把玩家消息计入。

修法（改成按条数 + 排除自己发的）：
```ts
function getConvUnread(conv: Conversation): number {
  const start = conv.lastReadMsgId
    ? conv.messages.findIndex(m => m.id === conv.lastReadMsgId) + 1
    : 0;
  return conv.messages.slice(start).filter(m => m.from !== "player").length;
}
```
同时规定：**玩家发出消息时，自动把 `lastReadMsgId` 推到该条消息**（设计 §4.3 已有"玩家主动发消息→当前会话自动清零"，但公式要与之自洽）。

### 🔴 H3. 「谁把 AI 的 message 写进存储」这条链路没人认领

设计 §8.2 写了要改 `brain.ts` / `types.ts` / `SystemPanel.vue` / `App.vue`，但：
- `brain.ts` 是**纯逻辑模块**，它不持有 `pluginData` 句柄；
- 存储写入在 `App.vue` 侧（`toonflowJsApi.pluginData.set`）或 `entry.ts` 后端（`context.tsApi.pluginData`），
  `brain.ts` 的返回值根本到不了存储层。

必须明确一条**唯一链路**，二选一：

**方案 A（推荐，全前端）**
```
callBrain() 返回 LLMDecision（含 message）
  → App.vue 消费 decision.message
  → 调 smsStore.receiveMessage(from, to, text)
  → smsStore 内部防抖 1s 写 pluginData.set("sms_conversations", ...)
```
好处：未读角标、"玩家正在看就不标未读"这类前端态天然在前端闭环，不用跨 postMessage 通信。

**方案 B（后端权威）**
```
entry.ts 在处理 sys_brain 回包时把 message 落库
```
问题：`t_plugin_session_data` 每次 set 都会触发宿主回包刷新，前端还要再拉一次，且"未读清零"要靠前端回写，会出现写-读竞态（`数据储存.t_plugin_session_data.md` 已知坑 #1）。**不推荐**。

补充：`brain.ts` 里 `brainBusy` 全局单槽 + 8s 超时是**全局闸门**，5 个角色共用一个 LLM 通道。这意味着「
一个角色发短信时，其他角色的 brain 请求会被闸门挡掉并走 `fallbackDecision`（程序化兜底）。所以：
- 短信发送必须**独立于 brain 主链路**，或复用同一次 LLM 调用的返回值；
- 否则「AI 主动发短信」会因闸门竞争而随机丢失。
建议：把短信生成放进 **brain 的同一次 JSON 响应**（设计 §6.1 已经这么设计了，✅），
但要明确 —— 拿不到闸门的那次决策**不发短信**（fallbackDecision 不带 message），避免"程序化兜底却发出一条机械短信"。

## 三、规范冲突 / 遗漏（不致命但会返工）

### 🟡 M1. 数据结构缺三样东西

`Conversation` / `Message` 建议补：

| 缺失 | 后果 | 建议 |
|---|---|---|
| `Message.type` | 已声明 `"text"` 预留，但没定扩展契约 | 保留但改成 `type: "text" \| "system" \| "action"`，`system` 用于「XX 加入了群聊」 |
| `Message.conversationId` | 消息平铺进 `conv.messages` 时，反向查会话靠遍历 | 加上，导出/清理时好用 |
| **消息条数上限** | `t_plugin_session_data` 单行 JSON 会无限膨胀，撞上 `pluginData.set` 体积上限 | `conv.messages` 保留最近 **100 条**（或按时间窗），超出丢最旧的；`lastReadMsgId` 指向被截断的旧消息时要重置为 `null` |
| `Conversation.pinned` | 无 | 微信体验必需，但可延后 |

另外 `nextConversationId` / `nextMessageId` 用 `number` 递增 —— 建议改 `string`（`crypto.randomUUID()` 或 `c_<ts>_<rand>`），
理由：number 计数器在"多标签页/多设备"下会撞 ID，且 JSON 里 number 精度有上限。ID 用 string 是零成本改动。

### 🟡 M2. 存储 sessionId 范围没定 —— 这条会直接导致"数据串号"

设计只说了 `dataKey = "sms_conversations"`，没说 `sessionId` 用什么。

按 `数据储存.t_plugin_session_data.md` 的已知坑 #3：
> 故事隔离：地图模板 key 必须带 `:<story>` 后缀。`sessionId="all"` 下不带后缀会故事 A 覆盖故事 B。

短信是**强剧情绑定**的内容（"萧肿"是谁取决于当前故事）。所以必须二选一并写进设计：
- **推荐**：`sessionId = "all"`（跨会话共享）+ `dataKey = "sms_conversations:<story>"` —— 短信跟着故事走，换故事不串；
- 或者：`sessionId = 当前会话`（默认）—— 每个故事会话一份短信。

**不要**用 `dataKey = "sms_conversations"` + `sessionId = "all"`，那是跨故事串号。

### 🟡 M3. 「AI 托管角色」= 哪些角色，没定义

设计 §7.1 说"和场上已存在的 AI 托管角色自动生成单聊会话"，但：
- `AIState.enabled` 是**玩家勾选的开关**，会随时开关；
- 角色可能死亡、离场、跨地图（`parked` 机制）。

如果每次开关勾选就新建一个会话，会产生一堆空会话。建议规则：
- 会话由**消息驱动**创建：AI 第一次真的要发消息时，才 `ensureConversation(roleId)`；
- 通讯录列表（"新建群聊"要选人）另取一份：所有 `AIState.enabled === true` 的角色 + 场上存活的 ally 类型实体；
- 角色下线不清会话，只是不再能发消息；`fromName` 冗余存储已经能兜住改名。

### 🟡 M4. 原型图结构与落地形态不一致

原型 HTML 是一个 **900×600 独立面板**（`.sms-panel`），带自己的标题栏和 `×` 关闭按钮。
但设计 §5.1 说是 **SystemPanel.vue 里加一个 tab**，SystemPanel 的实际形态是：

```css
.sys-panel { width: 80%; height: 80%; }   /* App.vue */
.sp-tabs  { display:flex; flex-wrap: wrap; }  /* 一行放 3 个，共 9 个 tab */
.sp-body  { flex:1; overflow:auto; padding:8px; }
```

问题：
1. 原型的独立头部（"💬 通信(短信) + 新建群聊 + ×"）在 tab 形态下**没有对应位置** —— tab 页签里放不下"新建群聊"按钮和关闭按钮。原型里的 `.sms-header` 需要重新安置（建议：放到 `.sp-body` 内的子面板头部，或做成 tab 右上角的悬浮 "+"）。
2. 系统面板已有 **9 个 tab**，`.sp-tab { flex: 1 1 30% }` → 加第 10 个会换行成 3-3-3-1。通信 tab 是高频功能，建议**把「通信」放到 tab 列表第一位**（未读消息应该是最容易被看到的入口），而不是追加在末尾。
3. `.sp-body` 有 `overflow: auto`，聊天窗口要自己处理滚动（消息流 `flex:1` + `overflow-y:auto`），否则会出现"整页滚动 + 消息区滚动"的双滚动条。
4. 原型写死 `width:900px; height:600px`，而实际是 `80%×80%` 且可拖拽。原型应改成 `100%` 填充。

### 🟡 M5. 原型缺系统按钮角标

设计 §4.1 和 req.md 都要求"系统入口按钮上显示未读数"，原型只做了
右下角一个 `badge-demo` 说明块（"系统按钮上 5 / 通信 tab 上 5"），
**没有真正画出来**。而实际的系统按钮是 `App.vue` 里的一个 44×44 的 `.sys-btn`（`⚙` 字符）。

需要补：
- `.sys-btn` 的右上角红点角标（原型里没画这个按钮）；
- `SystemPanel.vue` 的 `.sp-tab` 角标 —— 原型画的是 tab 内的 badge，但设计 §5.1 的 HTML 片段里 badge 是**在 `.sp-tab` 内**，这个是对的，不过缺 `position: relative` + 绝对定位的角标样式（现有 `.sp-tab` 是 flex 布局，塞个 span 会把 tab 文字挤歪）。

### 🟡 M6. 视觉风格与游戏现有主题不一致

游戏现有系统面板是 `#1e1f1f` / `rgba(255,255,255,0.06)` 的**深灰**风格（见 `SystemPanel.vue` 的 `.sp`），
原型用的是 `#16213e` / `#0f3460` 的**深蓝**+ `#e94560` 亮红。
亮红 `#e94560` 用在玩家气泡上，和游戏的 `#2f6fd0`（选中 tab 蓝）风格不一致。
建议：原型改用游戏现有变量（`#1e1f1f` 底、`#2f6fd0` 主蓝、`#cfd8e3` 文字），玩家气泡用蓝系而非红系——
因为**红色在这个项目里应该保留给"危险/未读角标"**，玩家自己的气泡用红色会削弱角标的语义。

## 四、值得肯定的部分

1. **存储选型判断准确** —— 明确区分了"地图集静态台词"和"运行时动态短信"，并选了 `t_plugin_session_data`。
   这条想清楚了，后面就不会走偏。
2. **未读清零规则成表** —— 微信式清零 + "正在看就不标未读"的实时判断，是正确的 UX 模型。
3. **把 message 塞进 brain 的同一次 JSON 响应**（§6.1）而不是另开一次 LLM 调用 —— 节省 token，且避免重复决策。
4. **群聊上下文注入 prompt**（§6.3）让 AI 之间能形成对话链条 —— 方向对。
5. **MVP 分两期**（§9）—— 明确先做单聊 + 未读角标 + 存储，群聊放第二版。范围控制得当。
6. **原型图独立成 HTML + 配套接口说明文档** —— 这个交付习惯很好，接口说明表可以直接当开发依据。

## 六、给 req.md 四个问题的直接回答

| 问题 | 评审结论 |
|---|---|
| 1. 未读消息显示在哪？清零机制是什么？ | ✅ 位置和清零规则都对。但**公式要改**（见 H2），且"实时已读"依赖前端态，需要在 `store.ts` 里统一实现，别散在组件里。 |
| 2. AI 托管角色主动发短信/发到群聊 | ⚠️ 方向对，但**必须补"玩家→AI"**（见 H1），否则不是聊天是广播。另外 brain 闸门会让短信随机丢失，需在 §6.1 补一条"拿不到 LLM 就不发短信"的规则。 |
| 3. 微信式群聊 + 单聊 | ✅ 数据结构和 UI 方向都对。需补：群成员增删、群内 AI 发言频率上限（否则会刷屏）、群名修改。 |
| 4. 存储在哪里？ | ✅ **存 `t_plugin_session_data`，不存 AI 台词列表** —— 判断正确。但必须补 `sessionId` 策略（见 M2），否则跨故事串号；还要补消息条数上限防 JSON 膨胀。 |
