# 通信(短信) 功能设计方案

> 版本：v2（2026-10-30 修订）
> 修订说明：v1 评审发现 3 个阻断性硬伤（H1 玩家→AI 链路缺失 / H2 未读公式错误 / H3 存储写入链路未认领）与 6 项规范遗漏（M1~M6），本版逐条修正。评审原文见 [`评审意见.md`](评审意见.md)。

## 1. 概述

在系统面板新增「通信」页签，实现类似微信的单聊/群聊功能：

- AI 托管角色可**主动**给玩家发短信，也可在群聊里发言
- 玩家可与单个 AI 角色单聊，也可与多个 AI 角色群聊
- 玩家发短信后，目标 AI 会被**立即唤醒回复**（不是单向广播）
- 系统按钮和通信 tab 上显示未读消息角标

### 1.1 与既有「角色对话」功能的关系

项目里已存在一套对话机制（触碰角色 → 头顶「聊天」按钮 → 走「角色发言器 agent」，台词同步到宿主聊天框，见 `game.md`）。

**两套并存，不合并**，职责划清：

| | 既有角色对话 | 通信(短信) |
|---|---|---|
| 触发 | 玩家走到角色身边点「聊天」 | 通信面板，随时随地 |
| 性质 | 面对面即时对话 | 异步消息（可离线阅读） |
| 存储 | 前端 `chatMessages` 内存态，关闭即丢 | `t_plugin_session_data` 持久化 |
| AI 来源 | 独立「发言器 agent」 | AI 托管大脑的同一次决策 |
| 目的 | 触发剧情 / 选项交互 | 异步通知 + 轻量沟通 |

**唯一交点**：`#ai 指令` 只在角色对话里可用，短信里不放 `#ai`（短信是轻量通道，复杂指令仍走面对面对话）。

## 2. 数据结构设计

### 2.1 会话（Conversation）

```typescript
export type ConversationType = "private" | "group";

export interface Conversation {
  id: string;                    // 会话唯一ID（string，见 §2.4）
  type: ConversationType;        // 单聊 / 群聊
  name: string;                  // 会话显示名（群名或对方角色名）
  avatar?: string;               // 群头像（可选）
  members: string[];            // 参与角色ID列表（玩家固定在其中）
  messages: Message[];           // 消息列表（按时间升序，最多 MAX_MESSAGES 条）
  lastReadMsgId: string | null;  // 玩家最后读到的消息ID（用于计算未读）
  createdAt: number;            // 创建时间
  updatedAt: number;            // 最后一条消息时间（用于会话列表排序）
  /** 玩家是否有未读回复（AI 已回但玩家没读）—— 群聊里区分"谁还没回我" */
  awaitingReply?: boolean;
}
```

### 2.2 消息（Message）

```typescript
export type MessageType = "text" | "system";

export interface Message {
  id: string;                    // 消息唯一ID（string，见 §2.4）
  conversationId: string;       // 所属会话ID（冗余，便于导出 / 清理）
  from: string;                  // 发送者ID："player" 或 角色ID
  fromName: string;              // 发送者显示名（冗余存储，避免查角色表）
  text: string;                  // 消息内容
  timestamp: number;             // 发送时间戳
  type: MessageType;             // "text" 普通消息 / "system" 系统提示（如「XX 加入群聊」）
}
```

> `type: "system"` 的消息**永远不计入未读**（见 §4.2）。

### 2.3 落库结构

```typescript
export interface SmsStoreShape {
  conversations: Conversation[];
  /** 数据版本号，用于未来结构迁移 */
  version: number;
}
```

### 2.4 ID 生成规则

**ID 一律用 `string`，不用自增 `number`。**

理由：
- 自增计数器在多标签页 / 多设备下会撞 ID；
- JSON number 有精度上限，且与 `lastReadMsgId: string` 类型不统一。

```typescript
export function genId(prefix: "c" | "m"): string {
  return `${prefix}_${Date.now().toString(36)}_${Math.random().toString(36).slice(2, 8)}`;
}
```

### 2.5 容量上限（防 JSON 膨胀）

`t_plugin_session_data` 单行 JSON 有体积上限（`pluginData.set` 上传限制），短信是**只增不减**的数据，必须封顶。

| 约束 | 值 | 说明 |
|---|---|---|
| 单会话消息上限 | **100 条** | 超出丢弃最旧的 |
| 单条消息文本上限 | **500 字符** | 超长截断并加 `…` |
| 总会话上限 | **50 个** | 超出丢弃最久未活跃的（按 `updatedAt`） |
| 落库体积上限 | **256 KB** | 接近时先裁剪最旧会话，仍超则只保 `lastReadMsgId` + 最近 30 条 |

**截断时的 `lastReadMsgId` 处理**：
若被丢弃的消息中包含 `lastReadMsgId` 指向的那条，则把 `lastReadMsgId` 重置为 `null`——
此时该会话所有未读消息都算未读，语义上正确（玩家确实没读过那些新消息）。

## 3. 存储方案

### 3.1 存储位置

**存插件数据 `t_plugin_session_data`，不存 AI 聊天台词列表。**

| 存储位置 | 是否使用 | 原因 |
|---|---|---|
| `t_plugin_session_data` | ✅ 主存储 | 短信是动态运行时数据，和 `ai_settings`、`map_data` 同层级，需跨会话持久化 |
| eventEngine 对话脚本（AI 聊天台词列表） | ❌ 不使用 | 那是事件触发的预写固定对话，是地图集静态内容，与实时短信是两回事 |

### 3.2 ★ sessionId 与 dataKey 策略（v2 关键修正）

v1 只写了 `dataKey = "sms_conversations"`，没定义 `sessionId`，**会导致跨故事串号**。

按 [`数据储存.t_plugin_session_data.md`](../../plugins_docs/插件补充/数据储存.t_plugin_session_data.md) 已知坑 #3：
> 故事隔离：地图模板 key 必须带 `:<story>` 后缀。`sessionId="all"` 下不带后缀会故事 A 覆盖故事 B。

短信是**强剧情绑定**的内容（"萧肿"是谁取决于当前故事），所以：

| 项 | 取值 | 理由 |
|---|---|---|
| `sessionId` | `"all"` | 短信跨会话共享，玩家重进故事还能翻到旧短信 |
| `dataKey` | `sms_conversations:<story>` | **按故事隔离**，换故事不串号 |

```typescript
// story 取自宿主注入的 state.worldName（entry.ts 在 init 时写入顶层）
const dataKey = `sms_conversations:${state.value?.worldName || "default"}`;
```

**明确禁止**：`sessionId = "all"` + `dataKey = "sms_conversations"`（裸 key）——那是跨故事覆盖。

**兼容读取**：加载时若带 story 后缀的 key 不存在，回退读裸 key `sms_conversations`，
并把它迁移到带后缀的 key（一次性），避免老存档丢失。

### 3.3 ★ 写入链路归属（v2 关键修正）

v1 的问题：`brain.ts` 是**纯逻辑模块**，不持有 `pluginData` 句柄；它的返回值根本到不了存储层。
v1 §8.2 列的 4 个改动文件都没覆盖"谁把 AI 的 message 写进存储"这条接线。

**本设计采用方案 A：全前端写入。**

```
callBrain() 返回 LLMDecision（含 message 字段）
  │
  ▼
App.vue 消费 decision.message            ← 接线点，唯一一处
  │
  ▼
smsStore.receiveMessage(from, to, text)  ← 写入内存 + 触发未读计算
  │
  ▼
smsStore 内部防抖 1s → toonflowJsApi.pluginData.set(dataKey, shape)
```

**为什么不用后端落库（方案 B）**：
`t_plugin_session_data` 每次 `set` 都会触发宿主回包刷新，前端还要再拉一次；
且"未读清零"要靠前端回写，会出现写-读竞态（存储文档已知坑 #1）。

**写入策略**：

| 时机 | 动作 | 延迟 |
|---|---|---|
| 新消息到达 | 防抖写 `pluginData.set` | 1s |
| 玩家阅读更新 `lastReadMsgId` | 防抖写 | 500ms |
| 玩家发消息 | 防抖写 | 500ms（同时把 `lastReadMsgId` 推到该条） |
| 退出游戏 / 切换地图 | **强制同步写** | 立即 |
| 落库失败 | `console.warn` 兜底，**不阻断玩法** | —— |

## 4. 未读消息机制

### 4.1 显示位置

1. **系统入口按钮**（App.vue 的 `.sys-btn`，44×44 圆形 ⚙ 按钮）：右上角红色角标，显示总未读数
2. **通信 tab**（SystemPanel.vue 的 `.sp-tab`）：文字旁显示未读数（与系统按钮一致）

角标统一规则：`> 99` 显示 `99+`，`= 0` 时整个角标元素不渲染。

### 4.2 ★ 未读数计算（v2 修正公式）

v1 的公式有两个错：
1. `lastReadMsgId === null` → `findIndex` 返回 -1 → 结果 = 消息总数，**把玩家自己发的消息算成未读**；
2. 用的是"位置差"而非"条数差"，玩家在中间插话时会把玩家消息计入。

v2 公式：**按条数 + 排除玩家自己发的 + 排除 system 类型**。

```typescript
/** 单个会话的未读数 */
export function getConvUnread(conv: Conversation): number {
  const startIdx = conv.lastReadMsgId
    ? conv.messages.findIndex((m) => m.id === conv.lastReadMsgId) + 1
    : 0;
  return conv.messages
    .slice(startIdx)
    .filter((m) => m.from !== "player" && m.type !== "system")
    .length;
}

/** 总未读数 */
export function getTotalUnread(conversations: Conversation[]): number {
  return conversations.reduce((sum, c) => sum + getConvUnread(c), 0);
}
```

> `slice(startIdx)` 中，当 `lastReadMsgId` 为 `null` 时 `startIdx = 0`，会从第一条消息开始数——
> 但因为过滤了 `from === "player"`，玩家自己发的消息不会被计入未读。✅

### 4.3 清零规则（微信式）

| 操作 | 效果 |
|---|---|
| 点进某个会话 | 该会话未读清零（`lastReadMsgId` 更新为最后一条消息ID） |
| 所有会话都已读 | 总未读数清零，系统按钮和 tab 角标消失 |
| AI 新消息到达时，玩家正在看这个会话 | 不标未读（实时已读，直接追加到消息流） |
| 玩家主动发消息 | 当前会话自动清零（`lastReadMsgId` 推到该条消息） |
| `system` 类型消息 | 永远不计入未读 |

### 4.4 实时已读判断

```typescript
/**
 * AI 发消息时判断要不要标未读。
 * 玩家正打开通信 tab 且正在看这个会话 → 视为已读。
 */
export function shouldMarkUnread(
  convId: string,
  activeTab: string,
  activeConvId: string,
): boolean {
  return !(activeTab === "sms" && activeConvId === convId);
}
```

> 这两个"当前视图状态"（`activeTab` / `activeConvId`）由 `App.vue` 持有，
> 因为系统按钮角标在 App.vue 层、tab 角标在 SystemPanel 层，两处都要用。
> 建议在 `sms/store.ts` 里用一个模块级 reactive 对象统一存，避免两处不同步。


**尺寸约束（对齐落地形态）**：

| 项 | 值 | 原因 |
|---|---|---|
| 根容器 | `height: 100%; width: 100%; overflow: hidden` | `.sp-body` 是 `flex: 1 1 auto`；不写死 px |
| 会话列表 | `width: 240px; flex-shrink: 0` | 固定宽度 |
| 聊天窗口 | `flex: 1; min-width: 0` | **`min-width: 0` 必须加**，否则 flex 子项被长内容撑破 |
| 消息流 | `flex: 1; overflow-y: auto` | **`.sp-body` 已有 `overflow: auto`** → 自己管滚动，避免双滚动条 |

**左侧会话列表：**
- ★ 顶部：**通讯录选择器**（搜索框 + 下拉），而不是「直接在列表里列全部角色」
  - 点搜索框 / 输入 / 点 ▾ → 展开下拉，三段：
    1. **群聊** —— 已创建的群聊（带未读角标），点一下直接切过去
    2. **角色** —— 通讯录里**还没建过单聊**的角色（带「托管」标识），点一下**主动建单聊并打开**
    3. **＋ 新建群聊** —— 打开建群弹窗
  - 搜索框按角色名 / 群名过滤；已建过单聊的角色**不再重复出现在「角色」段**（避免同一个人出现两次）
  - Esc / 点外部 → 收起
  - **为什么不用「列表里直接列全部角色」**：角色可能有几十个，会把真正的会话淹没在噪音里；
    微信/QQ 都是「列表只放已有会话，找人走搜索」这套交互。
- 会话列表本身**只放已有会话**（不塞全部角色）
- 每项：头像 / 名称 / 最后一条消息预览（截断）/ 时间 / 未读角标
- 按 `updatedAt` 降序排列（最新消息在最上面）
- 群聊名称后标注 `[群聊]` 标签
- **群聊预览显示发送者前缀**：`陈南璇: 前面有哥布林，小心`
- 空态（一个会话都没有）：提示「点上方搜索框选角色开始聊天，或新建群聊」

**★ 两条建会话路径（互不替代）**

| 路径 | 触发 | 用途 |
|---|---|---|
| `ensurePrivateConversation(roleId, roleName)` | AI **真的要发消息**时 | 消息驱动 —— 避免玩家反复开关 AI 托管攒出一堆空会话 |
| `startPrivateChat(roleId, roleName)` | 玩家在通讯录里**点某人**时 | 玩家驱动 —— 会话立刻建出来并打开，右半屏马上能打字 |

> ⚠️ 交互实现约束：下拉项的选择动作走 **`pointerdown`** 而不是 `click`。
> 组件挂在可拖拽的系统面板里，父层用了 `setPointerCapture` —— 一旦 pointerdown 被捕获，
> 浏览器可能不再在选项上合成 click →「点角色没反应」。pointerdown 比 click 早，不会重复触发。

**右侧聊天窗口：**
- 顶部：当前会话名称 + 成员数（群聊显示 "N人"，单聊显示 "单聊"）+ 右侧「+ 新建群聊」按钮
- 中间：消息流，玩家消息靠右、AI 消息靠左
- 群聊里每条 AI 消息上方显示发送者名字
- 底部：输入框 + 发送按钮（Enter 发送，Shift+Enter 换行）

### 5.5 视觉规范（对齐游戏现有主题）

游戏现有系统面板是**深灰**风格（`SystemPanel.vue` 的 `.sp`：`#1e1f1f` 底 / `rgba(255,255,255,0.06)` 面板 / `#cfd8e3` 文字 / `#2f6fd0` 主蓝）。

> v1 原型用了深蓝 `#16213e` + 亮红 `#e94560`，与游戏不一致，且把红色用在了玩家气泡上，
> 削弱了红色作为"未读/危险"信号的语义。v2 统一到游戏主题。

| 用途 | 色值 | 说明 |
|---|---|---|
| 面板底 | `#1e1f1f` | 与 `.sys-panel` 一致 |

## 6. AI 主动发短信 + 玩家→AI 回复机制

### 6.1 触发时机

**两种触发路径：**

**路径 1 · 心跳触发（主要）**
AI 大脑决策时（`callBrain()`），LLM 返回的 JSON 里加可选字段 `message`：

```json
{
  "reasoning": "在采药，想跟玩家说一声",
  "goal": "采集",
  "action": { "type": "gather", ... },
  "message": {
    "text": "我去东边药圃采药了，有事喊我。",
    "to": "player"
  }
}
```

`to` 取值：
- `"player"` → 发到与该角色的**单聊会话**（不存在则自动创建）
- `"group:<groupId>"` → 发到指定群聊会话

**路径 2 · 事件触发（辅助）**
战斗结束、完成采集、发现稀有资源等关键节点，由 `notifyAIEvent` 触发，AI 主动发一条"感慨"。

### 6.2 ★ 玩家→AI 回复链路（v2 关键修正 · H1）

> **v1 的致命缺陷**：v1 §6.3 只往 prompt 里注入了「**群聊**最近消息」，
> 玩家在**单聊**里写的任何内容完全没有进入 AI 的 prompt。
> 结果：`to: "player"` 的单聊只能是"AI 单向发消息"，不是聊天 —— 玩家发"药圃在哪"，AI 永远不会回。

v2 的三条修正：

#### ① 单聊 + 群聊统一注入玩家消息

`buildUserPrompt()` 新增一段（**单聊和群聊都要**）：

```
### 短信往来（最近 5 条，★ 表示还没回复你）
- [单聊·萧肿] 玩家 14:22: 药圃在哪
- [单聊·萧肿] 萧肿 14:23: 往东走第三个田埂
- [群聊·林家护卫团] 玩家 14:30: 大家小心
- [群聊·林家护卫团] 陈南璇 14:31: 前面有哥布林
```

#### ② 玩家发消息 → 目标 AI 立即被唤醒（P0）

玩家发送消息时，除了落库，还要**立即触发目标 AI 决策一次**：

```typescript
// App.vue 消费玩家发送
smsStore.sendPlayerMessage(convId, text);
// → 找到 conv.members 里的 AI 角色
// → 对每个成员调用 notifyAIEvent(entityId, "dialog", `收到玩家短信：${text}`)
// → 并置 aiState.pendingTriggerPriority = "P0"（不等心跳间隔，立即决策）
```

> v1 的心跳间隔是 20s（非战斗态），玩家发完消息要等 20 秒才看到回复 —— 不可接受。
> 这里用 P0 立即触发，与 `AIGameEvent` 现有的 `priority: "P0" | "P1" | "P2"` 机制对齐。

#### ③ 明确回复契约（防止 AI 刷屏）

在 prompt 的输出格式段加：

```
如果你在上面的「短信往来」里看到了 ★ 标记的玩家消息，
你**必须**在本次回复里给出 message.text 来回应它。
如果你已经回复过该消息（没有 ★ 标记），则**不要**再发重复的 message。
message 字段是可选的，不需要发短信时省略它。
```

### 6.3 ★ brain 闸门与短信可靠性（v2 补充）

`brain.ts` 的 `brainBusy` 是**全局单槽** + 8s 超时，5 个角色共用一条 LLM 通道（见 `App.vue` 的 `callBrainLLM`）。
这意味着"一个角色发短信时，其他角色的 brain 请求会被闸门挡掉"。

**规则**：

| 场景 | 行为 |
|---|---|
| 正常拿到 LLM 响应 | 解析 `message` 字段 → 发短信 |
| 拿不到闸门（`brainBusy` 为 true） | `callLLM` 返回 `""` → `fallbackDecision` 兜底 → **不发短信**（fallback 不带 message） |
| LLM 超时 / 解析失败 | 同上，**不发短信** |

> 为什么不在 fallback 时也发短信？fallback 是程序化兜底（"攻击最近敌人"这类机械决策），
> 让它发短信会产出没有上下文的机械短句。**宁可不发，也不要发垃圾。**

另外：短信生成**必须复用 brain 的同一次 JSON 响应**（v1 §6.1 已如此设计，✅），
**不要另开一次 LLM 调用** —— 否则闸门竞争会让短信随机丢失，且浪费 token。

#### ★ v3 落地补充：区分「没拿到 LLM」和「LLM 没说 message」

v2 的规则表只说了"两种情况都不发短信"，但**后续处理完全不同**：

| 情况 | 短信 | 待回复登记 | 理由 |
|---|---|---|---|
| 没拿到 LLM（闸门/超时/解析失败） | 不发 | **保留** | 还没问过 AI，下次心跳再问 |
| 拿到 LLM 但没有 `message` 字段 | 不发 | **保留** | AI 这次不想回，玩家那条 ★ 还在 prompt 里 |
| 拿到 LLM 且有 `message`，但被频率冷却挡掉 | 不发 | **清除** | 再重试也是被冷却挡，死循环 |

> 落地方式：`brain.ts` 拆出 `callBrainDetailed()`，返回 `{ decision, gotLLM, failReason }`。
> `failReason` 细分四种，用于决定**要不要重试**：

| `failReason` | 含义 | 重试策略 |
|---|---|---|
| `"gate"` | 闸门被占 / 通道不可用 / LLM 返回空 | **重试**（最常见，稍后就能拿到） |
| `"parse"` | 拿到响应但 JSON 解析失败 | 最多再试 2 次（共 3 次） |
| `"emergency"` | 紧急层接管，没走 LLM | **不重试**（紧急层优先，重试也没用） |
| `"gate"`（catch 分支） | LLM 调用抛异常 | 重试 |

> ★ 区分 `failReason` 的意义：不区分的话，"闸门被占"和"响应解析失败"会走同一条路 ——
> 要么都重试（解析失败会白白烧掉 25s 窗口），要么都不重试（闸门一挡玩家就收不到回复）。

#### ★ v3 落地补充：回复走独立通道 + keepAction 模式

玩家发短信后唤醒 AI，走的是**独立的一次 LLM 调用**（`callBrainDetailed(entity, state, { keepAction: true })`），
而不是往调度器队列里塞一个 P0 任务。理由：

| 方案 | 问题 |
|---|---|
| 塞调度器 P0 队列 | 调度器有预算/熔断/单槽位限制；战斗态还会筛掉"离玩家远"的角色 → 玩家刚发的消息被筛掉，要再等 20s |
| **独立调用（采用）** | 可能与调度器抢闸门 → 抢不到就重试（最多 25s） |

`keepAction: true` 的含义：**这次只取短信，不动角色的行动决策**。
不让 AI 回个消息就把"正在采集/正在战斗"的动作打断或替换掉。
实现上表现为：`keepAction` 模式下不覆盖 `aiState.currentAction` / `goal` / `lastBrainTick`。

### 6.5 ★ v3 落地补充：频率控制（防刷屏）

| 场景 | 限制 | 常量 |
|---|---|---|
| AI 主动发**单聊** | 同一角色 1 分钟最多 1 条 | `PRIVATE_MSG_COOLDOWN_MS = 60_000` |
| AI **回复**玩家单聊 | **不受限**（回复本来就该立刻发） | — |
| AI 发**群聊** | 同一角色 3 分钟最多 1 条 | `GROUP_MSG_COOLDOWN_MS = 180_000` |

> ★ 回复也会刷新单聊冷却计时 —— 避免"刚回完，玩家还没看到，紧接着又主动发一条"。

> ★ 判定顺序：**先判冷却，再建会话**。
> 否则"被冷却挡掉"却把空会话建出来了 → 玩家会话列表多出一堆空会话。

### 6.4 群聊消息流

- 一个角色发了群聊消息 → 其他 AI 角色下一轮心跳时，prompt 里能看到群聊最近几条消息
- 这样就形成了"群里几个 AI 自己聊起来"的效果
- **频率控制**（v2 补充，防止刷屏）：
  - 群聊消息同样受 AI 心跳间隔约束（20s/角色），不会无限刷屏
  - 单个 AI 角色**每 3 分钟**最多发 1 条群消息（`lastGroupMsgAt` 记录）
  - 群内同一条消息链，最多连续 3 个 AI 各发一轮，之后必须等玩家参与或超时冷却

## 7. 通讯录设计

### 7.1 群聊成员从哪来

不需要单独维护通讯录表：

- **单聊**：两条路径并存 —— ① AI 第一次真正发消息时自动创建（**消息驱动**）；② 玩家在通讯录下拉里点某人时主动创建（**玩家驱动**，见 §5.4）
- **群聊**：玩家手动创建，选择哪些 AI 角色加入
- 群成员列表就是 `Conversation.members`

### 7.2 ★ "AI 托管角色"的准确范围（v2 修正 · M3）

v1 说"和场上已存在的 AI 托管角色自动生成单聊会话"，但没说清"AI 托管角色"是哪些：
`AIState.enabled` 是玩家勾选的开关，会随时开关；角色可能死亡、离场、跨地图（`parked` 机制）。

**v2 规则**：

| 场景 | 规则 |
|---|---|
| 单聊会话创建 | **消息驱动**：AI 第一次真的要发消息时，才 `ensureConversation(roleId)` |
| 玩家主动发起单聊 | 玩家在通讯录下拉点某人 → `startPrivateChat(roleId, roleName)`，立刻建会话并打开 |
| 通讯录列表（新建群聊选人） | `AIState.enabled === true` 的角色 ∪ 场上存活的 ally 类型实体 |
| 角色被取消托管 / 死亡 / 离场 | **不清会话**，只是不再能发消息；`fromName` 冗余存储能兜住改名 |
| 反复开关托管 | **不产生新会话**（消息驱动路径不会建；只有玩家主动点的才会） |

> 如果按 v1 的"勾选即建会话"，玩家反复开关几次就会攒出一堆空会话。

### 7.3 新建群聊

- 点聊天窗口右上角「+ 新建群聊」按钮
- 弹出选择框：列出通讯录里的 AI 托管角色，勾选要拉进群的角色（≥2 人）
- 输入群名 → 创建群聊会话
- 追加 `system` 类型消息：「{角色名} 加入了群聊」（不计入未读）

### 7.4 群聊管理（v2 补充）

| 操作 | 说明 |
|---|---|
| 改名 | 群聊名称可改（单聊名称跟随角色名，不可改） |
| 踢人 | 从 `members` 移除；历史消息保留 |
| 退出群聊 | 玩家从 `members` 移除自己（历史消息保留，群沉到列表底部） |
| 删除会话 | 只删会话，不删角色 |
