## 1. 两条链路的环境事实（复测中澄清）

本次复测首先澄清了三个此前容易误判的环境事实：

| 事实 | 说明 |
|---|---|
| **3000 端口 = 插件前端 + dev-host 拟真宿主桩** | 桩的 tick 由**客户端 tick 消息**驱动（`vite.config.ts` 1731 行 `tf_plugin_tick` 分支）；客户端不发 → 桩不推进 → 前端也收不到 state → 画面冻结（画布全黑）。**这是桩的自循环依赖，与产品链路无关** |
| **5175 = 真实宿主**（`toonflow-game-web`），需要登录 + 故事会话才能进游戏 | 本次未走完交互流程（登录门槛），改用 60002 直连做真实链路断言 |
| **CD 按真实经过时间递减**，不是按 tick 次数 | `entry.ts` `tickDeltaMs()`：`_dec = round(dtMs/100)`，最小 1。→ **连续快速发 tick 不会让 CD 掉得更快**（这是设计，不是 bug） |

> 因此复测采用「**entry.js 权威逻辑层**（dev-host 桩内直接驱动）」+「**60002 真实链路**（API 断言）」双通道交叉验证。

## 4. 🔴 发现的真 bug：消耗品数量不扣（`durability` 默认 −1）

### 现象
```
干粮（count=1）连点 3 次 → 3 次都「恢复 14 生命」，count 始终 = 1
```
即：**一次性消耗品可以无限次使用**。

### 根因
`entry.ts` `useBagItem()` 按 `durability` 分三档（4776 行）：
- `dur < 0` → **永久**：不扣物品、不扣耐久
- `dur = 0` → 一次性：每次 `count - 1`
- `dur > 0` → 有限耐久

而 `durability` 的唯一来源是 `s.itemMeta[name].durability`（2934 行），而 `itemMeta` **只在玩家手动编辑物品（`sys_item_edit`）时写入**（7295 行）。
默认 `itemMeta` 为空 → `num(undefined, -1)` = **−1** → 所有物品被判为「永久」。

**已验证**：手动注入 `itemMeta["干粮"].durability = 0` 后，物品用掉即从背包消失（`count-1` 生效）→ 扣除逻辑本身没问题，问题在**默认值**。

### 影响
- 参数卡里的物品（字符串形式，如 `"干粮"`、`"银鲤×29"`）全部无 durability → 消耗品（干粮、药瓶）可无限用
- 装备/武器同理：不会因使用而损毁
- 该会话的 `itemMeta` 为空（DB 与内存态都验证过），即**线上现状即此状态**

### 建议修法
在 `mergeBag()`（2934 行）按物品语义给默认 durability，而不是一律 −1：
- `heal` / 消耗类（`inferItemType` 判定的 heal/buff 且非装备）→ 默认 `0`（一次性）
- 装备/武器（`atk` / `attribute` 类型）→ 保持 −1（永久）或按配置
- 判定不到类型时保持现状（−1），避免误伤永久道具

> ⚠️ 这是**独立于 v3 MCP 接入面**的既有问题，本次复测顺带暴露。

## 5. 本次顺带修正的测试方法问题（记录以免复发）

| 问题 | 真相 | 修正 |
|---|---|---|
| L6「攻击说距离超范围」 | 真实链路 state 是权威的，**不能改坐标**；怪在 164m 外 | 改用 MCP `spawn_entity` 在玩家 3.5m 处生成目标（MCP tool 走 entry 权威通道） |
| L7「隔 1s 依次点三个技能应冷却中」 | 三个是**不同技能**，独立冷却 → 本来就该都成功 | 改为「同一技能隔 1s 再点 → 冷却中」+ CD 归零后可再放 |
| CD 读值不准 | 读 CD 的那次 `tick` **自己又推进了 CD**；DB 是节流快照（滞后 2s） | 改用 MCP `query_state` 读**内存态**（零滞后、不推进游戏） |
| 「CD 不衰减」误判 | CD 按**真实毫秒**折算，快速连发 tick 每次只按最小 100ms 计 | 按 100ms 真实节奏发 tick |
| 满血时物品「没加血」 | 满血 → 回血被 clamp（正确行为） | 满血时断言「特效产生 + 不超上限」 |
