## 3. 发现的 3 个问题

### BUG-2（严重）：游戏世界推进速率从 10Hz 掉到 0.36 Hz

**实测**（40 次 tick 请求 / 5.7s）：

| 指标 | 值 |
|---|---|
| 请求数 | 40（10Hz） |
| 响应内 `state.tick` | 1 → 3 |
| **DB 里的 `state.tick`** | **0 → 2** |
| 有效推进频率 | **0.36 Hz**（设计 10 Hz） |

**根因链**（两个设计叠加）：

1. `tick.ts` 每个请求都 `getPluginData()` 从 DB 读 `plugin_state`（`PluginSessionDataService` 无内存缓存）；
2. `entry.js handle_action` **无状态** —— 每次都拿 DB 里的 state 重建，`step()` 只推进一次；
3. O2 的 `PLUGIN_STATE_FLUSH_MS = 2000` 让落盘滞后最多 2s；
4. → **未落库的中间状态被整体丢弃**，世界推进速率 = 落库速率 = 1/2s = **0.5Hz**。

**连带影响**（全部实测确认）：

| 受影响项 | 设计 | 实测 |
|---|---|---|
| 技能 CD 递减 | 24 tick = 2.4s | **6.4s**（2.7x） |
| 野怪 AI 移动 / 攻击 | 10Hz | 0.36Hz |
| 死亡渐隐（deathMs 递减） | 4 tick = 0.4s | 卡住不动（落库窗口内） |
| 玩家移动（服务端坐标） | 3m/s | 0.36Hz 的推进 → 视觉与服务端脱节 |

**注**：v2 文档 O2 的实测结论是「plugin_state updatedAt 42 秒仅 1 次更新」，当时把它当成纯收益（少写库）。**但那份实测只看了落库次数，没看世界推进速率** —— 落库降频在"entry 无状态"的前提下是有代价的。

### BUG-3（用户可见）：视觉已贴近，攻击却说「附近没有敌人」

**实测**（模拟玩家 3m/s 走向野怪，每帧带 pose）：

```
步进 | 视觉距 | DB距(DB滞后) | 点击attack结果
  21 |   6.00 |     8.10     | '附近没有敌人'  ❌
  28 |   3.90 |     8.10     | '附近没有敌人'  ❌
  35 |   1.80 |     8.10     | '附近没有敌人'  ❌
  36 |   0.00 |     8.10     | '附近没有敌人'  ❌   ← 玩家就站在野怪身上
```

**根因**：`entry.js case "attack"` **不读 `params.player`**，只用 state 里的玩家位置判 4m 范围（`SKILL_RANGE_M=4`）；而 state 里的位置来自 DB（滞后 2s）。移动速度 3m/s × 2s = **6m 滞后** → 视觉距 4~10m 的攻击被误判为超范围。

**对比**：`case "skill"` 和 `case "tick"` 都用 `params.player`（前端每次都带 `lastLocalPose`），所以技能不受影响；**只有 `attack` 依赖服务端位置** —— 这是设计不对称。

**修复方向（二选一）**：
- A：`attack` case 也接受 `params.player`（与 skill 对称）—— 改 1 行，代价最小；
- B：让 entry.js 有内存态（见下），状态不再依赖 DB 往返 —— 根治但改动大。

### BUG-1（中等）：死亡渐隐期 `deathMs` 停止递减

击杀响应内：`hp=0, deathMs=400, alive=true, kills+1` —— 伤害与奖励结算**完全即时**，没问题。
但随后 12 个帧 tick 内 `deathMs` 一直是 300 不再递减 → 渐隐动画卡住、实体长期留在 state。

根因同 BUG-2：渐隐靠 `step()` 里的 `deathMs -= 100`，而 step 只在落库后的状态上推进。

**附带观察**：`deathMs > 0` 的渐隐期里 `alive` 仍为 `true`，`case "attack"` 只滤 `alive !== false` → **玩家可以选中正在渐隐的尸体再打一次**（`damage()` 有 `!target.deathMs` 防二次结算，所以不会重复计分，但会浪费一次普攻）。

## 4. 测试过程中的其他发现

| 发现 | 说明 |
|---|---|
| `plugin_state` 由**首次 /plugin/tick** 初始化 | `#野外生存` 只写 miniGame 指针；`entry.js` 的空态兜底 `emptyState()` 才建 state（phase="select"）。我最初的脚本假设"编排后自动进选人"，是错的。 |
| 开发态 3000 是 **mock host** | `test-host/server.js` 的 tick 只 echo 状态、`skills: []`、kills 不变 —— **不结算冷却/伤害**，不能用它测即时性。必须用真实 5175 + 60002。 |
| 5175 iframe 是**跨源** | `http://127.0.0.1:60002/plugin/getAsset?...&token=...` → 主文档读不到 `contentDocument`；宿主用 postMessage 代理 tick（与 v3 文档 §2 的判断一致）。 |
| 浏览器抓包只覆盖主帧 | iframe 自身发出的 `/plugin/tick` 不在主帧 capture 里 —— 抓包验证 tick 时序这条路走不通。 |
| 后端安装副本 ≠ 源码仓 | 运行时 authority 是 `toonflow-app-run-db/plugins/1/.../entry.js`（mtime 11-11 18:06），源码仓 `plugins/toonflow-field-survival/entry.js`（11-12 09:45）。**改代码必须同步到安装副本**（v2 部署铁律）。 |

## 附：与 v3（MCP 接入层）的关系

这次测试对 v3 设计有三条直接影响（**已全部落入 v3 修订**）：

1. **v3 §5.1「写 tool 必须走会话串行锁」是对的**——但还不够：MCP tool 写入后，
   **下一个 tick 会从 DB 读到旧状态并覆盖它**（无内存态时）。MCP 写操作必须与 tick
   **共享同一份内存态**，否则 AI 刚杀掉的怪会被下一个 tick"复活"。
   → 已新增 v3 §5.1（内存态硬性要求 + 实现建议 + 多进程部署提醒）。
2. **v3 §7 验收项 2「玩家 ≤100ms 可见」在修复前不成立**——世界推进只有 0.36Hz，
   "下一个 tick"实际是 ~2.8s 后。→ 已改为「≤2 个帧 tick（≤250ms）」并新增验收项 2b（无状态覆盖）。
3. **v3 实施路线新增 M0 前置**：内存态修复必须先落地，否则 MCP 的"即时"无从谈起。
   → v3 §9 已加 M0 行（✅ 已实施）。

同时 v2 §3.5 记录了「O2 降频是否安全，取决于读路径是否也读 DB」这一教训：
**降频类优化不能只看写侧指标（落库次数），必须同时验证读侧（世界推进速率）。**
