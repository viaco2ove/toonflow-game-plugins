## 护送货物找回 + 任务目的地寻路 + 「到达」按钮（feat(plugin) 515874a）

用户需求三连：① 丢失的货物增加找回功能，直接回到用户旁边；② 增加寻路功能，
点击后用户自动走去目的地，地图传送时货物不要丢失；③ 目的地增加"目的地"图标，
走近显示"到达"按钮，点击后任务完成并进行奖励。

### 根因（货物为什么会"丢失"）
1. **后端** `handleLevelChange`：货物是 `side:"ally"`、没有 `mapName`、不在 `partyIds`
   → 走 ally 分支被 `parkRole` 停回 start_map，玩家到新图后 entities 里找不到它
   → `cargoAlive=false` → 任务板显示「货物：已丢失」。
2. **前端** `switchLevel`：`e.side !== "ally"` 过滤会把货物一起清掉（双保险失效点）。
   注意前端那条注释写的过滤条件是 `e.side !== "ally"`，实际 ally 过滤本身就足以杀掉货物。

### 改动
- **entry.ts**
  - `handleLevelChange`：`questcargo_` 前缀 / `entity_type==="QUEST_CARGO"` 的实体
    直接置 `mapName=lv` + `snapParty` 时贴到玩家身边（`ALLY_FOLLOW_GAP_M`）。
  - 新 action `sys_quest_recover_cargo`：在玩家身边重生成；`failReason==="cargo"` 的
    failed 任务连任务一起救活（status 回 active、`acceptedTick` 重置防立刻再超时）；
    **超时失败（failReason="timeout"）不救活**，但货物仍补。
  - `spawnQuestCargo`：先 splice 掉场上同 id 残留（含死亡淡出中的尸体）再生成，
    否则「找回」复活的是一具死尸。

    destRadius/cargoLost`。
- **vue/src/App.vue**
  - `questDestinations` computed：active 且有 arrive/explore 坐标、目的地在本图。
  - `drawQuestDestLayer`：canvas 层画旗帜（上下浮动）+ 椭圆判定圈（走近金色实线、
    远青色虚线）+ 目的地文字。
  - `updateQuestArriveBtn`（10Hz）+ `syncQuestArriveBtnPos`（render 每帧）：
    走近 → DOM 浮动「到达」按钮；`label` 目标已达成时变「交付」；
    坐标换算 `scale = clientWidth / W`（逻辑→CSS）+ `ox/oy = canvas.offsetLeft/Top`
    （.stage-rotate 是定位祖先，canvas flex 居中可能有黑边偏移）。
  - `onQuestArriveAtDest`：先 `sys_quest_arrive`，再轮询 questView.done（最多 ~1.2s）
    自动 `sys_quest_turnin` 发奖励 —— 对应用户"点击后任务完成，进行奖励"。
  - `questGoToDest`：同图 → `input.moveTo` + `recomputeMoveToPath`（A*）；
    跨图 → `pendingQuestWalk` 记坐标 + `onSysTravel`，`switchLevel` 落地后接着走。
  - `switchLevel` 的 ally 清理放行 `isQuestCargo`。
- **QuestPanel.vue**：货物行加「找回货物」，操作区加「寻路」。
- **mockHost.ts**：补 `sys_quest_recover_cargo` standalone 分支。

## 跨图寻路「点了没反应」：关卡 key 归一污染（2026-10-18 下午）

### 症状
接 Q12（探入冥夜走廊）点「🧭 寻路」→ toast 有、`pendingQuestWalk` 挂上，但玩家原地不动、
`currentLevelName` 永远停在 "Mulberry Town"。直测 `onSysTravel('Mulberry Dungeon')` 后
后端 `s.levelName` 已变、前端没切图、`teleportTarget` 被消费后为 null。

### 根因（三层叠加）
1. `loadLevelByName("Mulberry Dungeon")` → `levelNameToFile` 推成 `mulberryDungeon`，
   而故事包里只有 `maps/mulberryDungeon1..5.json` → 返回 null → `switchLevel` **静默 return**。
2. `QUEST_MAP_SLUGS` 里 `mulberrydungeon` 和 `mulberrydungeon1` **同值** "Mulberry Dungeon"
   → 层号在归一那一步就丢了；反查不回来。
3. 老存档只持久化了归一后的 `questBoard`，`restoreQuestBoard` 再 `normalizeQuestDef` 时把
   `o.map`（已归一）当成 raw 写进 `mapRaw` → `mapRaw = "Mulberry Dungeon"` 而不是 slug。

### 修法（双端 + 读时兜底）
- entry.ts：`QUEST_MAP_SLUGS` key 改回**真实 camelCase 文件名**（`mulberryDungeon1`），
  加 `QUEST_MAP_SLUG_INDEX`（大小写/分隔符无关）与 `QUEST_MAP_COMPACT`；
  `QUEST_MAP_KEY_REV` 反查（**同显示名取最长 slug** → "Mulberry Dungeon" 自愈成
  `mulberryDungeon1`）；`rawQuestMapKey()` 写 `mapRaw` 时反查；
  `questMapKey()` 只用于「是否同一张图」的判定（到达校验 / 可接归属 / 自动到达三处）。
- `buildQuestView`：`mapRaw` / `destMapRaw` **读时**再 `rawQuestMapKey(str(o.mapRaw)||str(o.map))`，
  跳过归一化的恢复路径也拿得到可用 key。
- App.vue：`levelKeyOf()`（key → 中文显示名 → 紧凑串 → 前缀兜底）+ `sameLevel()`；
  寻路 / 地图面板传送 / 传送门 / 开局切图 / 落地续走全部走它。
  `switchLevel` 改返回 `boolean`，加载失败弹 toast 并清 `pendingQuestWalk`；
  `applyTeleport` 切图失败不落点、落点变更后重算 A* 路径。
- vite.config.ts：`seedQuestDefs` 由「已存在就整体跳过」改为**按 id 合并补齐**
  （`__pdGet` 返回 `{value,updatedAt}` 包装体，必须先解包）。

## 混合目标任务（gather + arrive）为什么「寻路完还是交不了」

## 暗核吸收产生诡异技能名（fix(plugin) c2559b1）

### 用户截图反馈
8 个吸收暗核得到的技能里有 4 个是 AI 描述文字被截 12 字当技能名：
- "暗核已解析......宿主"
- "我为"
- "暗核的残渣正在与你融合"
- "暗核吞注入"

### 根因（entry.ts:3453-3456）
AI 输出纯文本（不是 JSON、也没命中池内）时，旧代码会执行
`picked = cleanSkillName(raw.split(/\n/)[0]).slice(0, 12)` —— 把整段描述
第一行截 12 字当技能名 → 写进参数卡 / 快捷栏 / 技能栏。

### 修法
- **有池**：池内匹配失败 → picked 留空 → 走 3461 行兜底池子随机
- **无池**：才接受 AI 纯文本第一行作为自由生成的技能名

### 测试
`.cache/test_kill_reward.mjs`（被 gitignore 不进 git）新增 §5 四个子场景：
- 5.1 有池 + AI 纯描述 → 走兜底池（不收录描述文字）
- 5.2 有池 + AI 描述含池内子串 → 按池内收（防误伤）
- 5.3 无池 + 合法 JSON → 走 JSON 解析
- 5.4 无池 + 纯描述 → 接受截 12 字（自由生成模式保留）
- 整体 29/29（之前 22 项 + 新增 7 项）

### 经验
- **永远不要把"AI 自由发挥的纯文本"当结构化数据用** —— 至少要有"看着像名字"
  的判定（长度上限 + 池内匹配 + 兜底）；本工程有 `skillPool` 这个"故事一致性"护栏
  就该当 hard constraint 用，而不是软提示
- `cleanSkillName()` 只剥括号注记，不会切长句 → 配合 `slice(0,12)` 极易截到描述片段
