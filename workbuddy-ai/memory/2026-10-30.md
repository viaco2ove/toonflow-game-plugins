## 通信(短信) 功能设计评审

对 `md/curr_design/toonflow-field-survival/通信(短信)/` 下的 req.md、通信(短信).design.md、原型图（HTML + 接口说明）做了设计评审，
产出 `通信(短信)/评审意见.md`。

### 结论
结构与方向正确、存储选型准确，但有 3 个「不做就会做错」的硬伤：

1. **H1 玩家→AI 链路缺失**：设计 §6.3 只把「群聊」注入 prompt，玩家在单聊里写的消息 AI 根本看不到 → 聊天退化成单向广播。
   修法：单聊+群聊都注入玩家消息（★ 标注未回复），玩家发消息触发目标 AI 以 P0 优先级立即决策回复。
2. **H2 未读公式错**：`findIndex` 返回 -1（lastReadMsgId=null）会把玩家自己发的消息算进未读；公式应按条数差 + 排除 `from === "player"`。
3. **H3 「谁把 AI 的 message 写进存储」无人认领**：`brain.ts` 是纯逻辑模块、不持有 pluginData 句柄，decision 到不了存储层。
   定为**方案 A（推荐，全前端）**：App.vue 消费 `decision.message` → `smsStore.receiveMessage()` → store 内防抖落库。
   （方案 B 后端落库会踩 `数据储存.t_plugin_session_data.md` 已知坑 #1 写-读竞态。）

### 其他发现
- `brain.ts` 的 `brainBusy` 是**全局单槽闸门** + 8s 超时，5 个角色共用一个 LLM 通道 → 「AI 主动发短信」会因闸门竞争随机丢失。
  规则：拿不到闸门走 `fallbackDecision` 时**不发短信**。
- 存储 `sessionId` 策略未定义（设计只写了 dataKey）→ 跨故事串号风险。
  应为 `sessionId="all"` + `dataKey="sms_conversations:<story>"`，或 sessionId=当前会话；不要用裸 `sms_conversations` + `all`。
- 数据结构缺：Message.type 扩展契约、conversationId、**消息条数上限**（防 JSON 膨胀撞 pluginData.set 上限）；ID 建议改 string。
- 原型与落地形态冲突：原型是 900×600 独立面板，但落地是 SystemPanel 内 tab（`.sys-panel` 80%×80%，`.sp-tab{flex:1 1 30%}`）。
  原型的独立头部（含 × 关闭）没有对应位置；原型缺系统按钮角标；配色（深蓝+亮红）与游戏现有深灰风格不一致。
- 现有已有一套「触碰角色→聊天」机制（`App.vue` 的 `chatMessages` + `chatCommand.ts`），
  短信面板与它**是两套东西**，设计没说明关系 —— 需明确是并存还是打通。

### 落地时的关键决策（与 v2 文档有出入，已回写文档）
1. **接线点从 App.vue 移到 `ai/index.ts`**：`callBrain()` 有三个调用点（调度器 pump / `#ai` 指令 / 短信回复通道），放在 App.vue 只能覆盖一个 → 短信会漏发。统一放 `sms/dispatch.ts`。
2. **`dispatch.ts` 单独成文件**：`ai/index.ts` 已 `export { issueAIChatCommand }`，chatCommand.ts 放进 dispatch 会形成循环依赖（index → chatCommand → index）。
3. **区分「没拿到 LLM」和「LLM 没说 message」**：前者保留待回复登记等下次心跳，后者也保留；只有「有 message 但被冷却挡」才清除登记。靠 `callBrainDetailed()` 的 `gotLLM` 判定。
   **后续又细化**：`callBrainDetailed()` 返回 `failReason: "gate" | "parse" | "empty" | "emergency"` ——
   - `gate`（闸门被占/空响应）→ **重试**（最常见，稍后能拿到）
   - `parse`（JSON 解析失败）→ 最多再试 2 次
   - `emergency`（紧急层接管）→ **不重试**（重试也没用）
   不区分的话：要么都重试（解析失败白烧 25s 窗口），要么都不重试（闸门一挡玩家就收不到回复）。
4. **玩家短信唤醒 AI 走独立 LLM 调用**，不塞调度器 P0 队列 —— 队列有预算/熔断，战斗态还会筛掉「离玩家远」的角色，玩家刚发的消息被筛掉要再等 20s。抢不到闸门就重试（最多 25s）。
5. **`keepAction: true`**：短信回复只取 message，不覆盖 `currentAction`/`goal`/`lastBrainTick` —— 回个消息不该把「正在采集/战斗」的动作打断。
6. **新增单聊冷却 60s**（群聊 180s 保留）；回复不受冷却限制，但回复会刷新计时。
7. **判定顺序：先判冷却再建会话** —— 否则被冷却挡掉却建出空会话。
8. **`awaitingReply` 改为派生状态**（每次改完消息重算），不是手动 toggle —— 多条消息交错时手动 toggle 会算错。
9. **★ 标记改为「最后一条 AI 回复之后的所有玩家消息」**（O(n) 扫描，原来 O(n²)）—— 玩家连发 3 条，AI 一条没回 → 3 条都标 ★。AI 回一条 → 这批全部算已回复。

## 通信(短信) 会话入口改造：搜索框 + 下拉联系人选择器

用户提了两个入口方案，采纳**方案 1**（搜索框点击弹出下拉，含全部角色 + 已建群聊 + 新建群聊入口），
理由：避免几十个角色把真正的会话淹没在列表里，且与微信/QQ 交互一致。

### 新增
- `vue/src/sms/SmsContactPicker.vue` — 搜索框 + 下拉（三段：已有群聊 / 全部角色 / ＋新建群聊）；带「托管」标识
- `vue/src/sms/store.ts` — 新增 `startPrivateChat(roleId, roleName)`：**玩家主动建单聊**（与 `ensurePrivateConversation` 的「AI 消息驱动建」区分）
- 接线：`SmsConversationList` → `SmsPanel` → `SystemPanel`（`sms-start-chat`）→ `App.vue`（`onSysSmsStartChat`）

### 下拉里「已建过单聊的角色」不再重复出现
`roleList` 计算时排除 `existing`（已在 private 会话里的 member）—— 避免同一个人出现两次。
副作用：搜「陈」时陈南璇不出现（她已有会话），搜「苏」出现苏沫/苏婉。

### ★ 选择动作从 `click` 改到 `pointerdown`
`SmsContactPicker` 的下拉项改用 `@pointerdown` 触发选择（`onItemPointerDown`，只响应主键 button===0）。
原因：组件挂在可拖拽的系统面板里，父层用了 `setPointerCapture` —— 一旦 pointerdown 被捕获，
浏览器可能不再在选项上合成 click → 「点角色没反应」。pointerdown 比 click 早，不会重复触发。
搜索框的「×清空」和「▾/▴ 展开收起」两个按钮也一并改成 pointerdown（同样的风险）。

### ★ 修掉一个既有 bug：mockHost.ts 缺 `num` 定义
`src/mockHost.ts:575` 用了 `num(...)` 但文件里**从未定义**（HEAD 里就存在，非本次引入），
standalone 模式下 `makeEnemyFromEntityType` 一调用就 `ReferenceError: num is not defined`。
在文件内补了本地 `num(v, d)` 实现（`mapConfig.ts` 有一份但没导出）。

### 新增集成测试：scripts/test-sms-dispatch.mjs（26 项断言）
覆盖 store 自测没覆盖的「决策 → 真短信」这一段：有 message 落库 / 无 message 不发也不清登记 /
`to` 指向不存在的群降级单聊 / AI 不在群里降级单聊 / 非法 to 降级单聊 / 空白 text 不发 / 合法群落进群 / decision=null 不发。

★ **测试踩的坑**：dispatch.ts 和 store.ts 一起打包时各自 bundle 了一份 store → 两份 state，
群聊查不到（"群聊不存在"）。修法：把 `./store` 标为 external，dispatch.js import 同一个 store.js。
